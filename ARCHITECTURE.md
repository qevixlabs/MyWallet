# ARCHITECTURE.md

How MyWallet is put together, and why each rule below is the way it is.

MyWallet is an offline-first Android money tracker: Kotlin + Jetpack Compose, Room, Hilt, minSdk 26. Multi-currency, Bikram Sambat or Gregorian, English or Nepali. No server, no account — the database on the phone is the only copy of the user's financial history, which is why several rules below are stricter than they would otherwise be.

## Commands

There is deliberately **no Android Studio** in this workflow: build with `./gradlew`, run on the emulator through `adb`.

**Every task name carries a flavour**, because the app ships two ways — see *Two distributions* below. `github` is the one to use for everything ordinary; `play` is only built when something is going to the Play Console.

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@17    # keg-only; /usr/libexec/java_home cannot find it

./gradlew :app:assembleGithubDebug
./gradlew :app:testGithubDebugUnitTest
./gradlew :app:testGithubDebugUnitTest --tests "com.mywallet.LoanMathTest"
./gradlew :app:testGithubDebugUnitTest --tests "*.LoanMathTest.the schedule clears the balance to exactly zero"
./gradlew :app:lintGithubDebug                    # clean — any error is yours
./gradlew :app:assembleGithubRelease              # unsigned unless keystore.properties exists
./release.sh "release notes"                      # test + build + tag + GitHub release, for the in-app updater

./gradlew :app:bundlePlayRelease                  # the .aab the Play Console takes
./gradlew :app:lintPlayDebug                      # the other half of "lint is green"
```

`release.sh` derives its tag from `versionCode`/`versionName` in `app/build.gradle.kts` and force-pushes, so bump both before running it. It refuses to run without `keystore.properties` (not in the repo), because an unsigned APK cannot install over the copy on the phone. It builds the **github** flavour: publishing the other one would ship a release the app has no way of updating itself to.

Tests are plain JVM JUnit — no Robolectric, no instrumentation tests, no `room-testing` dependency. Anything worth testing therefore has to be pure: put arithmetic and mapping logic in `domain/` or `core/` where a unit test can reach it.

### Running it on a device

```bash
export PATH="$HOME/Library/Android/sdk/platform-tools:$HOME/Library/Android/sdk/emulator:$PATH"
emulator -avd Medium_Phone_API_35 &
adb install -r -d app/build/outputs/apk/github/debug/app-github-debug.apk
adb shell am start -n com.qevixlabs.mywallet.debug/com.mywallet.MainActivity
```

### Two distributions

**The app ships twice, and the difference is one sentence of Google's**: *"An app distributed via Google Play may not modify, replace, or update itself using any method other than Google Play's update mechanism"* (Device and Network Abuse). This app has always fetched its own APK from GitHub Releases and handed it to the system installer, which is exactly what that forbids — so the `distribution` flavours exist, `github` and `play`.

**It is a source-set split and deliberately not a runtime `if`.** What must not ship is the *code that downloads and installs an APK*, and the only way to be sure of that is a source set the variant never compiles: `UpdateChecker` lives in `src/github/java`, the Play build compiles a stub of the same name in `src/play/java` that answers "nothing newer" and can do nothing else, and `AvailableUpdate` sits in `main` because Settings — which is in `main` and can see neither checker — names the type. `REQUEST_INSTALL_PACKAGES` and the `FileProvider` are declared in `src/github/AndroidManifest.xml`, since a manifest in `main` is merged into every flavour. The Play APK has been checked for both: no permission, and no `vnd.android.package-archive` or release URL anywhere in its dex.

**Settings withholds the whole offer rather than greying it out** (`BuildConfig.SELF_UPDATES`). A copy installed from Play is updated by Play, so a row that could only ever answer "up to date" is a row about nothing. The version number stays, because that is a fact either way.

**Nothing else differs.** Same `applicationId` — Play would refuse a change and the ad unit is bound to it — same signing key, same code, same figures. Which means the two are still one app in every sense but one: **a Play install and a GitHub install cannot update each other**, because Play re-signs with its own key and Android only accepts an update signed as the copy already installed. Moving between them is an uninstall, a backup and a restore, exactly as changing the package name was.

**The `applicationId` is `com.qevixlabs.mywallet`; the Kotlin `namespace` is still `com.mywallet`.** Those are two different things and only the first is a fact about the installed app — which is why the activity above is launched as `com.qevixlabs.mywallet.debug/com.mywallet.MainActivity`, the package on the left and the class on the right. The namespace is where the source lives, it is invisible to Android's package manager and to Google's ad servers, and renaming it would touch every file to change nothing observable.

Changing the `applicationId` costs a reinstall, because Android accepts an update only when the package name matches the copy on the phone: the new build installs *beside* the old one with its own data directory and an empty database. The way through is a JSON backup out of the old app and a restore into the new one. It has been done twice — `com.niraj.mywallet` until 0.61.0, then `com.mywallet` until 1.1.2 — and both times only because the app was on neither Play nor AdMob.

The second move was forced: **Google's ad servers refuse `com.mywallet`.** An interstitial request from it is answered with HTTP 403 where the identical release-signed, minified APK under `com.mywallet.trial` or `com.mywallet.debug` is served — run within one minute on one device, which rules out fill, throttling, R8 and signing. `com.mywallet` is generic enough that somebody else has already spent its reputation. **Frozen from here, and this time the lock is real:** the point of moving was to register *this* id with AdMob, an ad unit is bound to the package it was created for and cannot be moved, and either that registration or a Play listing turns a further change into a stranded database (the only copy of the user's financial history) and an orphaned set of ad units.

The debug build has `applicationIdSuffix .debug`, so it sits beside a real install rather than replacing it. To inspect or seed its database: `adb exec-out run-as com.qevixlabs.mywallet.debug cat databases/mywallet.db > local.db` (checkpoint the `-wal` locally); to write one back, `adb push` to `/data/local/tmp` then `run-as ... cp` it into `databases/`. There is no `sqlite3` binary on the emulator image and `adb root` is refused.

Driving the UI with `adb shell input`: dismiss the Google IME's "Try out your stylus" overlay first or typed text goes nowhere, escape spaces as `%s`, and never use `input keyevent 4` to close the keyboard — it pops the screen and discards the form.

## Architecture

**One table is the atom.** Salary, a bill, a subscription, a loan instalment, half a transfer and a cash correction are all rows in `money_entry` with different flags against different holdings. New features become new *kinds* of entry, not new stores. `WalletRepository` is the single door between the UI and storage; `RecurrenceRepository`, `LoanRepository` and `TransferRecorder` sit alongside it for the things that need their own rules.

**Layers.** `data/db` (entities, DAOs, hand-written migrations) → `data/repo` (repositories, all suspend/Flow) → `domain` (typed models with no Android or Room dependency, plus `LoanMath` and `Recurrence`) → `ui/screens` (one ViewModel per screen exposing a single `StateFlow` of a data class; Composables get formatted strings, never do arithmetic). `core/money` and `core/date` are the two primitives everything else is built on. Hilt wires it all from `di/AppModule.kt`.

`Clock` is injected everywhere rather than calling `LocalDate.now()`, so time-dependent logic stays testable.

### Money

`Money` is a value class over a `Long` count of minor units. Never `Double`, anywhere, for anything a user sees. Each entry stores the amount in its own currency **plus** `base_amount_minor`, `rate_to_base` and `base_currency_code`, captured at save time and never re-derived: a $10 charge from March keeps March's rate so a closed month stays closed.

- Anything that sums across entries must use `base_amount_minor`. Summing `amount_minor` across mixed currencies is always a bug.
- **Changing the display currency restates every stored conversion** (`restateBaseCurrency`, called before the setting is written). The frozen figure is only usable while it still names the currency being displayed; the moment the user switches to dollars, every stored figure is rupees, and drawing it under a dollar sign is wrong by a factor of a hundred and forty. It converts from each row's *own* amount rather than from the frozen one — that is the fact, and going through the old conversion would round twice — and it happens once, on the change, because the month totals and the breakdown are summed in SQL and a sum cannot convert its rows one at a time. At today's rate, which is the only rate the app has; a row whose currency has no rate on file is left exactly as it was.
- **A holding is converted whenever the currencies differ, whatever it asks to be read in.** `show_in_display_currency` decides which figure *leads on a row*; every total is summed from the converted one. Tying the two together left a rupee debt under a dollar display with no converted figure at all, so "to pay" fell back to its own and added रू 10,50,000 into a total wearing a dollar sign.
- **Only one rate table is fetched, and every other pair is worked out from it.** The feed is asked for the display currency's rates and nothing else, because that is the only conversion the totals need. `ExchangeRateRepository.rate` therefore tries the row on file, then the row that answers the same question upside down, then a pivot through whichever base the table does hold — and returns null rather than a wrong 1.0 when none of the three works. It used to give up after the first: a transfer from a rupee account to a dollar one at the same bank asked for NPR→USD, found no table based on USD, and took the fallback. रू 1,000 arrived as $1,000, in both balances and in the timeline, as fact. The form refuses to save a cross-currency transfer it cannot value for the same reason — a movement the app cannot price is one it must not write down.
- *Balances* are the exception and convert at current rates, because a balance is what the money is worth now. An account that cannot be converted is flagged (`balanceInBase == null`), never silently dropped from a total.
- Which currency an amount is *shown* in is a per-holding choice (`show_in_display_currency`, on both `account` and `loan`). A $10 charge from a dollar account did not become rupees, so leading with a rupee figure would state a valuation as if it were the transaction; the paying half of a cross-currency transfer is the exception, because there the conversion actually happened and both figures are facts.
- **Two lines, always in that order.** Wherever a single foreign figure is drawn — an entry, an account, a debt, a projection — the currency the money is actually in goes on top and what it comes to in the display currency goes underneath. Never one without the other: the top line alone leaves a holding that cannot be found inside the total above it, and the bottom line alone states a valuation as though it were the transaction. Totals are the exception and are summed from the bottom line, because that is the only figure that can be summed.
- **A symbol's spacing belongs to its currency, and the sign goes in front of both.** `CurrencyOption.spacedSymbol` is true for the rupee and the Indian rupee and false for everything else, so the app writes "रू 100", "₹ 100" and "$100" — each the way it is written where it is spoken. The minus sits ahead of the symbol ("-रू 100", not "रू -100"): the eye takes the symbol as the start of the amount, so a sign behind it lands mid-figure and a debit reads as a credit at a glance. `inputPrefix` gives a text field's prefix the same spacing, so a box being filled in and the figure it becomes are one number written twice rather than two ways of writing it.
- **Eighteen currencies are offered**, and three of them — the Bahraini, Kuwaiti and Omani dinars — are *thousandths* rather than hundredths. That is the whole reason `minorUnits` is a property of `CurrencyOption` and not a constant: storing a dinar as two decimal places puts every figure out by a factor of ten. Settings offers them in a picker rather than as chips, for the reason the reminder lead time is one — eighteen chips wrap into five lines of near-identical two-word answers — and a currency written as its own code is drawn once rather than as "AED AED".
- **A form offers four of them and keeps the rest behind "Show more".** Eighteen chips wrap into five lines of three-letter codes, so choosing the currency somebody was always going to choose meant reading the other seventeen first. Which four is the *user's* answer and not a fixed list: `CurrencyOption.shortlist` leads with whatever is selected — the form opens on the display currency, and a row of choices that hides the one it is on cannot show its own answer — then the currencies their holdings are actually denominated in, **most held first** with recency breaking the ties — the same rule the accounts are ranked by, since ordering on recency alone put a currency taken up once last week in front of the one most of their money is in — then `SUGGESTED` (NPR, INR, USD, AED) to make the number up. Somebody paid in riyals says so once by opening an account in them and never answers the question again. Read from the holdings (`AccountDao.currenciesInUse`, debts unioned in, since money borrowed in dirhams is a currency this user uses) rather than kept as a tally of what has been tapped: a currency picked by mistake and deleted stops being suggested, which a tally could never say. Worked out once when the form loads and never again as the user taps — a list that reordered itself under the thumb would move the chip beside the one being aimed at — and expanding appends the rest after the four rather than redrawing them in canonical order, because expanding a list must not move what the eye is already on. There is no way back: once every currency is on screen there is nothing left to ask for. And it is deliberately **not a chip** — every other pill in that row is a currency, and one shaped like them reading "Show more" was an eighteenth thing to read past, which is the opposite of what it is there for. It is the words in the colour that means "this does something", with no border of its own, centred against the chips and padded to their height so what the thumb aims at is the size of what it sits beside. The only other place the full list appears is Settings, which is a picker and has no length problem.

**Digits group the way the calendar's reader does** — 1,00,000 in Bikram Sambat, 100,000 in Gregorian (`DigitGrouping`, `CalendarSystem.grouping`). Lakhs and crores were unconditional for a long time, on the reasoning that the grouping describes the *reader* rather than the money. That reasoning stands; what changed is how the reader is asked about. The **calendar** is the app's own answer to "who is reading this?": somebody reading BS dates takes १,२३,४५,६७८ at a glance and somebody reading Gregorian ones counts the digits. Neither the language nor the currency can stand in for it — the app is read in English by plenty of people who think in lakhs, and a Nepali reader with a dollar account groups dollars their own way.

**One formatter carries one style, and everything derives from the one built from the setting.** `MoneyFormatter.forCurrency` is what a row's foreign-currency line is built with, so the two lines of a converted figure can never be punctuated two ways; `rememberAmountGrouping` reads it too, so a box and the amount printed under it agree. The ~thirty places that build a formatter for one row's own currency include several that cannot suspend to ask, so `SettingsStore.grouping` keeps the answer as the flow goes past — the same value, written only by that flow, and read where there is no way to await it. Three at the end and twos above is still what `groupSouthAsian` does, and `groupInternational` is its sibling; both are by hand for the reason they always were. `groupSouthAsian` does it by hand and `MoneyFormatter` takes only the *symbols* from the locale (which is how Nepali still reads १,२३,४५,६७८ in Devanagari). Two things make the platform's own answer useless here: it groups in thousands at every locale the app ships, Nepali included; and `DecimalFormat`'s `#,##,##0` pattern is honoured by ICU on the device but ignored by the desktop JVM the unit tests run on, so a pattern passes its test and is still wrong on the phone. **A box being filled in groups too, and only in what is drawn.** `rememberAmountGrouping` is a `VisualTransformation` on every field that carries a currency prefix — the entry form's "How much?", a holding's amount, a payment, a lump sum, more borrowed, money into or out of a goal — so रू 2700000 is read as रू 27,00,000 while it is being typed, which is the whole point of grouping and exactly where it was missing. The field's own value stays the bare run of digits, which is what `parse` reads and what `toPlainInput` still writes: nothing about saving, parsing or rounding changes. Grouping the *stored* string instead would put separators into the text the caret walks through, and every backspace across one would need handling of its own. Only the whole part is grouped — everything from the decimal point on is passed through as typed, a lone trailing "." included, because a box mid-figure must not have its decimals tidied while they are still being written. The separator comes from the locale by way of the formatter, so a field and the amount printed under it cannot punctuate one number two ways. The `String` overload of `groupSouthAsian` is what does it, and it is a separate overload rather than a parse-and-reformat because a box holds three things a `Money` cannot: a half-typed "1000.", a leading zero about to be overtyped, and more digits than a `Long`.
- `is_adjustment` rows move a balance but are excluded from every income/spending breakdown. That is how cash spent outside the app is reconciled — inventing a fake income entry to explain it would corrupt the analysis. Transfers, borrowing, lending, and principal coming back from someone the user lent to are all adjustments; repaying a debt is spending, and interest received is income. Before adding anything that moves money, decide which of those it is.

**There are no labels.** Every movement used to be filed under one — Food, Bills, Salary — with a starter set seeded on the first launch, a screen to manage them, a chip row on the money form, and "Where it went" built out of them. All of it is gone: the `label` table, `money_entry.label_id`, `recurring_series.label_id`, the seeder, the screen and the strings, dropped by `MIGRATION_28_29`, which rebuilds both tables without the column because SQLite gained `DROP COLUMN` in 3.35 and this app ships to 3.19. **One-way**, and that is what removing the feature means: what an entry was filed under is not recoverable, and a backup written after this carries no labels for an older build to restore.

Two things stood on labels and had to be given something else to stand on. **"Where it went" is a breakdown by holding now** — the same card and bars, grouped by the account the money moved through, which has a colour of its own so the bars keep their meaning.

**A slice with no account is named by what it does have.** An instalment names none by design — it left a balance the app was not watching — so the largest thing most people pay each month sat in a slice called "No account". Those rows are bucketed by the debt they belong to instead, reached the two ways `belongsToLoanId` is (the row's own `loan_id`, or the loan whose series wrote it), and the slice reads "Nabil Bank Loan" so a bank's debt and its savings are not two rows saying the same word. And **a quarter of interest is recognised by its derived id** rather than by the label it used to carry; see *Rates that move*.

**Colour is a holding's, and it is drawn where holdings are.** `HoldingPalette` (once `LabelPalette`) is **fifteen** colours — walked once round the wheel with the two neutrals at the end, so no two are close enough to be mistaken for each other at the size they are read, and starting at the teal because that is what an uncoloured holding gets and leading with the red would hand every first account the app's own "money going the wrong way". Three of them are reds, and three genuinely different ones: a debt is what people reach for a red for, and one red between a card, a term loan and money owed to a friend is no colour at all. It is the picker on an account's form, the dot on the Accounts page, the bar in the breakdown, and the dot on the timeline's own blocks of holdings — those listed the same accounts with nothing in front of them, so a bank found by its green on one tab had to be found by its name on the other. Every row in those blocks starts with a dot, debts included: they have no colour column, so they take the colour their figure is already printed in, exactly as the Accounts page does it. A *movement's* row carries none: the dot beside every entry was the label's colour, and with nothing to group by it would have been decoration.

**Home is a record, the Timeline is a plan.** Home shows what happened — what came in, what went out, where it went, the last few movements — and cannot be stepped past this month: a month that has not arrived has none of that, and filling it with what is *scheduled* made a page of forecasts look like a page of facts. Everything still to come lives on the Timeline, where every row says it is coming. That tab is called Timeline and not History for the same reason: half of what it shows is the future.

**The month is one fact, and both pages read it** — `MonthSelection`, injected into both view models, held for the session and deliberately not persisted (an app reopened a week later should open on the month it *is*). They are one month seen two ways, so "See all" tapped in June has to land on the Timeline in June, and a tab switch either way keeps the reader where they were. Home reads it **coerced to at most 0**: the Timeline may be looking at next March, and Home would have nothing to draw for it.

**The period is also stepped by dragging the page** (`swipeBetweenPeriods`, beside the steppers it drives): left for the next, right for the previous, on Home, Reminders and the Timeline alike, since it is one stepper saying its own nouns. The arrows were the only way to it and they are a 48dp target in the top corner — a stretch on a phone held one-handed, and the last place a thumb rests. It steps at 72dp while the finger is still down, so the label starts moving under the thumb, which is the only thing that says the page can be dragged at all; one step per gesture, however far the drag is carried. How far each page may travel is deliberately not asked here — the view models already clamp their own answer, and a second copy of that rule living in a gesture is how the two come to disagree.

**And the stepper is held above the list rather than scrolled off the top of it** (`PinnedPeriodHeader`, on Home, Reminders and the Timeline). It was the list's first row, so a month with a fortnight of movements in it scrolled away the one control saying *which* month they belong to, and the page then answered a question nothing on screen was asking.

**It does not give way as the page is read down.** That was the first answer — the header slid up out of the way on a downward drag and came back on the first upward one, the way a website's does — and what it produced was a heading that was usually *absent* and reappeared when the reader nudged the page, so "which month is this?" still could not be answered by looking. The month is the smallest thing on the page and the one every figure below it is relative to; a line of a phone screen is what it is worth. So it is a plain `Column`, which is also what puts the timeline's day headings directly under it: a `stickyHeader` pins to the top of *its list*, and the list's top edge is now exactly where the stepper ends rather than behind it.

**And whatever the page holds keeps that gesture.** It is attached to the list rather than to a box over the page, so anything inside is offered the touch first and the page's own drag never begins: a drag starting on a timeline row is that row's delete, in *either* direction — the row claims the touch before it is clear which way the finger is going — and the filter chips still scroll sideways. Nothing arranges that; it is Compose's own ordering, a child that consumes cancelling the parent still waiting for its slop. Drawn over the page it would win everything, and a swipe meant for a payment would step the month instead of opening the red. The screen edges are left alone, so the system's back gesture still works.

**And "See all" is a tab switch, not a push.** It leaves the same back stack behind it as tapping the Timeline tab would (`switchTab`). Navigating plainly stacked a second Timeline *above* Home, and the Home tab could then not be reached at all: its own navigate pops back to Home saving what it popped, and `restoreState` put the very Timeline it had just popped straight back on top. The tab looked dead; the back stack was chasing its own tail. Anything that moves between tabs goes through `switchTab` for that reason.

**And it stops at today, not at the end of the month.** A rule produces no rows for Home, but an entry the user *dated forward* is not a forecast the projection filters out — it is a real row inside the window, and a salary banked for the 3rd counted itself into this month's income, drew a bar on a day that has not arrived, and sat at the top of "recent" as though it already had. Everything else on the page stops at today (the balances do, the average over days elapsed does), so the window is cut at `min(endExclusive, today + 1)` — **in all three of the totals, the curve and the list, or none**. They are one month said three ways, and cutting one of them leaves the page arguing with itself about a payment the reader can see in the other two.

**The lock is the phone's own.** `ThemeChoice` and `screenLock` sit beside the currency and the calendar in `SettingsStore`, and the lock gate is in `MainActivity`, in front of everything: locked on launch, and locked again on `ON_STOP` so switching apps and coming back asks again while rotating the phone does not. **The prompt is asked for on `ON_RESUME`, never as the screen appears**: the screen appears at the moment the app *stops*, which is the one moment the phone cannot show a prompt — the attempt threw, took the "a prompt is up" flag down with it, and the Unlock button did nothing for the rest of the process's life. `askToUnlock` guards the call and reports failure through the same `onDone` every other outcome uses, and nothing clears the flag on the way out, because answering with the phone's PIN goes through `ON_STOP` and `ON_RESUME` while the prompt is still waiting. Deliberately no passcode of its own — one more thing to forget, guarding the only copy of the user's financial history — so it asks for the fingerprint or PIN they already have (`BIOMETRIC_WEAK or DEVICE_CREDENTIAL`). **Turning it on asks first and saves second**: somebody who cannot get past the prompt must not be able to put it in front of their own money, and on a phone with no lock at all the switch refuses and says why. **What it draws is a fingerprint and not the word "Unlock"**: the tap puts the phone's own prompt back up, which the sensor's mark says in one glyph in every language the app is read in, and a text button alone in the middle of an empty page read as a caption. The word survives as the icon's content description.

### The first launch

**Three questions before anything can be used** — language, calendar, currency — on `SetupScreen`, behind the lock and in front of everything else. They are asked on the way in because every figure and every date behind them is written in their answers: a page of rupees read in Nepali is a different app from a page of dollars read in English, and the currency in particular is the one setting that is nearly free to answer now and restates every stored conversion once anything has been recorded. They are the same three cards Settings holds and are drawn by the same code (`ui/components/SettingControls.kt` — `SettingsGroup`, `Explain`, `ExplainedRow`, `ChoiceRow`, `ChoicePicker`), because a currency chosen here and the same currency changed a week later must not look like two different decisions.

**And it is a layer over the app, not a page instead of it.** `MainActivity` draws `WalletApp` underneath and the questions as one panel on a dimmed page — the month, the cards, the tabs all visible behind it — because what the panel is saying is "here is how this will read", and a full screen with no app behind it says instead "answer this before you may see anything". The panel is the screen less the system bars and a hairline of margin — about nineteen twentieths of the phone, and what is left is deliberately not nothing: the app showing along every edge is what says this is a layer over something. The questions scroll inside it and **Continue is pinned to its foot**, or the one thing that ends it sits below the fold on a short phone. The scrim **swallows** every touch that misses the panel rather than dismissing on it: there is no way past three questions the whole app is drawn from, and a page that reacted through the dim would read as still in use. `SettingsGroup(boxed = false)` is what stops the three drawing cards inside the card that is already holding them.

**Continue lands on Accounts, not on Home**, and says the one thing that page cannot say for itself. Money has to have somewhere to sit before anything else in the app means anything, and an empty accounts list says nothing about where a first one comes from — so the shell points at the floating button with a `CoachMark`: the page dimmed, the button lit, "Add Your First Account" and one *Got it*. It is drawn by `WalletApp` rather than by the accounts screen because the button belongs to the shell, and pointing at a thing means knowing where it is: the button reports its own `boundsInWindow`, and the card is withheld until it has (`showAccountHint && onAccounts && addButtonAt != null`), or it would point at nothing on a page it is not talking about. The lock's few seconds do not start until this has been read — two things asking at once is neither of them being read.

Each answer is **written as it is tapped**, not gathered up behind a Save: the language takes effect immediately, and a Save that could fail would open the app in a state nobody chose. `setup_done` is written last, by Continue, so a phone killed part way through asks again.

**The lock is offered afterwards, from the bottom, a few seconds after the user comes to rest** (`LockOfferSheet`, `LOCK_OFFER_AFTER_MS`) — never as a dialog on the way in. It is the setting nobody goes looking for and the only one guarding the database, but somebody who has not seen the app yet has no reason to want it guarded, so the suggestion waits until the page underneath has their own figures on it and then comes up where the thumb already is. It stands in about a third of the screen (`SHEET_HEIGHT`) with the two answers at its foot: drawn to its content it was a strip along the bottom, which reads as a notice already dismissed rather than something being offered. **Any tap dismisses it**, on the page behind it or on the sheet itself, which is what makes it a suggestion rather than a question; the only tap that does anything else is *Turn on lock*, and the other button says *Skip*. Nothing is written by dismissing — the switch is still in Settings. **And only into a gap.** `WalletApp` reports `onIdleOnTab` — the user simply on Home, Reminders, Timeline or Accounts, with no add-menu open and no hint still up — and the wait only runs while that is true, so walking into a form cancels it and coming back out starts a fresh one: the suggestion arrives in a quiet moment or it does not arrive. **Seven seconds, counted from the last thing the user did rather than from arriving on a tab.** Three was the figure for a while and three is not a gap — it is the pause between finishing one thing and starting the next, so the sheet landed while the reader was still looking at the page they had just reached. And standing on a tab is not by itself a lull: a movement recorded *without* leaving the page — a row swiped away, a payment made on a debt's own card — left the wait running, and the offer could arrive on the back of the save. `AppViewModel.dataRevision` ticks whenever the user's own figures move and the wait is keyed on it too, so every recorded figure starts the count again. Settings is excluded for the opposite reason to the rest: the lock has its own switch there, and a sheet offering what the row two inches down offers is the app arguing with itself. Where the user is, is the shell's to know and the activity's to act on, which is why it is reported rather than decided in either place alone. Offered only where `canLock` is true, since a question whose only honest answer is "your phone cannot" is not a suggestion. Turning it on asks the phone before it saves, exactly as the switch in Settings does, and `MainActivity` marks the session unlocked when it succeeds — otherwise the lock just turned on would ask for the same fingerprint a frame later.

**All three are for a phone that has never been used, and "never been used" is asked of the database rather than of a flag.** `AppViewModel` reads `WalletRepository.hasHistory()` before anything else on the launch writes, and a phone with anything on it is not shown the questions, the hint or the lock suggestion however `setup_done` stands. That is what an upgrade needs: a user with two years of figures did not answer questions a later version invented, and being told where the add button is is the app talking over them.

**Nothing is seeded at all.** A Cash account used to be created on the first run so there was somewhere to record the first coffee, and it was the one holding the user had not asked for: it stood on the accounts page of a brand-new app claiming to be theirs, and it came back after Start over on a phone that had just been emptied on purpose. Its absence is why `hasHistory` counts from **one** holding rather than two — the first account on the phone is now one the user made, and an app that has one has been used. The practice entry the opening writes therefore has to survive having nowhere to go: an entry naming no holding is a shape the app already has, and it is what the timeline lesson is taught on when the demo holding has just been swiped away.

**Start over puts a phone back to never having been opened.** `DataEraser` clears the preferences as well as the tables now — they were all chosen *for* those figures — so the app comes back on the welcome questions, offers the hint and the lock again, and is no longer locked. The language is the one answer not in that store (AppCompat keeps its own copy and hands it to the platform), so `SettingsViewModel` puts it back to the phone's own after the erase.

**The Timeline owes two more, and they are spent when the user first walks onto it** — not during setup, because a gesture explained on a page nobody is looking at is a sentence about nothing. The first is the same `CoachMark` the add button gets, lighting the month stepper and saying the page steps when it is dragged sideways; the stepper reports its own `boundsInWindow` for it, exactly as the button does, since the card is drawn by the shell over the tabs and the page cannot reach there.

**And the arrows move** (`EdgeFlow`). Drawn still they were a pair of glyphs — the reader had to be told in words that they meant a drag, which is the sentence the card was already spending, and a page that says "swipe" with two motionless marks on it is asking to be taken as decoration. So the mark moves the way the thing it describes moves: three chevrons at each side, lit one after another from the inside out, which is a pulse running off the edge of the page. The eye reads travel from that without being told, and the direction it travels in is the direction the page goes. Both edges run it, because the gesture genuinely goes both ways and an animation flowing one way would teach half of it. Drawn by hand for the reason the chip on the card face is: what has to be animated is not a glyph but the *relationship between* three of them, which no single icon expresses however it is transformed.

It is the one of the three with **nothing lit under it**: what it is about is the width of the page rather than any control on it, so it points at **an arrow drawn at each side of the screen** and the card sits centred between them — an arrow, the words, an arrow. Lighting the dates was the first try and said the wrong thing twice over: it named the figure that changes while saying nothing about the drag that changes it, and the stepper is so nearly the full width that both arrows landed *inside* the spotlight, where a mark reads as part of the control.

**The second is a lesson the user has to *do*, and that is what stops it being a `CoachMark`.** That card's hole is a hole only to the eye: a `Popup` is a window of its own and takes every touch, so the row could be lit and pointed at and not swiped. `PracticeSpotlight` therefore draws its dim in the app's own composition — outside the `Scaffold`, so the tabs are dimmed as the other two cards dim them — and **puts no node over the hole at all**: the touch-eaters are the four rectangles *around* it, because what is not covered is what stays live. It is otherwise the same card, with the same pointer and the same filled button, the button reading *Skip* where the others read *Got it*. A tap outside is deliberately **not** taken as "understood" — a finger reaching for the row and catching the page beside it would have thrown the lesson away mid-gesture — so the two ways out are the swipe and the button.

**Whatever a spotlight lights clips to the shape of the hole** (`SPOTLIGHT_CORNER`, shared by the hole and by everything shown through it). The hole is cut round; a timeline row is a square rectangle of colour, so its four corners sat outside it and were dimmed with the rest of the page — which on a light row over a dark one is a grey halo hugging the card, and is what was left after the row was inset far enough to stop the corners being sliced by the screen edges. An accounts row never showed either fault: the card it sits in has already inset and rounded it. Both are only visible in the dark scheme, where the difference between a dimmed white and the page is a colour rather than nothing.

**What it is taught on is a real entry**, written by `addPracticeEntry` and filed like any other — a row drawn to look like one would have to be special-cased by every list it appeared in, and could not be deleted by the very code the lesson is about. It takes the id `saveEntry` **returns**, never one made up by the caller: a new row is given its own id there, so a caller's id names a row that was never written, and the lesson — which ends when its row goes — was over before it started. The end is the row's *absence* (`observeEntryExists`) rather than any screen reporting a delete, since it can also go from an account's statement or from the form. Skipped or finished, `endPractice` takes it back, so nothing the app invented is left in the user's own figures.

**The accounts page teaches the same swipe first**, lit and pointed at with the *same* title and button the timeline uses and opening on the same clause — a swipe takes a row away wherever the row is, and saying that twice in two ways would make it read as two gestures. The words then part: the accounts card adds the one gesture that page has and the timeline has not (`hint_swipe_delete_holding`, "…or long-press it to add an adjusted balance"), because a long press on a *holding* corrects its balance and a long press on an entry does nothing. It is a real holding for the reason the practice entry is a real entry, and it goes whether it is swiped away or skipped.

**Neither row is written by the card before it.** Both used to be, by that card's own *Got it* — so the second lesson was on screen in the frame the first left it, and the tap that dismissed the card was as often a tap aimed at the button *behind* it: somebody reaching to add their first account got a demonstration of deleting one instead. The row is **owed** and written into a gap, `LESSON_AFTER_MS` after the user comes to rest on the page it belongs to (`onIdleOn`, which reports *which* tab and not merely whether — writing a demo holding while the user is on another tab opens something they never asked for on a page they cannot see). Walking into the add menu or into a form cancels the wait; coming back out starts a fresh one. And somebody who spent that gap adding an account of their own comes back to a page that has one, where `addDemoAccount` declines outright — it asks the database (`hasAnyHolding`, `hasAnyEntry`) rather than trusting the flag.

**Neither delete is reported.** "Deleted" is the app confirming something the user meant to do to their own figures; these two rows are the app's own, written to be swiped and taken back either way, so the snackbar is withheld on both — on the timeline by deleting without the `onDone` that raises it, on the accounts list by not calling `onDeleted`. On the timeline it would also have carried an Undo for a row that is about to be removed regardless. `addDemoAccount` also sweeps its own leftovers before writing another, since a phone killed part way through the opening keeps the one it had: narrow on purpose — the same name, the same kind, and nothing has ever touched it, because a holding with a movement against it is somebody's own whatever it is called.

**The tutorial draws in the light scheme whatever the app is set to** (`TutorialLight`). A spotlight works by *not* dimming one thing, and in the dark scheme that is a dark row left dark on a page gone 62% black — nothing to see, on the theme half the phones are in. So the cards and the rows they are taught on are white paper laid on a dimmed page. Two things it must provide, not one: the colour scheme, and `LocalContentColor` — text that says nothing about its own colour reads the second, which a scheme does not set (only a `Surface` does), so every title on a light card kept the dark app's white ink and vanished into the paper while everything that stated a colour looked fine. It is deliberately **only** the tutorial: the welcome questions and the lock offer are the user's own screens on a phone set the way they like it, and forcing those would be the app overruling a preference rather than lighting something up for a moment.

**A swipe on the demo holding does not ask.** Every other one does — an account takes every movement that ever touched it and there is nothing to bring back — but this one the app opened a moment ago, it holds nothing, and it exists to be swiped away; a dialog there is the lesson interrupting the gesture it has just asked for. The test is the row being the lit one, so nothing about the question every other holding asks has changed.

**And a swipe dismisses a card — except on the card that is *about* swiping, where it does what it says** (`CoachMark(onStepPeriod =)`). The popup has the touch, so nothing reaches the page unless the card hands it over, and for the two lessons about deleting a row it does not: a swipe there simply means what a tap means, the card getting out of the way. The month card used to be the same, and the whole worry behind that — "the reader would be left on a month they never chose, reading about how they got there" — answers itself, because the card goes in the same gesture and there is nothing left to read. What it cost was the one thing a lesson must never do: a reader who did exactly as they were told saw the card vanish and the month sit precisely where it was, with nothing on screen saying whether they had done it right or done anything at all. The step is let through now, and it is `swipeBetweenPeriods` itself rather than a second reading of the same gesture, so the lesson is taught with the very modifier the page uses and the two cannot drift. `MonthSelection` is what it steps, that being the one month both tabs read, so the month the reader lands on is the month they moved to. The lesson that follows still calls `show(0)` before writing its practice row — a row dated today has to be on the month the reader is looking at — so the sequence is: swipe, watch the month change, and be brought back to today a second or two later with the next card.

**The month is put back before the practice row is written.** The row is dated today, and the lesson *before* it is about dragging the page sideways to change the month — so a reader who does as they were told is looking at some other month by the time this one is owed, the row was written where they could not see it, and the spotlight lit an empty page. `AppViewModel` therefore takes `MonthSelection` and calls `show(0)` immediately before `addPracticeEntry`. Safe on the ordinary path, where the offset is already zero and setting it emits nothing.

**And what is lit is the row *and the date above it*.** A swipe takes away a payment, and a payment on this page is a row under a day heading; lighting the row alone left its own date dimmed a few pixels above it, which reads as the spotlight having missed rather than as a deliberately small target. The two are separate items of a lazy list and nothing can measure both, so each reports its own bounds and the shell unions them — **only while they are still touching**, because that heading is sticky: once the list is scrolled it pins to the top of the page and stops being above its own rows, and a hole stretched between them would cut half the screen out of the dim. The heading rounds its top two corners to `SPOTLIGHT_CORNER` and the row its bottom two, so the block is one rounded rect the shape of the hole rather than two with notches of dimmed page between them.

**A lesson is withheld the moment the page it teaches on is the user's own.** What the opening owes is decided when the questions are answered, and the user may be several minutes and several holdings past that by the time they walk onto the tab it owes something to: after Start over they land on Accounts, add a bank and a loan, open the Timeline — and the app would demonstrate deleting a row on a page already full of their own figures. So the two writers ask first (`hasAnyHolding`, `hasAnyEntry`) and decline; the id staying null is what withholds the card, both `show…SwipeHint` flags being conditioned on it. The sideways-drag card is **not** withheld with them — it is about the page rather than about a row, and it reads the same whether the month is full or empty. The lock offer asks again at the moment it would appear, since the user may have turned the lock on in Settings in the minutes since it was owed.

**`AppViewModel.REHEARSE_FIRST_RUN` shows the whole opening on every launch** whatever the phone holds and whatever `setup_done` says, for reading the opening as a new user sees it without wiping a database. Shipping value is false, and false does **not** mean the opening is off: a phone with nothing on it gets all of it, and so does one whose figures Start over has just thrown away — `usedBefore` is asked **again** whenever `setup_done` is missing, so the questions, the hints and the lock offer come back in the session the user erased in rather than waiting for the next launch. Safe on every such emission, because the other way to have no `setup_done` is an upgrade from a version that never wrote one, and there the answer is the same "yes, this phone has been used" it already was. The flag only decides whether somebody who has already answered is asked again.

This replaced a five-stop coach-mark tour over the tabs, and the pages it explained say the same things in their own words underneath, where they stay.

### Dates and calendars

Storage is always Gregorian epoch-day. `CalendarSystem` only changes what is drawn and where a month begins, and the conversion lives at the edge in `DateDisplay`/`DateWindow`, so no query, sum or sort knows a second calendar exists. Date ranges are half-open `[start, endExclusive)`.

Bikram Sambat conversion is delegated to `io.github.shivathapaa:nepali-date-picker`. **Never reintroduce a local BS table** — an earlier hand-built one disagreed with the picker on thousands of days and was deleted. One source of truth only. That library's table is what bounds the calendar: `BikramSambat` probes it rather than hardcoding a range (1970–2099 BS today), and a date outside it is drawn in Gregorian rather than refused. **The month stepper itself has no ceiling** — a policy or a goal can end twenty years out, and a stepper that stopped two years ahead could not be walked to the month it ends in.

### Transfers

Moving money between the user's own accounts is **two** entries sharing a `transfer_id` — one row cannot move two balances, and across currencies the two amounts genuinely differ ($100 leaves Wise, रू 13,600 arrives). `TransferRecorder` writes and rewrites the pair; deleting or confirming either half does both. A repeating transfer is an ordinary series carrying `transfer_to_account_id`, and each occurrence converts at the rate on the day it falls due, not the day the rule was written.

**A transfer looks the same before it happens as after.** A real one reads both its figures off its partner row and draws the whole movement on one line — "$ 900 → रू 1,38,587". A projection has no partner row to read, so `projectForward` puts the same pair on the paying half (`transferPartnerAmount`/`transferPartnerCurrency`, in the *destination's* currency, not the display one) and `ProjectedEntry.convertedOnTransfer` answers exactly as `MoneyEntry`'s does. Without it one standing instruction was drawn one way in the month it was carried out and stacked two different figures in every month after, so the same payment appeared to change shape by stepping a month forward.

### Repeating entries

A `recurring_series` row is the *rule*, not its occurrences. Dates that have arrived are materialised as real entries; dates still in the future are computed on demand and never stored, so editing the rule corrects every projection immediately.

**A date that has arrived counts.** There is no confirm step and there must not be one again: a standing instruction the bank carries out on the 10th does not wait for the user's approval, and a loan entered with two years of history behind it showed the wrong balance until Confirm had been tapped twenty-four times. The `status` column survives, but `EXPECTED` no longer means "does not count" — it means the row is still the *rule's own words*, so changing the rule may rewrite or discard it. Saving an edit flips it to `CONFIRMED`, which is the user taking the row over; the rule must then leave it alone. Nothing else may read the flag.

`materialised_through` is the boundary between the two halves, and three things depend on getting it right — each of which was a bug:

- Projections start *after* it, not merely after today. Otherwise an occurrence that already exists as a real row is drawn again as one still to come.
- Changing a rule discards the affected `EXPECTED` rows and must roll the watermark back with them, or the replacements are never generated and the payment silently disappears from the timeline and from the balance.
- Those discarded rows are the one place in the app that hard-deletes rather than tombstones: they are about to be regenerated, and a tombstone would block that. A tombstone means "the *user* deleted this", and `occurrenceCount` counts them so it never comes back.

**A month means a month of the calendar the rule was written in**, and the rule carries which one — `recurring_series.recur_in_bs`, set from the calendar setting when the rule is saved and never re-read from it afterwards. Somebody who sets up a subscription on 1 Baisakh means the 1st of Baisakh, Jestha, Asar: that is the day they think in, the day their statement shows, and the day they will look for it. Stepping such a rule in Gregorian months puts its second occurrence on 31 Baisakh — back inside the Nepali month it started in — so one bill written on 14 April 2025 drew twice in Baisakh 2082 and read as a duplicate. `Recurrence` takes the flag; weeks never branch, being seven days in either calendar, and the day of the month is clamped to the length of the month it lands in, which BS needs more than Gregorian does with its months running 29–32 days.

**A policy's premiums and a goal's contributions follow the same rule**, and their `PeriodicPlan` takes the flag too — from `account.plan_recur_in_bs`, the account's own copy of its rule's answer, written with it in the same call so the two cannot drift. It has to be a copy: every reader of a plan's dates is a pure function of the account row — the maturity forecast, the card's table, the payment count — and none of them can reach the rule. Getting this wrong is not cosmetic, because the rule *stops* at `lastPaymentOn`, which the plan computes: counted in the other calendar that day lands a fortnight from the rule's own last occurrence, and the final premium is either dropped or paid into a policy that has already matured.

**A bank loan's instalment answers the same way, and its whole schedule answers with it.** It was Gregorian for everybody, and it still is unless the borrower says their bank counts in Nepali months: `loan.recur_in_bs` is that **opt-in** — the checkbox under "How long?" — and what the schedule actually steps in is it and the calendar being read, joined by `CalendarSystem.forInterest` exactly as a savings account's periods are. A bank debits on a fixed day of the English month whatever patro its borrower reads, so the display choice alone must never move a due date. The debt carries the flag rather than only its rule, for the reason `account.plan_recur_in_bs` exists: every reader of a loan's dates is a pure function of the loan row — the schedule table, the broken period, the day the rule ends, the count of payments made — and none of them can reach the series.

`LoanMath` charges interest for the days *between* payments, so its periods have to fall on the very days the rule produces or the timeline and the loan's own table land on different dates for one instalment. `Recurrence.addMonths` is public for exactly that and is the one place either of them steps a month; nothing on the loan side calls `plusMonths` any more. `Accrual.inBikramSambat` carries it into the arithmetic, `accrualFor` steps back a whole period through it, and `BrokenPeriod` measures "less than one whole payment period after the money arrived" in the same months — three Nepali months from 1 Shrawan is 18 October where three English ones are the 17th, so a first recovery on the 17th is a whole period in one calendar and a stub in the other. Asked in the wrong one it either invents an interest charge or misses one, which `LoanMathTest` pins.

**False on every loan already on file**, which the migration's default of 0 is there for: those schedules were written in Gregorian months and the borrower's standing order pays them on those days. The *rule* carries the effective answer rather than the opt-in, because that is what generates the dates — so `LoanRepository.recalendarSchedules` puts every opted-in debt's rule back in step when the setting moves, and `RecurrenceRepository.setRecurInBs` rebuilds its unconfirmed occurrences from the rule's start, which is what any re-calendaring does. Nothing happens to a debt that never opted in, which is what keeps a calendar switch free for almost every user.

**A rule the user writes simply follows the calendar being read.** The money form asked with a switch of its own for a while; it says which calendar instead ("Every occurrence is saved separately and uses the X calendar"), and `usesSelectedCalendar` is true for everything written there. Somebody setting up a subscription on 1 Baisakh means Baisakh, and the one place to change their mind about the whole app is Settings. The *stored* flag stays what it always was — see below — so a rule written today goes on meaning the months it was written in.

**The money form asks the calendar question too, and its answer is off unless given.** `DefaultCalendarSwitch` — the same control every bank holding is asked with — sits under the interval chips, carrying the sentence that was already there ("Every occurrence is saved separately and uses the X calendar") as its own subtext rather than a second one of its own. It was hard-wired to *yes* on the reasoning that a rule the user writes is their own rhythm and should follow the patro they read; what that cost is a schedule whose shape depends on a display setting nobody associated with it, with nothing on the form saying so. Withheld where there is nothing to ask — English being read, or a rule already running, the two conditions a holding's opt-in is gated on — and the sentence is then drawn alone, because it is a fact about the rule whether or not there is a choice about it. The name in it follows the *switch* rather than the setting, so an unticked rule reads "English calendar" on a page showing Nepali dates, which is exactly what it will do.

**Which is why the flag is stored rather than read from the setting.** This used to add months in BS whenever the user happened to be reading BS, so turning the calendar setting on or off silently moved every future payment of every rule — the reason it was ripped out and made Gregorian-only. Storing it answers that: the setting decides what a *new* rule is written in, and after that the rule remembers. Reopening a rule to change its amount keeps its own answer, so editing under the other calendar cannot re-anchor a schedule. **Changing a rule's calendar therefore rebuilds every unconfirmed occurrence from the rule's start**, where every other edit rebuilds from today: an amount that changes leaves rows that were right when they were written, but a calendar that changes leaves rows on days the rule never meant, and they are still `EXPECTED` — the rule's own words rather than anything the user has taken over.

There is no screen listing the rules. A rule is reached through the entry that created it — its earliest surviving occurrence, which `anchorEntryForSeries` finds — and deleting that entry stops the rule. **The two ways to delete mean two different things, and that is deliberate.** A *swipe* on the timeline or on Reminders acts on the row it is under: one date, and the rule carries on. Opening the entry and using the bin acts on what the form is showing — and the form is showing the **rule**, not an occurrence: every date opens its anchor (`ruleAnchorFor`), the repeat controls are the rule's own, and saving there rewrites every occurrence still to come. Removing one date from a screen that edits all of them was the odd answer. So the bin takes every occurrence, the ones already recorded included, and the rule with them — one at a time and through `deleteEntry`, so each puts back whatever it moved (a balance, a debt's principal, a goal's length), **oldest first**, because that door refuses a lump sum while a later one is still on file and walking forwards never meets that. The rule goes **last**, or `materialiseDue` writes replacements for the rows being removed. On an entry with no rule behind it both routes remove the one row, as they always did. It asks first now, having asked nothing before: it removes a great deal more than the row that was tapped, and none of it comes back from a snackbar. Rules with no entry left behind them can be stopped from the projected row itself.

**And a date still to come is swiped away like one that has arrived.** A materialised occurrence is a row and is removed by removing it; a projection is not a row at all — it is computed from the rule every time the page is drawn — so the swipe had nowhere to land, and the only month a payment could be dropped from was the one it had already been written into. `RecurrenceRepository.skipOccurrence` writes the occurrence **already tombstoned**: `occurrenceCount` counts deleted rows precisely so a date the user threw away is never generated again, and `projectForward` now asks the same question of the whole window (`occurrenceDays`, once per rule rather than once per date) before drawing one. The marker is `CONFIRMED` rather than `EXPECTED` — that is what it is, the user taking this occurrence over from the rule, and a rule edit discards its own `EXPECTED` rows, which would quietly bring the skipped date back. Undoing it is the one **hard** delete in the app besides the discarded rows: the marker is what blocks the date, so a tombstoned marker would go on blocking it.

**Only a rule the user wrote may be skipped a month of** (`ProjectedEntry.canSkip`). A loan's instalments are what its balance is counted from, and a policy's premiums and a goal's contributions are counted by the arrangement they belong to — each would go on showing a payment the timeline had dropped. `isPlanPayment` is carried for that, off the destination's kind, the way `loanName` is carried for the loan. The bank's own schedule — a quarter's interest, a deposit coming free — has no rule behind it at all. It is the same distinction `materialiseDue` draws between a schedule the app replays and one the user wrote. `LedgerRow.canDelete` on a debt's statement draws a different line and should not be read as this one: there, every payment goes and only the debt arriving stays.

**And every occurrence opens that same anchor**, whichever one is tapped and whether the date has arrived or not — `AddEntryViewModel.ruleAnchorFor` redirects before the form loads, so the row the user taps and the row the form saves are the same one. A rule is one thing and its occurrences are what it produces; the form used to draw the *tapped occurrence's* date beside the *rule's* repeat settings and write both on save, so opening June's row to correct an amount silently moved the whole rule's start to June and marched the schedule forward a month every time it was looked at. There was also no way to reach the rule from any row but the first, and nothing on screen said which row that was. A **loan's** instalment is the exception and opens as itself with the repeat controls withheld: that schedule belongs to the debt and is changed on the debt's own screen.

### Loans

A loan runs in one of two directions (`LoanDirection`): money borrowed, or money lent out. A lend is an asset — its repayments arrive rather than leave, it sits in its own section, and it is added to net worth rather than subtracted. The direction cannot be changed after the fact, because it would reverse the meaning of every payment already recorded.

A borrowed loan is not an account — you do not spend from it, and its balance follows an amortisation schedule rather than a running total. The instalment is an ordinary `recurring_series` pointed at whichever account the bank debits. All of `LoanMath` works in minor units on a reducing balance.

The unit of that schedule is a **payment period**, not a month. `payment_every_months` (1, 3, 6 or 12) sets both the periodic rate and the number of instalments, and the same value picks the series' `RecurrenceInterval`, so the arithmetic and the projected dates cannot disagree. Interest accrues over the gap, so the same loan paid quarterly genuinely costs more than one paid monthly — anything that shows a total must go through `LoanMath`, never through a monthly figure multiplied up. Terms are always stated to the user in months; only `LoanMath` counts payments.

**The debt arriving is a row whatever the user answered.** It is the largest thing that ever happens to a holding — it goes from not existing to owing what it owes — and the row used to be written only where an account was named for the money to land in, which is the field people leave blank on purpose. So the month a loan was taken out listed everything it has cost since and nothing about the loan: September had eighteen days of interest in it and no sign of the रू 27,00,000 those days were charged on. It is written for all of them now, naming an account or not — an entry naming no holding moves no balance, so nothing about the rule below changes — and `LoanRepository.writeMissingDisbursements` carries it to the debts already on file, since nothing else would until each was opened and saved again. **Only where there is no row at all, tombstone included** (`findAnyById`, the one read besides the backup merge that sees deleted rows): deleting it is the user saying they do not want it on the page, and a launch that put it back would be the app arguing with them once a day. The backfill states **what changed hands, not what is owed** — `advanced_minor` less anything added since, because `principal_minor` stops meaning "the sum borrowed" the moment a lump sum re-bases the debt, and a debt from before that column with anything behind it is left alone rather than given the shrunken figure.

Nothing is recorded arriving in an account when a loan is created **unless the user names one**. A loan is often disbursed straight to a seller, or was taken years before the app was installed, so nothing is ever inferred: the app records the debt and leaves the balance to the user to correct. What it offers is `disbursed_account_id` — optional, defaulting to a "Not recorded" chip, and written into whatever account they pick on `disbursed_on`, the day the money was received. Asked on the way in only, on any debt with a day the money moved: money between people (see below) and a bank loan with a schedule. Never on an overdraft, where money arrives by being drawn and that writes its own dated movement.

Most money between people has no terms at all — "I lent Sita 8,000" is a note of
who owes what, not a loan with a rate. Rate and length are therefore hidden when
reopening a loan that has none of them (`showsTerms`), because empty boxes imply
the user forgot to fill them in. What is offered instead is one line —
**"Add interest to this amount"** (`offersInterest`), which reveals exactly those
two. It is deliberately not the old "add a repayment plan": a schedule is
paperwork for the one kind of debt that exists to avoid it, but interest agreed
weeks after the money moved is how these debts actually work, and without the
line the only way to record it was entering the debt again and losing every
payment made against it.

**A savings or current account already on file is asked the same way** — the
rate, the payout interval, the explanation and the rate history are all withheld
when there is no rate, and `showsRate` is the account's `showsTerms`. Plenty of
savings accounts are opened in this app as somewhere for money to sit, and
reopening one showed an empty "Interest rate" beside an "Interest paid every"
reading 3 months and two lines explaining an arithmetic the account does none of:
four things to read past, all about a bank arrangement the user never said they
had. A deposit is excluded — what it earns is the whole of what it is, so a rate
it has no answer for is a fact missing rather than one not applicable. The offer
is one string for both (`loan_add_interest`, "Add interest to this account"),
because it is one act.

The terms block is **latched on load** (`termsRevealed`), not re-derived from what is currently typed: `hasTerms` reads the boxes, which are empty for the moment between clearing a rate and typing the next one — and in that moment the whole section vanished and offered to add the interest that was already there.

**Zero is how interest is taken back, and the date decides how much of it.** An emptied box and a typed `0` are the same answer — there is no rate any more — and `applyRateChange` accepts it where it used to refuse anything `<= 0`, which left a rate impossible to remove once given. The field then says **"Interest stops from"** (`cancelsInterest`), because "rate changed from" over a blank box asks the user to work out what a blank rate means. Two outcomes, and the date is the whole of the difference:

- **A later date stops it there.** `RateSchedule` charges every day at the rate in force on it, so the days before are still charged at the old figure. That is the honest answer for interest the two of them agreed to drop.
- **Its own start date undoes it.** `recordChange` keeps one row per effective day, so a zero dated on the day the rate started *overwrites* that row rather than following it — no day was ever charged. Said in those words (`cancelsAllInterest`), and only when it is true: a holding that opened at a rate had days at the opening figure before its first change, and a later change still on file resumes charging on its own date.

**A rate given to a debt that never had one is not a rate that changed.** The
date beside it says "Interest rate applied from" rather than "Rate changed from"
(`hadRate`), and it defaults to the day the debt itself began, because that is
what two people mean when they agree interest on money already lent — today would
charge nothing for the months it has already been out. That day is `movedOn`,
which is also the floor the picker refuses below, so the default sits *on* the
earliest answer rather than a day past it; a rate that genuinely moved still
defaults to today, and `hadRate` alone tells the two apart. Nothing writes the figure
onto `annual_rate`: the rate it *opened* at is still none, and everything it
charges lives in the dated change. Two things have to follow from that or the
rate does nothing at all — `metersInterest` asks `RateSchedule.everCharged`
rather than the holding's own figure, and `LoanMath.accruedInterest` takes the
schedule so each run of days is charged at the rate in force on it. The lists
read `rateShown`, the current rate, for the same reason.

A loan carries two optional dates and they are mutually exclusive by design: `emi_starts_on` for one with instalments and `due_on` for one without.

**The first instalment defaults to one interval after the money arrived**, which is what a bank does, and it *follows* both of the things that decide it rather than being filled in once: the interval, and `disbursed_on`. It used to count from today, so a loan taken last September was offered "one month from today" and somebody entering a year-old debt had to correct a date the form had made no attempt at. `withDefaultEmiStart` is the one place that answers, `emiStartPicked` is what stops it once the user has picked a date of their own, and `setDisbursedOn` re-applies it for the same reason `setPayEvery` does — a money-received date moved with the first EMI left behind describes an arrangement neither of them meant.

A `due_on` becomes a one-occurrence rule for the whole balance, so a lump sum falling due appears in the forecast like anything else. Only a *bank* debt is asked for one now — money between people is asked the day it changed hands instead, and keeps whatever `due_on` it already had; see below.

**The day the money arrived and the day the bank starts taking it back are two different facts**, and `disbursed_on` records the first. Interest runs from it. A bank recovers on a fixed day of the month, so money handed over on the 3rd meets the 20th before a whole period has passed, and what is taken then is not an instalment: it is the interest for those days, charged in days rather than twelfths, with the principal untouched. `BrokenPeriod` is the one place that decides — a first payment **less than one whole payment period** after disbursement, which is the only thing that can tell the two arrangements apart from dates alone. When it applies:

- `LoanMath.brokenPeriodInterest` charges it, **counting both end days**. रू 27,00,000 at 8.25% from 3 September recovered on the 20th is 18 days and रू 10,984.93 — the bank's own figure; 17 days is रू 610 short.
- It is written as an ordinary entry tagged `loan_part = INTEREST`, which already means "the money left and the balance did not move". Filing it as an instalment would have the schedule count a payment that cleared no principal, and the debt would read a month ahead of itself forever. Its id is derived from the loan's, so re-saving the form corrects that row instead of adding another.
- The series starts at the *next* recovery date, and the editor's schedule table counts its dates from there — not from `emi_starts_on`.
- **But it is the first row of that table while the loan is being created**, on the day the user typed as their first EMI date, all interest and the balance where it started. It is a payment on a date and the first one there is; leaving it out showed somebody who had just entered "20 September" a schedule beginning 20 October with a payment they will really make missing from it. It is counted into "interest over the whole loan" wherever it is drawn, or a reader adding up the column finds the total short by it. Only while creating: once the loan exists that charge is a row in the timeline like any other, and the table lists what is left.

`disbursed_on` is null on every loan that predates the column, and nothing is inferred from a null: without that date there is no gap to measure, and inventing one would invent a charge on a loan the user has already reconciled.

**Interest is charged for the days that actually pass**, at `rate ÷ 365` a day — never a twelfth of a year. February is not March, and a lump sum paid ten days after an instalment leaves ten days of interest on the old balance that twelfths silently forgive. Against a real seven-year loan the twelfths were रू 322 out over ten months; by days it is रू 25, which is holiday-shifted debit dates and rounding.

Three things hold this together, and each was wrong in an earlier version:

- **`LoanMath.Accrual` is how a schedule learns its dates** — `from`, the day this balance started running, and `firstPaymentOn`. Passing none keeps the old twelfths, which is right for a loan with no dates to count between. A period runs from the day *after* the previous payment through the payment day, so consecutive periods neither overlap nor skip a day.
- **`accrualFor` decides where the first period starts**, and is the only place that may. Use `started_on` when it falls *inside* the first period — a re-based loan, whose next instalment charges only the days since the lump sum — and the whole period otherwise. A loan entered long after it began has `started_on` sitting on its own first instalment, and taking that literally charges that payment nothing.
- **The meter starts at the day the money moved, not at `started_on`.** A lump sum re-bases the debt and moves `started_on` to the day of the payment — so a meter that opened there quietly forgave every day of interest before it: रू 7,095 on a year-old रू 1,00,000 paid down last month. `disbursed_on` is in the `min` for that reason. A lump sum is all principal by design and settles no interest; the schedule side carries those days forward (`carried_interest_minor`) for exactly the same reason, and the metered side must not simply drop them.

**A lump sum comes off the principal in full, and the days behind it are carried.** A balance is only true on the day it was billed, and a payment lands between instalments far more often than on one — so the days since that instalment were already charged, on the larger balance. Those days go into `Accrual.carriedInterest` (persisted as `loan.carried_interest_minor`) and are collected by the next instalment, exactly as a statement shows them. The two wrong answers either side of this are both worse: charging a whole fresh period on the reduced balance forgives them (रू 322 out), and adding them to the principal compounds them (रू 25 out).

**The editor's own preview has to build the same accrual the loan runs on**, from the loan's stored `started_on` and `carried_interest_minor` — not from the disbursement with nothing carried. It did the second, which is exactly the pair of wrong answers above: it measured the first period from the day the money arrived a year ago rather than from the lump sum, and forgave the days that lump sum left behind. The table quoted रू 19,94,974.50 for the payment the timeline had at रू 19,96,043.61, both drawn on the same screen an inch apart. Anything that previews a schedule reads `storedStartedOn` and `storedCarriedInterest`; only a loan being created has neither, where the disbursement is the only day there is.

**The schedule table is "Remaining payments" once anything has been paid**, and every payment the debt has ever had counts towards the line above it. `Loan.paymentsMade` is the *schedule's* bookkeeping — instalments since `started_on`, which is how many rows to drop — and a lump sum resets it to nothing, so the form read "1 already paid before this" under a debt with a year of instalments behind it, and never counted the broken-period charge at all. `LoanRepository.paymentsMade` answers the question the reader is actually asking, classified through `LoanLedger.kindOf` so it agrees with the statement they can open and count: every instalment, every lump sum, every interest charge serviced on its own. The debt arriving and more borrowed on it are not payments (`LoanMovementKind.isPayment`).

**The quoted instalment is still the monthly formula** (`emi`). Banks quote in twelfths and accrue in days, and so does this; changing the quote would make the app disagree with the borrower's own statement about the one figure they know by heart. For the same reason `tenureAfterPrepayment` walks the schedule when it has dates rather than using its closed form, which assumes every period is the same length.

`InstalmentStyle` says how each instalment is made up — a level EMI, or interest only (the balance waits). The stored `emi_minor` means a different thing in each, which is why `LoanMath.instalment` exists.

`PRINCIPAL_ONLY` — a fixed slice of principal with the period's interest on top, so the payment falls — is no longer offered when creating. Paying a fixed slice off the balance is what *Pay off a lump sum* already does, on any loan, whenever the user actually has the money; a whole schedule shape for it was a third answer to a question with two. The enum value, its arithmetic and its chip all stay for loans already running that way, because rewriting a live schedule is not a renaming. On such a falling schedule the repeating series carries the *first* payment, since a series holds one amount and each occurrence is confirmable anyway. Its *explanation* did not stay: the line under the chips names both shapes at once (`loan_style_explain`) rather than describing whichever is selected. The question there is which of the two to pick, and a description of the one already chosen answers it only by being tapped through — the reader had to select a shape to find out what it was.

### The forms

**Where money is *sent*, a bank is one place.** Every chip that asks which account money moves through — a loan's "Money pay from", a disbursement's "Money received on", a deposit's "Money receive on", the account inside a payment card — offers **one chip per bank**, labelled with the bank's name alone and standing for its **savings account**. `payableHoldings` picks it and `payLabel` names it. Listing every holding under one name made the user choose between three answers to a question with one, and naming the holding ("Nabil Bank · Salary") asked them something they had not thought to ask themselves.

Three rules inside it: a bank with nowhere for money to sit — one you only have a loan with — is not offered at all; a **current account stands in where there is no savings account**, since it cannot be created any more but the ones on file are still spendable and dropping them would strand an older install's payments; and the account **already chosen is always in the list** (`keep`), because a form that quietly forgot the account a loan has been repaid from for two years would be worse than an extra chip. Deposits are in none of these lists, as nothing can be paid into or out of one.

**The note is asked first, and it is asked for.** It stands where the label used to: with labels gone, nothing else on a movement tells one of a bank's payments from another, and a page of rows reading "Money out · Nabil Bank" says nothing the Accounts tab did not. So it leads the form — what this is, then what it cost, which is the order the question is asked in — and an empty one refuses the save, transfers included. It is what `entryTitle` reaches for before anything else, so the note the user types *is* the row.

**The currency is not asked on money in or out.** The account the money leaves or lands in is denominated in one, and that is the whole of the answer — a second question could only be answered a contradictory way, and dollars typed against a rupee account is not a currency the movement has, it is a mistake. The account chips print the code, and the converted figure still sits under the amount.

**The form asks which *account*, and nothing else.** "Paid from", "Landed in", "Out of", "Into" — the places money sits, which is banks, wallets and cash. A debt and a goal are neither, and both were offered here for a while under a second heading, **"or use this account?"**: the debts the app could record a movement against, and the goals. That row is gone.

What it cost was a form doing two unlike jobs at once. Every debt chip was an operation from the debt's own screen wearing an entry's clothes — `drawFromOverdraft`, `increaseLoan`, `applyPrepayment` — reached from a page with no field for what those operations actually need, and each with its own refusals to explain (a debt at both ends of a transfer, a debt beside an account in another currency, a draw over the limit). None of that is money in or money out, and the row also carried the app's only exceptions to the form's own rules: no repeat, and an amount denominated by something that is not an account. **One question, one kind of answer.** Money against a debt is made on the debt's screen and money into a goal on the goal's, where both already had a card for it; nothing about those cards or the balances they write has changed.

The rules that decided which debts appeared went with the row (`rebuildSources`, `growsOn`, `canGrow`, `canShrink`, `HoldingSource`, `SourceKind`, and the `TWO_DEBTS`/`DEBT_CURRENCY` errors, which only that row could provoke). A transfer is now two accounts at its two ends, full stop, and `transferEnds` counts places money can sit. **`OVER_LIMIT` stayed**, being the one of the three the card still provokes from the form the card is still on: a purchase over the ceiling and a cash advance over it are both refused there — see *Overdrafts and credit cards*.

**A goal already named by an entry stays in the row.** It is the one exception, and it is not an offer: `accountChips` keeps a goal while it is `selectedAccountId` or `toAccountId`, because a form that cannot show what it is set to is worse than one that shows a chip it would not offer again. Movements filed against goals before this — including every Deposit and Withdraw the goal's own card wrote — reopen showing which holding they were.


**The account row is drawn whenever there is an account to draw in it** (`showsAccountRow`). It used to be withheld for a *single* one, on the reasoning that one account is not a question but an answer already filled in — and what that produced was a money form with no "Paid from" on it at all. Somebody with one bank account and a term loan sees exactly that: the loan's instalments belong to its own screen, so it is offered in neither row, and the form that was about to move their money named no holding anywhere while the Accounts page listed every bank they had. A form has to say what it will debit even when there is nothing to decide; one chip, already selected, is that sentence and costs a line.

**Both rows show a few.** The accounts at either end draw their first several and keep the rest behind one word (`ShortlistChips`, `Shortlist.HOLDINGS`). Eight holdings, for the reason the currency row shows four: all of them wrapped into four or five lines of near-identical pills, so picking the account somebody was always going to pick meant reading past every other one they own. The word is not a chip, expanding appends rather than reorders, and there is no way back — all exactly as the currency row does it.

**The order is what the user actually uses**, most first, counted from the movements themselves (`AccountDao.byUse`, returning `HoldingUseRow`) and not kept as a tally of taps: a tally records what was once looked at, so an account picked by mistake and never used again would lead the row for ever, which is the same argument that makes `currenciesInUse` read the holdings. Uses lead and recency only breaks ties — a salary account touched once a month must not fall behind a cash tin touched yesterday — which is the query's own `ORDER BY uses DESC, lastOn DESC` and is the one rule here no unit test can reach, there being no `room-testing` dependency. There was a `Shortlist.rank` that interleaved two tables for the second row of chips; it went with that row, and the accounts arrive ranked from SQL. Worked out **once, when the form loads**, and never again as the user taps: a row that reordered itself under the thumb would move the chip beside the one being aimed at. What the form *opened* on leads its row and is pinned there for the session (`Shortlist.order`), or reopening an entry filed against something rarely touched would put its own answer past the end of the shortlist and the form could not show what it was already set to.

**What is being added is asked before the form opens.** The Accounts button opens six options — Bank, Wallet, Cash, A person, Insurance, Goal, each with a line saying which is which — and the form arrives knowing the answer (`Routes.ARG_GROUP`).

They **grow out of the button** rather than arriving as a modal sheet (`AddHoldingMenu`): nearest option first so the eye follows them up from the thumb, the plus turning a quarter turn into the cross that closes them again. A sheet was a page of its own for six words, and it covered the button that had just been tapped.

**And they take no height in the button's slot.** The `Scaffold` stacks the snackbar directly above that slot, so with the options measured the whole strip grew by six cards the moment the plus was tapped and a "Deleted" that had just appeared at the foot of the page shot up to the middle of it. They are drawn inside a box fixed at zero height and allowed to overflow upwards, so the slot is the button's own size whether the menu is open or not.

The six share **one width, taken from the longest of them plus a little air** — the column is its widest child (`IntrinsicSize.Max`, capped on the column itself so a long line wraps rather than running off the phone) and every option fills it, with more padding at the end of a row than at the start, since air asked for there is air every option gets — lined up on the button's edge and see-through. Stretched to the width of the page they read as a sheet with gaps cut into it, and each at its own width they read as six unrelated things; one block hanging off the button is neither. The floor on the translucency is legibility: the page underneath is being dimmed for a moment rather than replaced, and the scrim is the only thing keeping the words apart from whatever is behind them. Two details make it work where it is: it is drawn **in the floating button's own slot**, so neither it nor the button has to know where the other one is, and its entrance is driven by an `Animatable` starting at zero rather than `animateFloatAsState`, which takes its first value as its target and would draw each option already in place. The dimming is separate (`AddHoldingScrim`, over the page and under the button) because the button is the way out of the menu, and a close button behind a scrim reads as disabled. It used to be the form's first row, which meant the first thing anyone did on "Add account" was decide which screen they wanted; six answers open six different forms, and that is a question, not a field. What is left inside is the *sub*-choice, and only where there is one: a bank holds four things and money with a person runs two ways, so the "What is it?" heading appears for those two and is absent rather than empty for the rest (`showsKindQuestion`). **The form then says which of the six it is** — "Add a bank account", "Add a wallet account" — because on the four kinds with no sub-choice the chip row is absent and nothing else on the page names the answer the sheet just took.

**A transfer is not offered where there is nowhere to move money to.** The form has always greyed its Transfer tab out on a phone with one account and said why underneath; the menu in front of it has no room for that sentence, so it drops the option instead (`AppViewModel.canTransfer`, counted the way the form counts its ends — the places money sits, so a deposit, a policy and a goal are not among them). An option that opens a page in order to explain that it does nothing is worse than an option that is not there.

**Both buttons ask before the form opens.** The Accounts one has always opened six options; the Timeline's opens three — money out, money in, a transfer — for the same reason and through the same menu (`AddEntryMenu` beside `AddHoldingMenu`, sharing the option row and the scrim). They are three different forms wearing one title, and which one it is was the first thing a user had to fix on a page that had already opened on a guess. The form keeps its segmented button: this is where a movement *starts*, not a decision it is held to. `Routes.ARG_TRANSFER` carries the third answer, because a transfer is not a direction — it is both at once.

**The floating button adds whatever the page is a list of** — an entry on the Timeline, an account on Accounts. Accounts therefore has no second plus in its heading: two buttons a thumb-width apart doing different things could not be told apart without tapping one. Settings is a list of nothing and has no button at all, and neither has Home: it is a summary of the month rather than a list of anything, and the entry it would add joins the list on the next tab along.

**A date measured from another cannot be picked before it.** `WalletDatePicker`, `DatePickerBox` and `DateField` all take a `minDate`, and both grids honour it — Material's `SelectableDates` on the Gregorian one, `NepaliSelectableDates` on the other, which is asked in Bikram Sambat and answers by converting each cell rather than comparing a Baisakh to an April. Days below the floor are greyed rather than removed, so the reader can see where it is instead of wondering why the month looks short, and a calendar opened with nothing chosen opens on today unless the floor is still ahead of it. **The years on offer start at the floor's own**, in both grids: greying the days is not enough by itself, since a floor a fortnight old leaves years of months that are entirely dead and a reader paging back through them cannot tell whether they have gone too far or not far enough.

What the floor *is* is `HoldingEditorState.movedOn` — the day the money changed hands (`disbursed_on`), or the day the arrangement began where that was never recorded. Every date on a debt's form is measured from it: the first EMI (a bank cannot recover money it has not handed over — while creating, the disbursement box being filled in is read first, since it is the answer the user is giving), a payment (the balance a payment meets is the balance as it stood on its own day, and a day before the debt began has none), more borrowed or lent, and the day a rate started applying. A goal takes it from its own start day, and it is null on a bank account, which has no one day it began on. Null is a real answer everywhere: a debt entered before the app asked for a disbursement date has no such day, and inventing one would refuse dates that are perfectly true.

**A unit is part of its figure, not a question beside it.** "How long?" reads back as `1 years` inside its own box, and the Months/Years chips appear only while that box has focus — `termShown` and `TermUnitChips` do it for the loan's term, the deposit's, and the interest payout interval in Settings. They live in `ui/components/Common.kt` for that reason: a unit that read back one way on one screen and another way on the next would be two widgets pretending to be one. Permanently drawn, they were two chips under every form restating what a filled-in field already said; and the chip has to put focus *back* in the box when tapped, or the row it sits in closes behind the tap and switching months to years costs three taps instead of one.

**A bank's arrangement is agreed in years, so that is what "How long?" opens on.** Nobody says "sixty months" out loud: a deposit runs for a year or five and a loan for two or seven. Months was the default because it is the unit the app *stores*, which is a fact about the database rather than about the person filling the box in, and it cost a tap on nearly every bank holding. Set from the group being added, so it never touches a holding already on file — there the length on file decides which unit reads it back.

**And on a deposit, "How long?" pairs with the rate.** A deposit has no payout interval — what it earns arrives in one piece when the term runs out — so the slot beside the rate was empty and the length sat alone on the next line, reading as an unrelated question. They are the two facts a deposit *is*, and the same pair the form already states side by side once it exists.

**"Pay every?" is the same field with a third answer**, and `PayEveryChips` follows the same focus rule for it. The third answer — "at the end", one payment when the term runs out — has no figure to type, which is why the chips used to be drawn permanently: making the box vanish took the chips' anchor with it and left no way back to a schedule. The box goes **read-only** instead of away, so it is still there to be tapped, the focus requester is always attached, and every unit in the form appears and disappears by the same rule.

**One title size for a named thing** — `TitleStyle`, in `theme/Type.kt`. Every screen reached through a back arrow uses it for its title ("Edit account", a loan's name in its statement), and so does a bank's name over its holdings. It is deliberately below the headline a tab uses for its own page: a screen you arrived at is subordinate to the one you left. Before it the four such screens had drifted to three different sizes, which read as three different kinds of screen.

**Save sits at the foot of the page on a short form and at the foot of the content on a long one.** A cash tin asks for a name, a balance and a colour, and Save landed wherever those happened to end — a third of the way down, with the rest of the phone empty beneath it, which reads as a form still loading rather than one already answered. The page's own foot is where a thumb goes looking for it. The scrolling column is given a floor of one viewport (`BoxWithConstraints`, `heightIn(min = )`) and lays its two halves out `SpaceBetween`: with room to spare the slack falls between the questions and the button, and with none the column simply grows and Save follows the last question down exactly as it always did. Weight cannot do this — inside a scroll the height is unbounded, so there is no remaining space for a weighted child to take. `imePadding` moves out to the box that measures the viewport, still ahead of the scroll as it must be, so the floor shrinks with the keyboard instead of forcing a page's worth of empty scroll underneath it.

**A form asks in full width and states in pairs.** While creating, a field being typed into gets the whole width. Once the holding exists its name and opening balance are settled text — two short facts being read, not two boxes being filled — so they sit side by side on one line instead of as two captions with a gap between them. `pairsOpeningWithName` draws the difference, and is deliberately separate from `isReadWhereItSits`: the two were one flag, and widening the layout question silently took the display-currency choice away from every foreign bank account.

### The one card face

**What the user holds is drawn on a payment card** (`BankCardFace`, at the top of the Accounts tab). That figure is the one thing on the page nobody has to read a label to want, and it sat on the same white rectangle as everything under it — so the tab opened on a column of identical cards with only the type size saying which of them mattered. A card face is the one shape a reader already knows carries a balance.

**It is drawn, not depicted.** The chip and the contactless arcs are a few strokes on a `Canvas` — nothing to keep in step with the theme, nothing to redraw at four densities, no asset. They are also the only marks on it: a magnetic stripe, a signature panel and a network logo would each be a picture of a card rather than a card, and none of the three would be saying anything about the user's money. **And nothing on it is a real card** — no number, no name, no expiry, and it must not grow one: this is a total across every holding there is, and dressing it as a particular bank's card would be the app inventing an account.

**The face is dark in both schemes** (`WalletColors.cardFace`, three stops rather than one colour — a flat rectangle of primary blue reads as a banner, and it is the sweep from indigo through the app's own blue into its own green that reads as a card). Every other surface follows the phone; this one cannot, because a card face is an object the page is holding rather than a region of the page, and a white one would be a fourth shade of paper stacked on three others. What changes between the schemes is only how hot it is allowed to be — on a near-black page the light scheme's stops glare, so the dark set is pulled down a step.

**Which is why everything on it takes its ink from `OnDarkPanel`** — the mirror of `TutorialLight` and the same argument in reverse. In the light app `onSurface` is near-black and `moneyIn` is a deep forest green, and both vanish into indigo; what reads on a dark face is the ink already designed for one. `LocalContentColor` goes with the scheme for the reason `TutorialLight` sets it. It is for panels the app draws dark on purpose and nothing else: anything that follows the user's own choice must go on following it.

**And the supporting lines carry the mark of the direction they run in** — what is owed, what is owed back, and the two netted off. At `bodyMedium` on a dark face the only thing telling those three apart was a colour, which is the one signal a reader may not have; it is the same argument that already puts a sign in front of every amount in the app. They are the app's own in/out arrows, so an arrow means here what it means two taps away. **Home's headline card takes the same pair** on its "went out" eyebrow and its "came in" line, drawn there rather than through `SectionHeader` because a card's own eyebrow is not a section of the page and would arrive with the heading's gap and rule.

**The quiet ink on the face is its own** (`CardFaceMuted`, white at 0.72) and not the dark scheme's `onSurfaceVariant`, which is what it took at first. That colour is a cool grey chosen to be read against a near-black page; over indigo it loses most of its contrast and over the green corner it goes muddy, so the two lines a reader has to work hardest for — what is held in another currency, and what it all comes to — were the least legible things on the card. White at an alpha holds the same distance from the face at both ends of the sweep, which no opaque colour can do.

**Every section heading on Accounts carries the mark of what it is a section of** — a bank, the wallets, the goals, the policies, money with a person, the cash that is nowhere in particular. The page is a column of near-identical cards under near-identical headings, and the one thing that differed between them was a word set in the same type as every other word on it. The glyphs are the ones the add menu offers those same kinds under, so the mark a holding was picked by is the mark it is later found under. Read from the heading the group already carries rather than from what is inside it: a bank's card holds a savings account, a deposit and a loan at once, so no holding in it can speak for the block. **The Timeline's blocks take the same marks** (`GroupHeader(icon =)`), because they are the same holdings: a bank found by its mark on one tab has to be found by that mark on the other, exactly as it is found by its colour.

**A mark heads a section of a page, never a field.** `SectionHeader` and `GroupHeader` both take one, and where it is passed is the rule: the ten groups in Settings, Home's two, the heading over a list on an inner page — a debt's payments, a holding's transactions, a schedule — and the blocks below the Timeline's log. Not a form's field labels, of which the holding editor alone has twenty: those name one box rather than a part of the page, and a glyph on each would be a column of decoration down a form. Not a sub-heading inside a section that already carries a mark, where a second glyph says the two are unrelated things.

**Settings names its headings by string resource rather than by the finished words** (`SettingsGroup(@StringRes title)`), and looks the mark up from the id. The welcome panel asks three of the same questions with the same component, and the two must not look like two different decisions — passing the words in would have left the icon a second argument for each of the thirteen call sites to remember, and a heading added to one screen could arrive without one. Two of the glyphs are deliberately not the obvious choice: **Backup is not a cloud**, because the app promises no server, its manifest turns Auto Backup off to keep that true, and a cloud on the one screen that writes the user's whole financial history to a file would say the opposite where it matters most; and **Reminders is a clock rather than a bell**, the bell belonging to Notifications two sections above it.

**Reminders gets none of this beyond its empty page, and that is the design rather than an omission.** Its rows are movements, and a movement's row carries no mark — the dot beside every entry went with the labels. The one distinction an icon could draw there is "already recorded" against "still to come", which the page deliberately does not draw: the user is being reminded of the payment, not audited on whether the app has written it down yet.

**And an empty page wears the glyph of the list that is empty** (`EmptyState(icon =)`). Two sentences centred on an otherwise blank page read as an error message however carefully they are worded, because a blank page with words on it is what an error looks like. The mark is the tab's own, or the one the rows it is waiting for would have carried, in a soft disc — a single outlined shape floating over the fold reads as a control that failed to load. Decorative, and carrying no content description: the two lines under it say the whole of it in words.

### The month, drawn

**Home's chart is a running total, not a tick per day** (`MonthCurve`). The strip of one bar per day was the app's signature element and three things were wrong with it on real months: it was drawn in the **primary blue** while every money-out figure in the app is red, which was the one place the palette contradicted itself; four days' spending in a thirty-day month was four hairlines standing on an empty rule, which reads as a chart that failed to load rather than as a quiet month; and it answered a question the page is not asking — Home asks *am I all right this month?*, which is about pace, and pace is exactly what a per-day chart cannot show without the reader adding the bars up by eye.

A running total answers it directly, and the line's **steepness** is the rhythm the ticks used to show — a heavy day is a jump, a quiet week is a flat run — so nothing is lost. **The track runs the whole month and the line stops at today**, which is the other half of what the ticks did: the strip's length was the real length of the month, so a 32-day Nepali month was visibly longer than a 30-day one and the calendar setting stopped being abstract. The gap between where the line ends and where the track does is now how far through the month the reader is, which the ticks never gave. Past today nothing is drawn at all: a flat run to the month's end would read as a fortnight of spending nothing rather than as a fortnight that has not happened.

**A slice of foreign money leads with the money.** A dollar account's spending is dollars, and the card summed `base_amount_minor` and drew only that — so a $99 charge sat under "Where it went" as रू 13,860, a valuation stated as though it were the transaction, and the figure the reader knows was nowhere on the page. So the slice takes the app's two lines like every other foreign figure: the currency the money was actually in on top, what it comes to underneath. The query answers both (`ownTotalMinor` beside `totalMinor`) and hands back the own figure **only where the slice is of one currency** — `currencyCount` is what says so, since two currencies added together is a figure that is true nowhere, and a mixed slice keeps the converted one alone. The **bar and the ranking are untouched**: those are sums across slices, and the converted figure is the only one that can be summed.

**And a slice of "Where it went" opens the holding it was spent through.** The card answered the question down to a bank and then stopped, leaving the reader to find that same bank again on another tab to see what the figure was made of. Which page depends on what the slice is: a debt's slice carries the *loan's* id in `accountId` — an instalment names no account, so those rows are grouped by the debt they belong to — and `loanKind` being set is what says so. The one slice that opens nothing is the one with no holding behind it.

### The timeline is a receipt

**The page is torn once, where it is really cut** (`Perforation`, `DashedRule`). The tab is marked with a receipt, each day already sits on paper of its own, and the rule under a day's heading is broken rather than solid for the same reason: a solid one says the heading and its payments are unrelated where a broken one says the sheet carries on underneath. The tear itself was drawn between **every** pair of days at first, and at that scale it stopped saying anything — a month of daily payments was a column of scissors, and a mark meaning "the page is cut here" on every join is a mark for cutting nowhere. It is spent once now, at the one join that genuinely is a cut: where the log of the days ends and the blocks saying where the month leaves each holding begin. Between days there is a plain gap again. Withheld when there is nothing below it, since a tear at the foot of the page is a sheet torn off nothing — the same argument that always kept it off the top.

### A settled fact is stated, not asked

**`SettledBox` is drawn by hand and is no longer a disabled text field.** The trouble with a disabled `OutlinedTextField` is what its frame says: the notched border with the label cut into it is the strongest "type here" signal in the whole Material set, so a form that had settled down to one live box among nine settled ones still looked like nine boxes to fill in, and the one worth touching was the hardest of the ten to find. Greying it made that worse — it read as a form that had broken rather than as one that had been answered. What is left is a rule down the left edge with the label above the value: the shape a quotation takes, which is what a settled fact is. Hand-drawn for the reason `ChoicePicker` is — nothing is ever typed into it, and a real text field cannot stop looking like one. **Still not filled**, since fill means "write here" everywhere else. The eye can still hunt for it, which is the whole of what the box was doing for a date or a length.

**But a settled box sharing a line with a live field takes that field's height** (`matchesFieldBeside`, `Modifier.besideField`). Measured to its own content — which is right, and is what makes the rule exactly as tall as however many lines the value wraps to — it is exactly wrong beside an `OutlinedTextField`, which stands at its 56dp minimum however little is in it: the rule then ended a third of a box short and the settled half of the row read as having floated upwards. Two rows do this, and both are a rate beside an answer that has settled — "Interest rate" beside "Pay every?" on a bank's debt, and beside "Interest paid every" on a savings account whose first quarter has been credited. The row is given `IntrinsicSize.Min` so the field sets the height, and the box is inset at the top by half a label's line height, because Material notches the label *into* the top border and the field's visible box therefore starts that far below the space it was given. Taken from the label's own line height rather than measured off a screenshot, so it follows the type scale.

**A day's payments are divided by a rule across the words** (`RowSeparator`). A day's block had nothing between its rows at all, so three payments on one sheet ran together. What keeps it from reading as the *end* of the day is where it is drawn rather than how long it is: inside the row's own padding, so it starts and stops where the words do, while the day heading's rule runs the full width of the paper. It ran a little over half the row for a while, on the reasoning that a short rule reads as a break inside a block — and a rule stopping in the middle of nowhere reads as one that failed to finish. Full width across the words is the same sentence said cleanly. It is drawn inside the swipeable row rather than between rows, or it would hang over the red a swipe opens.

**The month is abbreviated where the calendar abbreviates, and it is never clipped.** "Aug 2026", not "August 2026" (`gregorianMonthYear`): that heading already carries two arrows and, once the reader has stepped away from now, a way back to it — and spelled out there was no room, so "September 2026" came out as "September 202" and the one line every figure below is relative to lost its year. Nobody reads the heading for the *word*. Bikram Sambat is untouched, its month names being short already and having no abbreviation anybody writes. What guarantees the rest is `weight(1f, fill = false)` on the label: **weighted**, so it is measured against what is left rather than being clipped by what comes after it, and **non-filling**, so with room to spare it stays its own width and the arrows go on hugging it — filling, it stretched and shoved the forward arrow against the screen edge on every ordinary month, which is the common case paying for the rare one.

**The stepper hides an arrow it cannot use rather than greying it** (`StepArrow`, on every page with a period). Greyed out it was still a control the thumb aimed at and the eye read as a way forward, and a page that offers a direction and then does nothing is worse than one that offers nothing. **But it keeps its place, and the place is a mark rather than a gap**: removed outright, the heading slides across the page at the edge and slides back on the first step away from it, so the one line every figure below is relative to moves under the reader as they walk the months. An empty slot is no better — Reminders *opens* at its own edge, so the first thing anybody sees there is a date sitting an arrow's width from the margin with nothing to its left, which reads as a control that failed to draw. The chevron therefore stays and stops being a control: no button, no ripple, no target, a fifth of the ink. That is a long way from the greyed-out `enabled` this replaced, which kept the whole 48dp button and Material's own disabled ink.

**The heading over a list on an inner page is a title, not an eyebrow** (`ListPageHeader`). Those pages used `SectionHeader`, which is the small grey caption a *form* separates its questions with — 11sp uppercase in the muted ink, so the one line naming what a whole page is a list of was set smaller than every row beneath it. That is the same fault `GroupHeader` was written to fix on the timeline, and it takes `GroupHeader`'s type for the same reason. **The spacing lives in the component**, not at the call sites: each of the three pages supplied its own and they had drifted to 40dp, 28dp and 8dp above the card, on three pages built to look like each other. The optional explanation under it is part of the same block, since leaving that to the caller is what let the gap under it drift too — and where a page has *several* such lines and draws them itself, as the schedule does ("2 already paid", the interest over the loan, the arrears note), they are indented by `GROUP_HEADER_GUTTER` to the same edge: at the page margin the block had two left edges a mark's width apart, which reads as a mistake rather than as an indent, and its sibling two taps away had always lined up. The statement card on the holding editor takes the corner and inset every other card uses, having had 16 and 18 of its own.

### Rows in a list

**An amount is red out and green in, everywhere it is drawn.** `WalletColors.moneyOut` and `moneyIn`, and the only three exceptions are a transfer (below), a balance gone negative (`error`, the alarm the ordinary red must stay clear of) and a debt's own ledger, which colours by what the payment did to the *debt* rather than by which way the money went. Money out was plain ink for a long while, on the argument that most rows are money out and colouring them all red makes ordinary life read as a series of alarms — and what that produced was a column where one figure in ten was coloured and the rest were the same ink as the words beside them, so a reader scanning for what a month cost had nothing to scan. Three places had drifted further still and are now on the same two colours: Home's "went out" headline, which was plain ink over a green "came in"; a day's total on the timeline, whose out half was grey; and the statement inside a holding's editor, which used the *primary* blue for money in. The red is a considered one rather than `error`: it is on every second row of every list, and the shade that means "this will not save" cannot also mean "you bought lunch".

**A transfer is one row.** Both halves are stored — one row cannot move two
balances — but a timeline that lists a transfer twice reads as money appearing
from nowhere and going somewhere else. The paying half is the one drawn
(`isTransferArrival` marks the other), because it names both ends and, across
currencies, carries both figures. It is unsigned and uncoloured: a transfer is
neither earned nor spent, and a minus in front of it would claim the money had
left the user's world. The arriving half is still in the list the arithmetic
reads — the balances need it — and only the drawn rows drop it.

Two things a row must not say are its own type and nothing else. A transfer that
says "Transfer" distinguishes nothing — every transfer says that — so it names
both ends instead: `transferFromName`/`transferToName` are resolved once in the
repository (the direction decides which end this half is) and a named transfer
keeps its name on top with "Wise → Nabil Bank" underneath. A projected loan
instalment carries `isLoanPayment` and says "EMI", because a bank's name alone
does not distinguish its term loan's instalment from anything else it is
involved in.

Projections are drawn at exactly the same size as real entries. They used to be
smaller and greyer, which read as *less important* rather than as
*not-yet-happened*; the section heading and the running balance already say it is
a plan.

**Every other row carries a faint band** (`rowStripe`, on Home's recent list, Reminders, an account's statement and a debt's). The colour beside each row went with the labels, and a screenful of three-line rows with nothing between them ran together. It claims to mean nothing, because a row is not *about* anything by being the second one, which is why it is a breath of the page's own ink rather than a hue. But it is **`WalletColors.rowBand`, one value per scheme**: it was a single four-percent alpha over `onSurface`, on the reasoning that the page's own ink is right in both — and four percent of white on a near-black page is a clear step where four percent of near-black on cool paper is invisible. The value read as scheme-independent and had only ever been looked at in the dark one, so the light scheme had no banding for as long as the band existed. Applied before the row's padding so it reaches both edges; inset, it would read as a card. **And it is a breath rather than a stripe** — roughly half what it was first set to. At six percent on the paper a list now sits on, the banded rows read as a second colour of row rather than as one list: a checkerboard, which is a pattern the eye follows instead of reading past. All the band has to do is stop three lines of text running into the three below them, and the smallest step that does that is the right one. One value per scheme means the five lists that band — Home, Reminders, an account's statement, a debt's, a loan's remaining payments — cannot drift apart.

**And a list of movements sits on its own paper** (`listPanel`, `WalletColors.listSurface`, on Home's recent list, Reminders and each day of the Timeline). Those three drew their rows straight onto the page, so a screenful of movements had no edge anywhere — the list and the background behind it were the same colour, and both schemes read pale. The Accounts tab answers this with a white card, and repeating that here was the wrong answer twice over: on Home the recent list would be a third white card under two others with nothing saying it is a different kind of thing, and every page in the app would be one shape. So this is deliberately **not** `surfaceContainer` — where a card is raised off the page towards white, this is a sheet set *into* it, a shade deeper and cooler in the light scheme and a shade lighter and bluer in the dark one. A card is a thing on the page; a list is a tray cut into it. The band still bands, inside the paper rather than across the page.

**The tray has to be the page's own paper a shade deeper, not a second colour of paper.** The light one was `#E7EDF7`, whose blue sits sixteen points above its red where the page's sits five above its own — so it read as a pale blue panel laid on cool grey rather than as the same sheet cut into, and the mismatch was the first thing the eye found on every list in the app. The band went with it and for the same reason: it was the page's near-black at 2.8%, and a neutral wash over cool paper *greys* it, so the banded row was not a deeper row but a duller one — it is a cool dark blue now, mixed from the same ink the tray leans towards.

**And both steps are measured against what they sit on.** Fixing the hue and leaving the depth alone was only half of it: the tray still sat eleven points under the page, and the band eight under the tray — very nearly as strong as the sheet it was drawn on, so the odd rows read as a third surface rather than as the same one shaded. The tray is `#ECEFF4`, about seven under the page, and the band five under the tray. It has to be *found* rather than noticed: what the sheet is for is giving a screenful of movements an edge, and anything past the faintest step that does that is a panel laid on the page. **Light only.** The dark scheme's pair were tuned against the page they sit on and are untouched.

It is a **modifier and not a wrapper**, cut round at whichever ends are the ends of the list and square in the middle, because a `LazyColumn` cannot put a box around items it has not composed: Reminders paints one sheet a row at a time, and the Timeline paints one per day — its sticky day heading is that day's top edge, which is also what keeps it opaque as the rows pass behind it. A **swipeable row paints the paper itself** (`SwipeToDelete(background =)`) rather than taking it from the item around it: a swipe opens a gap, and the red has to be what shows through it. That is also what lights the row a lesson is taught on, `TutorialLight` providing the light scheme's paper without the row knowing anything about it.

**Every list of movements is on it**, not only the three tabs: an account's *Every transaction*, a debt's *See every payment* and a loan's *Every payment* are the same rows about the same money two taps further in, and one of them on paper beside one on the page would read as two different kinds of page. Each ends at the **last row shown** rather than at the last row there is — what is past that is *See more*, a button asking for the next page and not part of this one. On the schedule the column headings are the top of the sheet, exactly as a day's heading is on the Timeline. Rows are inset from the paper's edge (`LIST_PANEL_ROW_INSET`) rather than from the page's, the way a card's rows are.

**The one table that stays in a card takes the band anyway** — the schedule drawn *inside* the loan being created, where there is no debt to open a page for. The band is an alpha rather than a colour, so on white paper it comes out as a whisper off white and on the page's own paper as the tint it always was; nothing had to be told which surface it is on. What it did need is `cardBleed`: a card has already inset its content, a row cannot pad itself by a negative amount, and a band that stops short of the edges reads as a stripe laid on the paper rather than as one row of it. So the row is measured wider by the card's inset at each end, placed back by that much, and reports the width it always had — only the paint spills, and only in the middle of a card, where the edges are straight and the corners are somebody else's problem.

**On the Timeline the band is on the day heading and not on the rows.** It is already cut into days by a sticky header with a rule under it, so banding the *rows* was a second grouping laid over a page that had one and the two did not line up — a day of three payments read as a stripe pattern rather than as a day. Every other list of movements is one flat run of rows with nothing dividing it, which is exactly where banding the rows earns its keep. `STRIPE_FROM` went with it: it existed because banding a day of one or two rows singled them out, and no other list groups by anything. What the band does here instead is separate the one line on the page that is about a *day* — the date, the weekday and what the day came to — from the payments beneath it, on the heading over a day that has happened and the heading over a day still to come alike, because those two are one kind of row and cannot be drawn two ways on one page.

**A row is three lines, and the date is the third.** What the row *is* leads,
what it says about itself — the bank, the route, what the payment did to a debt —
is the line under it, and the date sits on its own beneath both. All three used
to share two lines, so a row with anything to explain was ellipsised before it
reached the date, and the bank's name went first: the one thing that tells two
payments of the same amount apart. Only the date's length is knowable in advance,
which is why it is the part given a line of its own. The timeline passes
`showDate = false` and gets two lines, because its day header has already said it.

**The arrow in a route is drawn, not typed.** `ROUTE_ARROW` is written into the
strings the rows build and swapped for an icon by `RouteText` at the moment they
are set — as a character U+2192 comes from whichever font on the phone carries
it, not the one setting the words beside it, and it sits low enough to read as
pointing downwards. `MoneyRoute` does the same for the pair of figures. Anything
that joins a route into a longer line has to be drawn with `RouteText`, or the
glyph comes back.

**A day still to come is headed exactly as a day that has happened.** Both are `stickyHeader` rows, so both pin under the month and travel off with the payments beneath them. A future day used to draw its heading *inside* the block of rows it headed, which meant the stickiness stopped at the first projection — and on a month made entirely of them, which is every future month, nothing pinned at all and the reader scrolled a list of payments with no day against them.

**On the timeline a day is set smaller than the rows under it, and in italic.** A
day is the margin the list is written down rather than one of the things in it;
at the same size and weight as an entry it read as that day's first row. One
`DayLabel` draws every one of them — the sticky header over a day that has
happened *and* the heading over a day still to come, which was set as a
`titleSmall` and made an EMI's date read louder than the rent that had already
gone out. Any new list that groups by day uses it too. The blocks below the log —
Accounts, what is owed, what is owed to you — take `GroupHeader` instead of the
small grey eyebrow, and the *first* of them carries a rule above it. That rule is
the seam between the two halves of the page: what happened day by day, and where
it leaves each holding.

### Reminders

**A tab for what wants doing**, between Home and the Timeline. The Timeline
answers "what does this month look like" and buries today in the middle of it
behind a stepper and three filters; this is the short answer.

**The setting is a lead time, not a window.** `reminderLeadDays` is *how many
days before something falls due the user is told about it* — zero, the morning it
happens, by default, and at most six. It is not "how far ahead the tab looks":
that framing turned the page into a forecast of the week, which is the Timeline's
job, and it is the wrong shape for the question being asked.

**And it belongs to the notification alone.** It governed the tab as well, on the
reasoning that one number meaning one thing on both is what stops them saying
different things about the same morning — and what that produced, on a page that
can be *stepped*, was every payment drawn on two consecutive days: a reader
walking forward with a day's warning asked for met the same rent on the 6th and
again on the 7th, and read it as the app having recorded it twice. The two
questions are simply different. A **notification** answers *what is coming*,
which is what a warning is; a **page you stepped to** answers *what happens on
this day*, which is one day's worth. So `ReminderViewModel` reads no setting at
all now — which is also what stops the two drifting apart, there being nothing
left on the page to disagree with — and the repository names the two rather than
sharing one function through a lead parameter: `due(leadDays)` for the
notification, `onDay(day, entries)` for the tab.

It is one of the settings asked with a **picker** (`ChoicePicker`) rather than a
row of chips. Seven answers wrapped onto three lines of near-identical phrases —
"2 days before", "3 days before" — which is a paragraph to read for a decision
that is one number; the current answer is stated in the box and the rest sit
behind it. The currency, the language and the automatic-backup rhythm are pickers
for the same reason: each has more answers than a line holds, and a row of chips
spends the width of the card stating the ones the reader did not pick in order to
change the one they did — the language row in particular laid out two languages
they are not reading in.

**What decides between the two is whether the answers fit on one line**, not what
kind of question it is. The theme stays chips, its three answers being one word
each; so does the **calendar**, which has exactly two — **English (AD)** and
**Nepali (BS)** — and hiding one of two answers behind a tap saves nothing and
costs the glance that says which one is on. Both are asked identically in
Settings and on the welcome panel, which is the rule for every question the two
screens share.

Those two labels name the *era* rather than the country: a Nepali reader knows
their dates as BS and everyone else's as AD, and "International (2026)" both
carried a year that would go stale and left the other answer unnamed. **And they
are the only names either calendar has.** Mid-sentence the era comes off —
"follows the English calendar" — but the stem is the same word the chip is
picked by (`calendar_name_english`, `calendar_name_nepali`). It said
"International" for a while, which was a third name for a thing the settings page
already called two, and a reader who chose "English (AD)" was then told their
interest follows something else.

**And a picker's box is as wide as its widest answer**, measured rather than
fixed (`fieldWidthFor`). One width for all of them was right while every picker
held a short code and clipped anything longer; the widest of *all* the answers
rather than the one showing, so the control still does not move when it is used,
and measured rather than guessed because the same list is read in two languages
that do not agree about how much room an answer needs.

**And a picker is a box, not a line of text.** It was a row of plain text with a
chevron beside it, which is the shape the app uses everywhere else for a fact
that has *settled* — so the one thing on the card that could be changed looked
like the one thing that could not, and nothing said otherwise until it had been
tapped. It is a bordered, filled box now, **168 by 44 and drawn by hand rather
than as an `OutlinedTextField`**: nothing is ever typed into it, and a real text
field cannot go below its own minimum height or stop asking for the width it was
built to hold prose in — full width it promised a sentence and held three
letters, and it stood taller than every chip on the cards either side of it. A
fixed width rather than what the answer happens to need, because "AED" and
"HK$  HKD" are not the same length and a control that moves when it is used is
one the thumb has to find again. The menu keeps Material's own size, which is the
width of the box it came out of, and opens **scrolled to the answer already on
file** — AED is last of the eighteen currencies, and a user paid in dirhams
would otherwise open the list on a screenful of currencies that are not theirs.

**What a picker means goes beside it** (`ExplainedRow`), where `Explain` sets its
line underneath. A row of chips takes the width of the card and leaves nothing to
put beside it; a picker is a small box with most of the card to its right, so the
sentence sat under empty space and spent a second line of the card on it. Middles
aligned, because the two are one line read across rather than a heading with a
note under it.

**One flat list, soonest first, drawn exactly as Home draws a movement** — what
it is, what it says about itself, and the day it falls on underneath. No
"Today"/"Tomorrow" headings and no day sections: a payment simply joins the list
when it comes within the lead time, and its own third line says which morning it
lands on.

**And the page can be asked about a day other than today.** `DaySelector` steps
it, and it is the timeline's `MonthSelector` one unit down — the same control,
drawn by the same private `PeriodSelector`, saying its own nouns, because two
steppers drawn differently would read as two unrelated ideas. **It is the page's
only heading**, as the month is on Home and the Timeline: the title reading
"Reminders" over a tab labelled Reminders said nothing the tab had not, and the
line under it explained the page to somebody already on it. Both strings were
deleted with it, which is what `UnusedResources` is for. It opens on today,
goes no further back than that (a day gone is not something that wants doing, and
only the real rows of it survive — the projections are computed forwards, so a
past day would list half of itself), and reaches
`ReminderViewModel.MAX_DAYS_AHEAD` days out; past that the question stops being
"what wants doing" and becomes "what does next month look like", which the
timeline already answers a month at a time rather than thirty taps at a time. The
edge is clamped in `showDay` as well as by the arrow being disabled, since the
arrows are drawn from a state that lags a tap.

**Stepping asks about one day, and the answer is that day.** The list is exactly
`[day, day]` — `ReminderRepository.onDay` — for the reason above: a window that
moved with the day being looked at drew every payment twice as the reader walked
forward. It stepped `[day, day + leadDays]` for a while, which at the default lead
of zero was already one day at a time and only misbehaved for somebody who had
asked to be warned early — which is to say, for somebody who had used the one
setting the tab has. The empty state says "for this day" rather than "for today"
once the reader has stepped off it, and the offset is held for the session and not
persisted, for the reason the month is not.

`ReminderRepository` gathers from the same four sources the timeline uses — a
rule's materialised occurrences, its projections, a savings quarter's interest,
and a maturity — so a row here and the row for the same payment there cannot
disagree. **Today is made of real rows, not projections**: `materialiseDue` runs
the moment the app opens, so an occurrence dated today is already an entry and
every balance counts it. Those rows are drawn like any other and carry no
"already recorded" note — the user is being reminded of the payment, not audited
on whether the app has written it down yet — and hiding them would blank the page
at the moment it was opened to check.

**Nothing at the foot of it.** The page answers *what wants doing*, one payment
at a time, and a sum of a few days' payments is a figure with nothing to compare
itself against — neither a month's spending, which Home gives, nor what is left
afterwards, which the Timeline gives. `Reminders.moneyIn`/`moneyOut` stay,
because the notification is one line and the total is the whole of it;
adjustments are outside both there, as everywhere else, so a day of nothing but
transfers reads as zero rather than as an expensive one.

**Once a day the phone can be told.** `ReminderScheduler` puts a `ReminderWorker`
on WorkManager at the hour the user picks, and it posts **only when something is
due** — a daily notification that arrives whether or not it has anything to say is
one the user learns to dismiss unread, and by then it is the one carrying their
rent. It counts the same lead window the tab shows, because that is what the
setting means; with no lead asked for it can say "due today", and with one it
says "coming up" instead, since half of what it is counting has not arrived yet.
**One thing due is named; several are counted.** "1 thing due today" is the
least useful sentence the app can say — the reader has to open it to find out
whether it is the rent or a magazine, which is what a reminder exists to save
them — so where there is exactly one, its own note is both shorter and the whole
answer. It stops at one deliberately: two or three named on a lock screen is a
list of what somebody owes, readable by whoever picks the phone up, and it grows
past the one line a notification gets anyway. Beyond that it gives a count and a
total and nothing else: the payments themselves would be on a lock screen
anybody can read.

**A tap on it opens Reminders**, not Home. The notification is a note about the
list on that tab, and landing on the summary of the month was an answer to a
question nobody asked. `MainActivity` holds the request as state rather than
reading its intent, for two reasons: the tap often arrives while the app is
already running, which reaches `onNewIntent` and never touches the intent
composition first saw; and with the screen lock on nothing can navigate until the
user is past it, so the request has to survive being unanswered for a while. The
route is checked against the tabs that exist before it is followed — an extra is
something any app on the phone can send.

**And it opens the day it is about, which is not always today.** The tab answers
for one day; the notification counts a lead window — so a user warned a day early
gets a note about tomorrow's rent and used to land on today's page, where it is
not. It carries the day as a second extra (`EXTRA_DAY`, an epoch day), the
**soonest** of what it is counting, since the rows are sorted and what is nearest
is what they are being warned about first; at a lead of zero that is today, which
is everybody who has not asked to be warned early. Held beside the route and
consumed separately, because it is applied later: the tab is navigated to first,
and the day can only be given to a page that has composed — so the Reminders
composable applies it and clears it, rather than the navigation clearing it a
frame before anything could read it. `showDayOn` clamps it like every other way
of moving that page, so a day out of range lands on the nearest one it can show:
the tap must land somewhere. Checked for being a day at all on the way in, for
the reason the route is checked.

Two rules about the schedule. **Changing the time re-aligns it and a launch does
not** (`realign`): `UPDATE` leaves the next run where it is, which is what an app
opened at ten to nine needs, and `CANCEL_AND_REENQUEUE` is what a changed hour
needs. And **the permission is asked for at the switch**, not on arrival at the
screen — a prompt on a page opened to change the theme is one that gets refused
out of hand — with `areNotificationsEnabled` checked again before every post,
since it can be revoked at any time.

### Rates that move

**A rate belongs to a period, not to a holding.** Nepali banks review savings and floating loans quarterly, so over seven years the figure on file is the current one and every sum ever computed from it was computed at some other rate. `rate_change` records each move with the day it took effect; the holding's own `annual_rate` column keeps meaning *the rate it opened at* and nothing but creation may write it. Overwriting it would recompute years of settled history at whatever the bank charges this month — which is why the editor never passes the typed figure through on an edit, only the stored base.

**Changing the rate asks when, and the answer starts at today** on every holding — a rate is agreed on the day it is agreed, and the day the money moved is a different fact. Defaulting to that day silently charged a debt for months nobody had agreed a rate over. The date field appears the moment the figure is edited and not before, because that is the only moment the answer matters. `RateSchedule` then answers "what was the rate on this day", and splits interest at the changes rather than averaging across them — a rate that doubles on the 11th costs the old rate for ten days and the new one for twenty-one, and the day it starts is charged at the new one.

**A loan's instalment does not move.** That is the whole shape of a floating loan here: the standing order goes on paying the same figure and the change lands inside it — more interest and less principal, or the reverse. What gives is the **term**, so `applyRateChange` recomputes it and moves the rule's end date with it. Nothing is written to the timeline, because no money changes hands on the day a rate changes; what changed shows up in the split of every instalment after it, which the loan's own statement prints payment by payment.

**A savings period pays its own share of the annual rate** — at the usual three months, 9% a year is 2.25% a quarter, *not* `9% × 92 ÷ 365`. A period runs from the 1st of a month to the day before the next one opens, with the interest landing on that next 1st.

**Whose months, is asked of the holding — and answered by two things, not one.** This is the one place in the app where the calendar decides when money *moves* rather than how a day is drawn, so every function in `SavingsInterest` that counts a year or opens a month takes a `CalendarSystem` and none of them may assume. Bikram Sambat cuts the year at 1 Baisakh, Shrawan, Kartik, Magh; Gregorian cuts it at 1 January, April, July, October.

**But the display setting alone must never decide it.** Reading dates in Nepali is a preference; a bank closing its quarters on 1 Baisakh is a fact about the arrangement, and most Nepali banks do neither — they work in English months whatever the passbook is printed in. So the holding carries an opt-in (`account.interest_in_bs`, `loan.recur_in_bs`) and `CalendarSystem.forInterest` joins the two: Bikram Sambat only when the holding says so **and** that is the calendar being read; English in the other three cases, which is the default and the answer for almost everybody. **Uses default calendar** — `DefaultCalendarSwitch`, under "Interest paid every" and under "How long?" — is the only way in, and it is off unless somebody says otherwise. The alternative, inferring the bank's months from the patro, moved every payout day and every due date the moment a user switched their display.

It is one control, and it is asked in three places now — a savings or current account's interest periods, a debt's instalments, a deposit's term — drawn as the switch row Settings uses for the app lock: the words are part of the target rather than a caption beside it.

**It is asked only while the holding is being created.** Answering it later re-cuts periods that have already been counted from: every closed quarter restated, every due date moved, on a holding whose figures the user has been reading for months. So the switch is gone from an existing holding and the answer is *said* there instead — "Interest payout follows the X calendar" under a savings account's rate, "EMI calculation follows the X calendar" under a debt's rhythm. A holding set up in the wrong calendar is deleted and entered again, which rewrites one arrangement rather than everything derived from it.

**And a policy, a goal and a repeating entry are not asked at all.** Those are the user's own rhythm rather than a bank's schedule: they follow the calendar being read, there is nothing to opt into, and a switch there was one more thing to get wrong on the way in. The switch says which way it is *set*; the line under it names what the months are actually counted in, which is the half a reader can act on and is English until the switch is on.

**And it names what *this* form counts in them**, which is the caller's to say (`explain`, one string per site: a recurring payment, an interest payout, an EMI calculation, a deposit's term, premiums, contributions). One control asked in six places is one *question*, not one sentence — a goal has no EMI and a loan pays no interest into anything, so the single line that tried to cover all six read "EMI or interest calculation" on every one of them and was at least half about some other form. Withheld where there is nothing to opt into — a debt with no schedule, an overdraft, and **every holding belonging to somebody who reads the app in English on English dates**, since a switch offering the calendar already in force says nothing and both answers step the same months. The test is `calendarIsNepali || languageIsNepali` and not the calendar alone (`AppSettings.readsNepali`, which asks the stored tag where there is one and the phone where there is not): a reader in Nepali on Gregorian dates is still somebody whose bank may well close its quarters at the end of Ashoj, and the switch is how they say so. It records the opt-in either way — `uses_selected_calendar` is what the user answered and `recur_in_bs` is what the dates are actually stepped in — so a holding ticked under a Gregorian display goes on counting English months until the day the display moves, which is exactly what a stored opt-in is for. It carries a little air under its line wherever it is drawn, because the field below it started immediately under the explanation and the sentence then read as a caption belonging to *that* field rather than to the switch above it — a small gap, since the line and the switch are one control.

**Which way it defaults is the difference between a schedule somebody else set and a rhythm the app counts.** A **debt** is the one that says no: a bank debits an instalment on the day the loan agreement names, which is an English date whatever patro the borrower reads, and a schedule that moved with the display setting would be the app guessing at somebody's standing order. Everything else says yes — a repeating entry, a policy, a goal and a deposit are the user's own arrangements, counted in the months they think in (somebody setting up a subscription on 1 Baisakh means Baisakh, Jestha, Asar), and a savings or current account is a Nepali bank's quarter, which closes at the end of Ashoj, Poush, Chaitra and Ashad — the passbook the reader is checking the app against. `HoldingEditorState.interestInBs` is therefore nullable, and `usesSelectedCalendar` fills the default in from what is being set up. The bank account's yes is conditional on the switch being **on screen** — which is where Nepali is the calendar being read — because opting one in behind a reader's back would leave a quarter that moves the day they first switch their display, which is the one thing the opt-in exists to prevent. Every one of them is still a default and one tap from the other answer.

**The opt-in and the effective answer are two columns wherever the dates are generated from a row.** `recurring_series` carries both: `uses_selected_calendar` is what the user answered and `recur_in_bs` is what `Recurrence` actually steps in, written from the pair on every save. A plan and a deposit keep the same pair in `account.interest_in_bs` and `account.plan_recur_in_bs`, because every reader of a premium date or a maturity is a pure function of the account row and none of them can reach the setting. That is also why the setting moving has to restate them — `PlanRepository.recalendarPlans` beside `LoanRepository.recalendarSchedules`, on the setting change and on launch.

**Both columns were backfilled from the effective answer on upgrade**, which is the only reading that leaves every rule doing exactly what it did the day before: one written in Gregorian is pinned there for good, and one written in Bikram Sambat goes on following the calendar it was written under. The plans are turned *on* only, never off, since a savings account may already carry an opt-in of its own.

**Either half of the answer moving restates everything, and nothing computed on the old one may be left standing.** Ticking the box on a holding, unticking it, or changing the calendar setting all re-cut the periods — so all three run the recomputation on the spot rather than leaving it to the next launch. `HoldingEditorViewModel` reposts when the opt-in moved as well as when the interval did (`storedInterestInBs` is what tells it), `saveLoan` already reposts, and `SettingsViewModel.setCalendar` does both sides. **The debts first and the interest second**, which is the order the launch runs them in and for the same reason: re-calendaring a rule rewrites the instalment rows it has generated, and those rows are movements the interest is computed from — reposted first, the interest is worked out on balances the loan is about to restate. `recalendarSchedules` also runs on launch, before `materialiseDue`, so a backup restored onto a phone reading the other calendar arrives in step.

**Switching the setting therefore moves the payout days of the holdings that opted in, and nobody else's.** For those, the answer is the one an interval change already gets: `postDueInterest` works the whole history out again in the calendar now in force, and `sweepStrayPostings` takes the credits left on days it has no period ending on. Keeping the old ones beside the new would pay the same days twice — a Gregorian quarter and a Nepali one overlap rather than abut — which is why the past is restated rather than left alone. It is idempotent and rewrites each posting in place, so switching back returns exactly what was there before. `SettingsViewModel.setCalendar` runs it on the spot, and `LoanRepository.recalendarSchedules` beside it puts each opted-in debt's rule back in step: left to the next launch, the account shows credits on days it no longer pays on and the timeline draws a due date the debt's own table disagrees with.

**How long a period is, is the account's own answer**, and it is asked beside the rate on the holding it describes — "Interest paid every" (`account.interest_payout_months`, three months where nothing was ever said), in the same box every other length in the app uses: the unit inside it, the Months/Years chips only while it is being typed. Those two boxes are one question — what does this account pay, and how often — and one without the other says nothing about what lands in it. Banks do not agree: quarterly is the common Nepali arrangement, but monthly, half-yearly and yearly all exist, and the whole point of the figure is that it matches the passbook. `SavingsInterest` takes the gap on every function that has an opinion about it — the payout days, the day a period opens, the slice of the year it pays — and nothing in it may assume three; `InterestRepository` reads it off each account as it walks them, because a user with savings at two banks is on two rhythms and a figure summed from the wrong one is simply a different account's interest.

It was one row in Settings, for the whole app, and the reason that had to go is the same reason it was a setting rather than a constant: banks do not agree — and neither, therefore, do two accounts belonging to one person. `SettingsStore.takeInterestPayoutMonths` is what carries an upgrade across: a phone that answered the old question has real interest on file worked out from that answer and no migration can read a preference, so the value is *taken* — read and removed in one act — on the next launch and written onto every account that has none (`adoptStoredPayoutInterval`, before `postDueInterest` and never after). Taken rather than merely read so that it happens once and for ever: an account created afterwards is the user answering for itself, and a second sweep would overwrite them all with the figure they had replaced. A phone that never answered has nothing to take, which is what a null column already means.

**It settles when the first period is credited, and not before.** Changing it after that does not describe a new arrangement, it rewrites the old one: the payout days move, the postings sitting on days that are no longer payout days are swept, and a passbook the user reconciled against last year stops matching. So what closes the question is that an answer to it is already on file — `payoutSettled` is `postingsFor(account).isNotEmpty()`, read from the credits themselves rather than from a flag somebody set, and the box is then drawn as a settled one (a box, disabled, the way a settled length always is) with a line saying why. Before that first credit there is nothing to rewrite and it stays open: an account entered with the wrong rhythm can be corrected as long as the correction costs nothing.

That is what replaced a latch, a Save row of its own and a confirmation dialog. All three existed because one setting stood for every account at once — it could be settled long before the account it would first apply to was created, so the app had to ask the user to promise. Per account there is nothing to promise: the form's own Save writes it, and the moment it has been acted on it stops being editable on its own. Nothing else in the app un-asks it, `DataEraser` included — it is a fact about a bank and lives on the account it describes, so clearing the tables takes it with the figures it produced.

**The year always restarts at its own first month** — 1 Baisakh in Bikram Sambat, 1 January in Gregorian. Periods are counted from there, so a gap that does not divide twelve — every five months, say — leaves a *short* period at the end of the year rather than drifting across the calendar for ever. `periodStart` therefore finds the previous payout day rather than stepping back by the gap, which would land in the middle of that short one and charge days twice. The short period pays what it is worth: its own months over twelve. That is the same rule the whole-year case follows, which is why a year of periods comes to the annual rate exactly, whatever the gap — `InterestTest` pins it for every gap that divides twelve.

This is deliberately **not** the day-count convention loans use. A loan accrues day by day at `rate ÷ 365`; a savings period is a fixed slice of the year. The two disagree by about a quarter of a percent of the interest — small, and wrong.

Within the period, money earns for the share of it that it was there: रू 1,00,000 arriving halfway through a quarter earns 2.25% of half. The period's own length in days is the denominator, so a 90-day quarter and a 92-day one both pay exactly a quarter of the year on money held throughout. That is why every movement's date is kept whether or not it is ever shown — and why the span is **half-open**: the first day earns, the payout day does not, because it opens the next period. A movement dated *on* the opening day is not a movement at all, it is opening balance; the previous period's own interest is credited on that very day, so getting this wrong silently shorted every period after the first.

**But interest is not a launch job, it is a derived figure**, and it is worked out again wherever money lands on a day a closed period was counted over. It used to run at launch and nowhere else, and that is a whole class of bug rather than one: a loan taken last September and entered today writes eleven months of movements into a savings account in a single save — the money arriving, the broken-period charge, every instalment since — and every one of them falls inside a period the bank has already paid on. The account showed the right balance and **no interest at all**, and stayed that way until the app was next killed and reopened. `InterestRepository.repostIfBefore` is the trigger, and everything that writes a dated movement calls it: `saveEntry`, `saveTransfer`, `deleteEntry`, `undoDeleteEntry`, a lump sum, a drawdown, more borrowed. `saveLoan` and `deleteLoan` call `postDueInterest` outright, beside the `materialiseDue` they already call and for exactly the same reason. `recordChange` calls it too — a rate corrected on a Tuesday changes what every closed period since earned, and the figure on screen must not disagree with the rate printed above it until the app is killed.

**Only for a day *before* today.** A period closes on its payout day and is counted up to it exclusive, so nothing dated today or later can be inside one — and the ordinary case, an entry added for this morning, must not pay for a walk over every account's whole history. On an edit it is the *earlier* of the old and new dates, since an entry dragged forward out of a closed period changes it as much as one dropped into it.

**Both of them run once per launch, in `AppViewModel`** — not in the view models of the two tabs that happen to show a schedule. They used to, and an app opened on Home therefore showed a month with today's instalment missing from it and a balance that had not felt it, until the user happened to visit the Timeline or Reminders. A restore runs them too, since a restored rule arrives with its own watermark and occurrences already owed.

**`postDueInterest` works the whole history out again, every launch, and is deliberately not incremental.** Each posting's id is derived from the account and the day, so recomputing a period rewrites that one row: running from the account's earliest known day is idempotent, and it is the only thing that stays right when the past changes underneath it. Three ways it does, each of which produced a figure the passbook disagreed with while this started at the watermark:

- **A movement lands behind the watermark.** A loan disbursed last September and entered today credits रू 27,00,000 to an account three closed periods ago, and the bank has been paying interest on it ever since.
- **A rate is corrected**, which changes what every day since was earning. `recordChange` used to roll the watermark back and tombstone the rows by hand; it no longer needs to.
- **An account's interval is changed**, which moves the payout days themselves. Postings sitting on a day the new interval has no period ending on cannot be rewritten, so they are found by their derived id and swept (`sweepStrayPostings`) — left behind, switching quarterly to half-yearly would pay the account twice for the same six months. The form settles the interval the moment anything has been credited, so this is now an upgrade adopting the old setting or a restored backup rather than anything the user can do to a working account; the sweep stays, because both of those can still move the days.

`account.interest_posted_through` survives as the record of how far interest has been credited, which is what `projectDue` reads. `projectDue` does the same arithmetic for periods still to come, so a future month shows the credit as a row and the account's forward balance feels it — the bank's schedule is as much a part of "where will my money be?" as an EMI is. Those rows carry `isInterest`, which is what stops a tap offering to stop a repeating rule that has never existed.

**A period's own credit is money the next period earns on**, so each one is added to the working balance as it is worked out — that is what the bank does, the credit lands and starts earning the same day. Which is exactly why the account's *stored* postings are taken back out first (`AccountDao.movementsExcept`): left in, the run would be reading its own previous answers, and every launch nudged each figure a little further — रू 362 over four quarters of a seven-year loan, converging on the right answer but never arriving. Taken out and put back as they are recomputed, the run says the same thing every time.

The posting is an ordinary money-in entry, and **its derived id is the whole of how it is recognised** — `<account>-interest-<day>`, which is also what makes recomputing a period rewrite the same row. Three things read it: the sweep of a stray posting, the query that keeps the app's own answers out of the balance it computes from (`movementsExcept`, matched with `substr` rather than `LIKE`, which would read `_` as a wildcard), and the row's own title. It used to carry an **Interest** label as well, and the label was what those queries matched on; with labels gone the id is the only mark it has — which it always had to be, since the id is what makes the recomputation idempotent. Accrual starts at the earliest day the rate meant anything, never at the beginning of time: an account given a rate today has not been silently earning for years. **What decides that day is whether the account opened at a rate, not whether a change was later recorded against it** (`earliestRateDay`). `annual_rate` means "the rate it opened at", so an account that has one starts at the earliest day the app knows anything about it — the day it was created *or* the day of its oldest movement, whichever is earlier. An account the user has told the app held रू 27,00,000 since last September really has been earning quarters on it, and the interest there is not invented: it is worked out on money the app was told was in the account, on the days it was told it was there. The creation day still guards the account with no history at all.

**Reading the first dated *change* as that day is what this replaced, and it destroyed interest the moment a bank repriced.** A savings account opened at 5% and moved to 6.5% in April lost every quarter before April — रू 68,793 and three whole postings that simply never appeared, on a phone where nothing said they were missing. It ran the wrong way round besides: recording a rate **rise** left the account earning *less* than recording nothing at all, so the one act a user performs to keep the app honest was the act that cost them. `scheduleFor` has always carried `annualRate` as the schedule's base, so the days before the first change were priced correctly the whole time — they were simply never reached. The first change is still the honest start where the rate lives **only** in the history: a rate agreed on a holding that never had one charges from the day it was agreed and not one day earlier, which is exactly what a null `annual_rate` beside a dated change means, and is the same distinction `hadRate` draws on the form.

### Fixed deposits

`AccountKind.FIXED_DEPOSIT` is money put away for a term. Nothing may be paid into it or spent from it, so it appears in no list on the money in/out form and at neither end of a transfer — the one holding besides a policy that is absent from both rows.

**It holds what was put into it, and that is what every list shows.** No special case computes its balance — no entry ever names it, so the ordinary path falls through to the opening balance. It is locked, not gone, so it belongs in the Accounts row and in "what you have" like anything else the user owns. There was briefly a balance that crept up day by day towards maturity; it was a savings account wearing a deposit's name, and on a deposit whose day had passed it read as zero — the user's money simply absent.

**Simple interest over the whole term**: `principal × rate ÷ 100 × years`, arriving in one piece on the day it comes free. That is deliberately the bank's arithmetic and not a better one — it is what Everest Bank's fixed-deposit calculator computes, whose script offers a compounding branch and then calls itself with compounding switched off. A deposit is the one holding the user has a printed figure from the bank to check against, and an app quietly returning more than the certificate says would be telling them their bank had short-changed them. `FixedDepositTest` pins this by recomputing the reference's own line.

This is a third convention, and all three are deliberate: a loan accrues `rate ÷ 365` a day, a savings quarter is a fixed slice of the year, a deposit is simple interest across its term. Each is the one that product's bank actually uses.

**The day the money went in is the fact stored**, and the day it comes free is that plus `deposit_term_months`. The form asks for the start date, because that is the day the user remembers; two columns for one arrangement could disagree.

The editor leads with the figure the user is actually asking for — what they get back — with the day underneath it and the interest inside it on the line below. What went in is not repeated there: it is the starting balance, already asked for and stated beside the name. A figure for "what it has accrued so far" was tried and removed twice over: it repeated the deposit, and a balance creeping up day by day describes a savings account rather than the arrangement the user agreed to.

A deposit is deliberately **excluded from `earningInterest()`**, though every one of them has a rate: that query feeds the savings quarter, credited as a real entry, and a deposit earning on its own term would be paid twice.

**Its rate cannot move**, and it cannot be changed into another kind — `bankHoldingsFor` offers it only itself.

**Maturity is drawn as a forecast and never written down.** `maturingBetween` produces the timeline row — a movement between two holdings, in the two-line shape a transfer takes — and nothing materialises when the day arrives. The app records the arrangement and leaves the moving of the money to the user, exactly as it records a loan without pretending to have watched the money land. An automatic payout is the one thing that can make a deposit's money vanish: credited to an account the user has since corrected by hand, or skipped as back-dated and credited nowhere at all. A forecast cannot.

**A deposit's forward balance is that one day, not a sum.** Subtracting the projected maturity from what it holds gave a *negative* balance, short by exactly the interest — the money leaving is the deposit plus its interest, and only the deposit was ever in there. So it is what it holds until the maturity date falls inside the window being projected, and zero from then on.

**Money between people is handed back in one go.** Nobody sets up an EMI with their sister, so a `PERSONAL` loan has no frequency, no instalment, no first-payment date and no schedule table — `paysInOneGo` withholds all of it, and `LoanRepository` refuses to compute an instalment for one however long it was agreed for. Its length sets the *interest*, not a schedule: the total is `FixedDeposit`'s arithmetic, simple interest over the term, because a rate agreed between two people for an agreed length is the same arrangement as a deposit seen from the other side. **Unless the rate has not been in force the whole time** — one agreed half way through, or added to a debt that never had one, charges the days since it was agreed and not one day more, and the deposit's arithmetic cannot say that: it knows a length and a figure, not when the figure started applying. So a debt with anything in its rate history is charged through the history instead, which splits at each change and returns nothing for the span before the first. The two agree exactly on the ordinary case, a whole-year term at one rate. A null `emi_minor` is load-bearing and must stay null — and it is the *only* test for "this debt has no schedule to disturb". `increaseLoan` asked for a term of zero instead, which is exactly wrong here: agreeing to pay Sita back within a year sets `term_months` and leaves `emi_minor` null by design, so lending her another रू 2,000 was refused in silence — the *More* card took the figure, said nothing, and left the balance where it was. What remains is everything about what is owed: the balance, every payment against it, a lump sum off it, and more borrowed or lent on the same arrangement.

**Every one of those is mirrored for `I lent`, wording included.** Money the user gave someone is an *amount lent*, not a loan amount; a payment against it is *received on*, not paid on; and a preview saying "you would owe" is the wrong way round when they are the ones repaying. The rule for spotting the gaps: any string a person-debt screen reaches whose words assume the money was borrowed needs an `_lent` counterpart, and the ones that do not — "Payment", "How much?", "See every payment" — are the ones worth leaving shared.

**What it is and when it started read as one line.** On a debt already on file the day it changed hands is settled text beside "A person · I borrowed", where the name and the amount pair below it — a disabled box further down spent a whole line on a date nobody could type into.

**The one date it asks for is the day the money changed hands** — `disbursed_on`, drawn as "Money borrowed date" or "Money lent date". It is the date **every interest figure is counted from**: it goes into the `min` that sets `started_on`, and `meteredInterest` runs day by day from there to today, so a debt written down months late is charged for the months it actually ran. Where a length was agreed, the day it is owed back falls out of the two facts already given — start plus term, shown in the card and never stored.

It replaced a "clear it by" field, and that was the wrong end of the arrangement: nobody fills in a date they have not agreed, nothing could be measured from it, and the one date both sides do remember went unrecorded. `due_on` itself survives untouched — an older debt that has one keeps its one-occurrence rule, and the form simply carries the stored value through — but nothing new writes one, so a personal loan created now has no series at all.

**Money between people moves twice, in opposite directions, and usually through two different accounts.** So the form asks both: `disbursed_account_id` ("Money received on" when borrowing, "Money paid from" when lending) is where the money itself went on the day it moved, and `pay_from_account_id` ("Money pay from" / "Money receive on") is where the repayments go from here on. Every one of those labels leads with **Money** deliberately: a heading of two prepositions ("Received on", "Pay from") reads as a date until you have read the chips underneath it. The second was the only one asked for a long time, and it left the user recording the same movement twice — once as the debt, once by hand. A bank loan is asked the same pair, in the same words and with the same defaults; the rules below hold for both.

Answering the first writes an ordinary `money_entry`: an **adjustment**, `IN` for borrowed and `OUT` for lent, dated the day it moved, carrying `loan_id` and no `loan_part` — the same shape `increaseLoan` writes, which is what makes the ledger read it as the debt's opening movement and the interest meter walk back through it. `LoanMovementKind.OPENING` tells it from a genuine top-up (told apart by the derived id, never by shape): calling the borrowing itself "Borrowed more" reads as a debt that has already grown, and it would be counted into "so much more borrowed since it started". The timeline has to make the same distinction and does it the same way — `MoneyEntry.isLoanOpening` off `LOAN_DISBURSEMENT_SUFFIX`, tested *before* `isLoanIncrease`, which the opening also satisfies — because a row and the statement it appears in must not call one movement two different things.

Three rules hold it together:

- **Written once, on the way in.** A lump sum rewrites `principal_minor` in place, so re-deriving the movement from the form on a later save would restate what changed hands as whatever is owed today. The field is settled text once the debt exists, for the same reason.
- **Optional, and blank is a real answer** — offered as a "Not recorded" chip rather than a hidden second tap on the selected one. A debt written down months after it moved sits against a balance the user has already corrected by hand, and crediting it again would double it.
- **It may name an account for a day before the app was told about the loan**, which is the deliberate exception to the rule below. That rule is about rows the app generates *for* the user from a schedule; this one is the user answering "where did it go", on a field they leave blank precisely when the balance already accounts for it.

It is also the account more of the same arrangement moves through: the *More* card defaults to it before `pay_from_account_id`, because another रू 2,000 lent leaves the account the first रू 8,000 left, not the one their repayments arrive in.

**What the editor offers is a pair of buttons, and they are deliberately not blue.** `HoldingActionsCard` draws one per thing a holding can have done to it — Payment and Borrow more, Payment and Lend more, Deposit and Withdraw — the leading one filled and the rest outlined, since on every holding here the first is the act money usually moves by and two filled buttons of equal weight would make "Borrow more" as likely a tap as "Payment". Both take the theme's **secondary**: Save is the one filled *primary* button on the form and it sits an inch below them, so a filled blue offer that only opens a sheet was a coin toss for the thumb — and the outlined one takes the same colour, or the pair reads as two unrelated controls. Each carries its own mark ahead of the words (`Payments` for a payment, a plus for more of the same arrangement, the app's own in/out arrows on a goal), which is what tells two same-shaped buttons apart before either is read. The plus is the same for borrowing more and lending more, because that is one arrangement growing and an arrow would have to point two ways to say it.

**And every box that names an amount refuses the decimals the currency has not got** (`amountInput`, the holding editor's own). `MoneyFormatter.parse` has always truncated them on the way to a `Money`, so "15000.999999999" was already worth रू 15,000.99 to everything downstream — including the ceiling a payment is clamped to, which is how a figure over the limit could sit in a box looking accepted. Two places for most currencies and three for the Gulf dinars, taken from `MoneyFormatter.minorUnits` rather than assumed. Only the fraction is touched: a trailing ".", a lone separator and the whole part are all somebody mid-figure, and a box that tidied those under the caret would be unusable.

**A payment says what it was about, and that is never its title.** Every movement a debt's own card writes — a payment, more borrowed, more lent — takes an optional **Note (optional)** under the amount, because three payments to the same person are otherwise three identical rows and the only thing that tells them apart is what the two of them said at the time. Where it goes is the whole of the design: the row's title stays the **debt** on every one of them, and the note joins the line underneath, on the end of what the payment did — "Dad" over "Borrowed more - school fee". A note that took the title would leave a reader who has three arrangements working out which of them "school fee" moved, and the app's own word for the movement is the one that is always there and always means the same thing, so it leads and the note qualifies it. The hyphen is deliberate where the rest of that line is interpuncts (`loan_movement_with_note`): it says one phrase and its qualifier rather than one more fact beside the account and the debt. Stored in the entry's own `note`, in place of the debt's name — which is what these rows have always carried when nothing is said, and what `MoneyEntry.ownNote` still reads as "the app wrote this, not the user", so blank changes nothing anywhere. One sentence, said in one place (`loanMovementLabel`) and read by all four lists that draw such a row — Home, the Timeline, Reminders and an account's statement, which grew the line it never had — with the debt's own ledger joining its note to the kind the same way rather than printing it on a line of its own. Offered on every debt for the reason the cards themselves are shared: a form that behaved one way on money with a person and another on a bank's would be two forms wearing one shape.

**And a payment is called a Payment**, on every debt and in both directions, which is the word on the button that recorded it (`prepay_title`, the same string the card's own title is drawn from). It read "Off the balance" and "Off what they owe" — words that describe what the money did to the balance rather than what the user did, and that nobody had seen on the screen where they did it, since the card, its title and its button all say Payment. **An instalment is an "EMI Instalment"** for the same reason, in one string (`loan_movement_instalment`) that the row on Home, the Timeline and Reminders shares with the kind on the debt's own statement: it was "Loan payment" on the three lists and "Instalment" on the ledger, which is one payment wearing two names two taps apart. Both places that name a movement read the same rule — `loanMovementLabel` and the ledger's own `labelRes` — and the ledger takes the whole `LoanKind` rather than an `isOverdraft` flag, a drawdown being the one increase still named for the facility it came out of.

**A card that acts in place says what it did.** Every card on the holding editor — a payment, more borrowed, money into or out of a goal — acts and then reads the holding back rather than closing. The cost is a page that rearranges itself under the thumb: the preview and the two option buttons vanish, the card shrinks, and the only evidence is a figure further up that the eye was not on. It read as the screen glitching. `HoldingMessage` is a resource and its arguments — never a finished string, since the words belong to whichever language the screen is being read in — shown in a snackbar that says what moved and what it left ("रू 300 paid — रू 700 left to pay") and goes away on its own. It is cleared *after* it has been seen: clearing first changes the key the effect runs on and cancels the snackbar in the frame it appeared.

**Recording a payment does not close the form.** Both cards read the loan back and empty their own box instead: what the user wants next is the balance the payment produced, and it is on this screen — being thrown out to the accounts list meant tapping back in to see whether it had worked. The preview above the button cancels its predecessor (`previewJob`), because each keystroke asks the repository a fresh question and the slower answer for "1" was landing on top of the one for "1000", promising a balance रू 999 away from what the button would produce.

**Which account a payment moves through is a question about that payment, so it is asked inside the card that is about to make one.** *Pay off a lump sum* carries its own "from", *More* its own "into", each starting at the loan's own account and each opening the choice only when tapped. Neither is written back to the loan and neither touches a row already recorded: a debt usually repaid from the bank can still be paid down once in cash, and saying so must not restate where the earlier payments came from. The next movement starts from the loan's account again.

That is why a debt already on file has **no account section of its own**, whatever kind it is — every movement the form can still make carries one, and a settled line repeating the answer above them was one more thing to read and nothing to do. Between people the account is optional on both sides (`payFromOptional`), preselected on neither, since plenty of money between people is cash, and `applyPrepayment`/`increaseLoan` therefore take the account **exactly as the caller names it**, with no fall back to the loan's own — a lump sum handed over in cash must not quietly debit the account the instalments come from. A null account still writes the entry, so the ledger shows the payment, and neither of them falls back to the loan's own account. **Nothing in the app records interest serviced on its own any more**; `LoanPart.INTEREST` is written only by the broken-period charge. If that is wanted back it is a card on the debt's own form, beside the lump sum, and not a question on the money-in form.

One wording for the same card wherever it appears: an overdraft's repayment box and a term loan's lump sum are the same act, so both say **Payment** and **How much?**, and what is owed is **To pay** — **To receive** where the money is coming back. The account those payments leave is **Money pay from** on both, for the same reason: "Repay from" over a facility and "Money pay from" over a schedule asked the reader to notice a difference that is not there. And an overdraft's ceiling is the **Approved amount limit** — the bank set it, not the borrower, and the bare word "Amount" beside a name was the one thing on that line saying nothing about itself; what it has actually taken is on the card underneath, which says "drawn so far" in those words.

**Where one figure has to stand for a debt, it is what would clear it today.** `Loan.settleToday` is the balance plus the interest metered on it, and the Accounts row, the "owed"/"owed to you" totals and net worth all use it — a total that leaves out interest already run is the one figure the user cannot act on. The row says what is inside it ("incl. रू 2,904.11 interest") in place of "of रू 1,00,000", because a current figure that has grown past what was borrowed reads as an error rather than as a debt costing money. Identical to the balance on anything with a schedule, where the interest lives inside the instalments and metering it again would count it twice. Two lines still beat one wherever there is room for two — see the card below, which keeps them apart.

**One card, and it leads with the figure they shook on.** "You pay back in total" sat directly above "What you owe" with the same number in both until something had been repaid, so they are one card: the agreed total leads where there is one, what is left of it is the line underneath, and the metered interest is withheld while a total is showing — a length turns the debt into simple interest over that length and the meter stops. The way into the statement lives in that card too, and only when `hasMovements`: a debt between people is entered long before the first repayment, and a button that opens an empty page reads as the app having lost them.

**A length between people stays editable.** There is no schedule for it to rewrite — it sets the interest and the day it is wanted back, both of which two people move between themselves — and it is so often left blank at first that a settled box read as the bare word "Months" with nothing in front of it. The rate's "when did it change" question is asked with a person's words there too: no bank moved it, the two of them agreed something else.

### Insurance

`AccountKind.INSURANCE` is a policy: premiums going out for an agreed length, one payout at the end. It is an **account and not a debt** — the premiums paid into it are still the user's money — and it is its own kind for the reasons a deposit is: nothing may be spent from it, nothing paid into it by hand, and on one known day the whole of it moves. It sits in `HoldingGroup.INSURANCE`, after *A person*, and cannot be changed into anything else.

**Both figures are asked for, and neither is derived from the other.** An endowment hands back more than the premiums and a term plan hands back nothing, and the split between them is the insurer's business — not a rate the user could type in. Dividing the maturity amount by the number of payments would quote a premium that disagrees with the policy document, which is the one thing a policyholder has to check the app against. So `maturity_amount_minor` and `premium_minor` are two facts off the certificate, and `Insurance` computes only what falls out of them: how many premiums there are, when each falls, and what they come to in all.

**The number of premiums is counted, not divided.** `(termMonths - 1) / everyMonths + 1`, because the first premium falls on the day the policy is taken out — an insurer takes one to put the policy on risk — and the last one whole gap before it matures. A twenty-year policy paid yearly has twenty premiums, and one agreed for eighteen months has a second at twelve: dividing the two lengths drops it, and the app quietly stops paying a policy still in force.

**"How long?" and the maturity date are one answer with two faces**, and each sets the other — a policyholder knows one or the other depending on which document is in front of them. The length is the fact stored, so the date snaps to a whole month; nothing is written down twice.

**Each premium is a transfer, not spending.** The rule is an ordinary `recurring_series` carrying `transfer_to_account_id` pointed at the policy, so the schedule needs no machinery of its own: dates that have arrived are already real rows, dates still to come are projected from the same rule, and editing the policy corrects both. The money leaves the bank and lands in the policy — it has not gone anywhere, and a month with a premium in it must not read as an expensive one. That is also why the policy's balance needs no special case: it is the ordinary sum of the rows that name it, which is exactly "the premiums paid so far".

**A row never says only "Transfer".** One end of a plan's transfer can be unknown — a payment dated before the rule was written names no account on the paying side — and `transferRoute` then draws the end it does know, "→ Nepal Life Endowment". It used to fall back to the bare word, which is the one thing a row must not say: every transfer says it, so a premium the user went looking for in the timeline was indistinguishable from anything else that had moved.

**A premium from before the app was told about the policy still lands in it.** This is the one exception to *an occurrence dated before its rule was written names no account*, and it is a narrow one: the account the money left has a balance the user has since corrected by hand, so debiting it again would subtract the same payment twice — but the policy is a holding the app opened itself and is the only bookkeeper for, with no way to correct it by hand, so crediting it is not double-counting, it is the only counting there is. A goal is the same and is in the same list (`PLANS`). `TransferRecorder.record` takes `debitsSource`/`creditsDestination` for exactly this, and `materialiseDue` withholds only the paying side.

**The card says what the arrangement is worth, once.** `Insurance.Terms.gain` is
the payout less every premium put in, and it is the only figure on the form that
is neither typed in nor printed on the certificate — the premium, the count and
the total were all there and the one question a policy is bought on was left for
the reader to do in their head, a hundred and twenty premiums apart. It has to be
able to say **less** as well as more: a term plan pays out nothing, and a line
that could only read "more" would describe every policy as an investment. A goal
has no such line, because a goal hands back exactly what was put into it.

**Maturity is a forecast and is never written down** — `MaturityRepository` (which serves the deposit's maturity and a goal's target day too, all being the same shape: a figure, a date, and somewhere it goes). Nothing materialises when the day arrives, for the reason a deposit's payout does not: an automatic credit is the one thing that can make the money vanish. The forward balance is that one day and not a sum — a policy holds its premiums until the payout falls inside the window and nothing from then on, because what leaves is the sum assured and only the premiums were ever in there.

**A policy and a goal say their own name inside "What is it?"** — "Goal · New Bike", "Insurance · Nepal Life" — and have no name field underneath, which was the same words a second time on consecutive lines. A policy's payout is settled beside it, where it reads as one of the two facts off the certificate rather than as the single live box on a page of settled ones. **How long? and Pay every? pair on one line** on both, in that order: the length is the arrangement and the rhythm is how it is met. A policy opens on Years, like every other arrangement a bank or an insurer agrees.

**A goal's transactions are reached from its own card.** The statement card underneath led with the balance again, under a second heading, an inch below the one the progress card opens with — the same figure twice, inviting the reader to look for the difference. What it had that the progress card did not was the way to the rows, so that is what moved into it.

**A policy's name stays editable, and its terms do not.** The name is a label its owner chose, like a bank holding's own name, and renaming it rewrites nothing. The premium, how often it falls, the day it started and how long it runs are the insurer's and are settled text once the policy exists — changing one would rewrite premiums already paid. What stays live besides the name is the maturity amount, which no schedule was ever computed from, and where the payout lands.

A policy is at **no bank**: its name is the policy's, and a heading made of it would promise other holdings at an insurer the user never named. So it groups with cash and wallets under *Other*, is in no list on the money in/out form or at either end of a transfer, has no "correct this balance" pencil, and is never offered as a bank name or as one of a bank's tabs.

### Goals

`AccountKind.GOAL` is money put aside on purpose: a figure to reach, and a rhythm that reaches it. It is the mirror of a policy and runs on exactly the same machinery — a rule that moves money into it, one day on which it comes back out — which is why `PlanRepository` saves both and `PeriodicPlan` counts the dates for both. **The difference is which figure is given and which is worked out.** A policy is told what each premium costs; a goal is told only what it is for, and the app divides.

**The contribution rounds up.** रू 1,00,000 over twelve months is रू 8,333.33, and twelve of those leave the user four paisa short of the thing they were saving for. Rounding up overshoots by less than a minor unit per payment and reaches the goal, which is the direction that cannot disappoint — and what the plan actually comes to is stated in full on the card, so the few paisa are never a surprise. It is stored (`premium_minor`) rather than re-divided on every read, because the rule that moves the money was written from it.

**Nothing about a goal is invented.** No interest, no return, no growth: a goal holds exactly what has been put into it, which is what makes the progress bar a fact rather than a forecast. For the same reason **its payout is what will actually be in it** — what it holds today plus the contributions still to come — and not the target. Promising the target regardless would have the forecast credit an account with money nobody put aside.

**The target is settled once the goal exists**, unlike a policy's maturity amount. Every other figure is computed from it, so changing it would restate what the contributions already made were meant to be — and a bar measured against a target that moved is not progress. What stays live is the name, the colour, and where the money lands at the end.

**What to save each time is not asked for.** The form asks the target, the length and the rhythm; the contribution is divided out of them and drawn on the card, in the slot where it used to be a box. It *was* one — the other side of the rhythm, each setting the other (`Goal.everyMonthsFor`), so somebody who knew they could spare रू 5,000 a time could type that and have the rhythm follow, and a typed figure snapped to what its nearest rhythm actually produces when the box lost focus. What it cost was the same number twice on one screen under the same words: a box reading रू 8,334 with a card three inches below reading रू 8,334, and nothing saying which of them was the answer. The card is the one that can also say how many payments there are and the day they reach the target, so the card is the one that stayed — moved up under the two boxes it is divided out of, above the start date, rather than left at the foot of the form. `Goal.everyMonthsFor` stays where it is, tested and unused: it is pure, and the question it answers may well be asked again.

**And the day the money lands is the last thing on a form the user came back to.** A deposit's maturity, a policy's payout and a goal's target all ask where the whole of it goes, in one shared row (`LandsInSection`). While the holding is being written down it sits among the answers being given; once it exists it is the only answer on the form still worth changing — everything above it is settled text and everything below it is a card of figures — so it drops to the end, against the colour picker.

**Money in or out is the one thing that moves the length.** *Deposit* and *Withdraw* are the goal's version of a debt's payment card — an amount, a day, the account it moves through — and both write an ordinary transfer. What they change besides the balance is `deposit_term_months`: the saving each time is what the user committed to, so putting money in early means fewer contributions are left and the goal arrives sooner (`Goal.termAfter`), and taking money out pushes it away. The rule's end date moves with the term so no contribution falls after the goal has been reached; its amount and rhythm are never restated.

**And that card is the way money reaches one.** A goal was offered on the entry form beside the accounts for a while, on the reasoning that a goal is money the user puts aside when they have it; it went when the whole of that second row went — see *The forms*. Nothing about how a goal holds money changed with it: an entry naming one is still an ordinary entry, its balance is still the sum of the rows that name it, and an entry already filed against a goal still opens with the goal shown.

**So the length is worked out again wherever the balance moves**, and `GoalTermKeeper` is the one place that does it: `saveEntry`, `saveTransfer`, `deleteEntry`, `undoDeleteEntry` and the debt movements the entry form makes all reach it, as well as the card itself. **The delete matters as much as the save** — a contribution added and taken back left the goal shortened for good, promising a day the saving had not reached. It is a class of its own, small as it is, because `PlanRepository` depends on `WalletRepository` and the ordinary movements live in the second: two copies of this arithmetic would leave a bar disagreeing with the day printed beside it.

It is deliberately a **re-derivation and not a restore**: the length is a function of what is in the goal, not a figure remembered from before the last movement. So a goal whose stored term does not match what `termAfter` would say for its balance — which is any goal created before it was first moved, `perPayment` having been rounded up on the way in — settles onto the derived figure the first time anything touches it, and stays self-consistent from then on. Two paths to the same balance now give the same term, which is what the bar is measured against.

**A goal is drawn, not described** — **and so is everything else with an end to reach** (`HoldingProgress`). Two figures and a date are a sentence to be read; a bar is the one thing on the Accounts page that can be understood without reading, which is the whole point of setting a goal rather than simply having savings — and just as true of a debt being paid off, a policy being paid up, a deposit running down its term and a card filling towards its ceiling, every one of which was a row of digits the reader had to do arithmetic on. **What "along" means is the arrangement's own question**, and the answers are not all one shape: a goal is money towards a target; a policy is premiums handed over out of all of them (deliberately not the payout, which is the insurer's money arriving whole on one day, and a bar creeping towards it would draw the premiums as though they were growing into it); a **deposit is the term**, since nothing about its money moves until the day it comes free; a debt is what is *cleared*, measured against `borrowedInAll` rather than the balance, because `principal_minor` is rewritten in place by a lump sum and a bar measured against it would jump back to empty the day somebody paid a chunk off; and a **card is the odd one and fills as the headroom is spent**, because a borrower's question about a card is how much of the ceiling is gone. The interest metered on top is left out of the debt's: it is not principal, it grows every day the debt sits, and a bar running backwards on a debt nobody had touched would say the borrower was losing ground by doing nothing. **Null is a real answer and is not zero** — a card whose limit was never recorded, a debt from before the column that records what was advanced — and nothing is drawn at all, because an empty bar there states a fact nobody knows. Each is in the **holding's own colour**, the one it is known by everywhere else; a debt with no colour column takes the ink its figure is already printed in. The row carries the bar full width under it, a goal with "of रू 1,50,000" beside the balance, and the editor leads with a card — put aside so far, the bar, how far along, what is left, and the day it is due. That card is why the statement card below it drops its own headline figure on a goal: the same balance under two names in two headlines invited the reader to look for the difference.

Goals, policies and wallets each get a **section of their own** on the Accounts page rather than sitting in *Other*. A goal or a policy is an arrangement, not a place, and one alongside a cash tin reads as somewhere money happens to be rather than something the user set up on purpose; a wallet *is* a place — eSewa and Khalti hold money as a bank does — and only fell in with the cash because it has one holding each and so no name to head a section with. Those are the headings the app writes itself, which is what `AccountGroup.titleRes` is for — and under one, a row drops the kind from its subtext (`saysKind`), because the heading has just said it. What is left under *Other* is the cash, which is the money that really is nowhere in particular.

### Overdrafts and credit cards

**One product under two names.** A credit card and an overdraft are the same arrangement — an approved ceiling, money drawn against it, interest on what is actually drawn — so the kind wears both words (`accounts_kind_overdraft`, "Credit card / Overdraft") rather than the app growing a second kind that does identical arithmetic. Nothing behind the label changed, and the enum keeps its own name: renaming a stored value is a migration for the sake of a word.

**A card is spent from, and it is offered where money is spent from.** It appears in the money form's "Paid from" row and at the paying end of a transfer, each chip carrying what it has left to draw — the figure that decides whether the purchase being typed is possible at all, said before the save rather than in the refusal afterwards. This is the one debt back in that row, and narrowly: a term loan is repaid, never spent from, and a card cannot receive income. It is the only exception to *money against a debt is made on the debt's own screen*, because on a card the purchase **is** how the money leaves — recording it as a drawdown there and again as spending here was two entries for one act.

**A purchase is spending and a balance going up at the same time**, which nothing else in the app is (`LoanMovementKind.SPEND`, `LoanRepository.spendOnCard`). रू 2,000 of groceries on a रू 50,000 card counts as रू 2,000 spent that day, leaves रू 48,000 to draw, and starts metering interest on the रू 2,000 from today — the same day-by-day meter a drawdown starts, since it is the same drawn balance. A **drawdown** stays an adjustment and is what a transfer *out of* a card writes: there the money arrived somewhere, so a month lived on the card must not read as expensive until it is actually spent.

**Its price is that settling a card counts as nothing**, and that is not optional. Every rupee was already counted on the day it was spent, so counting the bill as well would say a रू 2,000 bag of groceries cost रू 4,000 — `repayOverdraft` therefore writes an adjustment. A term loan is the opposite and unaffected: nothing was counted when the money was borrowed, so its repayment is where the spending is recognised.

**It is told from everything else by its shape**, not by a new column (`MoneyEntryEntity.isCardSpend`): money out, against a facility, naming no account and no rule, and not an adjustment. Nothing else writes that. A new `LoanPart` value would have been plainer, but an older build restoring the backup could not parse one — and this row has to be readable by every version that can open the file. The rule is mirrored in SQL by `LoanDao.balanceChanges`, which needs the same verdict to give the row the sign its direction alone would get wrong; `is_adjustment = 0` is what keeps money lent on an existing arrangement, also OUT with no account, out of that branch. The two are one rule and have to move together.

**A payment box is capped at what is owed, as the digits are typed.** A payment larger than the debt is not a payment, it is a typo — and a silent one, because `applyPrepayment` clamps what it *writes* while the box goes on showing the figure that was typed. So the box is clamped instead: somebody who means to settle a card taps a long run of nines and gets exactly what settling it costs, interest and all (`maxPayable`, which is `Loan.settleToday`). The same rule caps a goal's Deposit at what is left to reach it and its Withdraw at what it holds. Half-typed input is left alone — a lone "." is somebody mid-figure, and a box that rewrote itself under the caret would be unusable.

**A card carries a colour of its own** (`loan.color_argb`, added by `MIGRATION_29_30`). Every other debt has none and keeps what a debt has always had: the colour of its own figure, red owing and green owed to you — right for something that is only ever a balance to look at. A card is not. It sits among the accounts on the money form, it is paid with, and the rows it produces are read down the same lists theirs are, so it is found the way an account is found. The column is on `loan` rather than on cards alone, because it costs nothing on the debts that never use it and a second migration to widen it later would cost a version; only the card's form asks. The breakdown coalesces the two, and `BackupFormatTest` is what caught the field missing from the backup before it shipped.

**Refused above the limit rather than clamped.** A purchase the card would have declined is not a purchase, and writing a smaller one silently would be the app deciding what the user bought. The message goes under the amount, because the answer is a smaller figure.

`LoanKind.OVERDRAFT` is the bank's third product, and the one place a loan needs **two** figures rather than one: `credit_limit_minor` is what the bank approved and `principal_minor` is what has actually been drawn. Conflating them would open every overdraft owing its full limit on the day it was created, so `saveLoan` writes the limit from the form and leaves the balance alone — editing the ceiling must never rewrite the debt.

Everything schedule-shaped is absent by construction: no series is written, no instalment, no style, no due date. Nothing is owed on any date until money is taken, so a projected payment would be the app inventing a debt. The form hides all of it and offers a limit, a rate, a duration and a box to pay back what is drawn.

Two operations move the balance, and both are ordinary `money_entry` rows:

- **Drawing** (`drawFromOverdraft`) raises `principal_minor` and writes an `IN` **adjustment** into a real account. Borrowing is not earning — a month spent living on the overdraft must not read as a good one. Refused above the limit, in the view model as well as the repository, so the user is told which field is wrong instead of watching Save do nothing.
- **Repaying** routes through `applyPrepayment`, which short-circuits for an overdraft: the money leaving is spending, the balance falls, and nothing is re-based because there was never a schedule.

Both are made on the overdraft's own screen. The entry form offered a drawdown for a while, as a transfer out of the facility, and the whole of that second row is gone — see *The forms*. Drawdowns already recorded still open there and are still shown as what they were: a drawdown is borrowing rather than income, so it reopens with no repeat (`isExistingDrawdown`), and the account it came from is stated rather than asked.

**An overdraft with nothing drawn owes nothing, and the form says so.** The approved limit sits beside the name as settled text — the bank sets it, not the borrower, and a box invited typing into the one figure on the screen the user has no say over. "Pay it back" is absent until there is a balance to pay, and editing the rate asks *when* only once money has actually been taken: with nothing drawn there is no interest for a date to split, and the new figure is simply what the facility charges from now on.

### One bank, several holdings

A savings account, a term loan and an overdraft at the same bank are three rows sharing one name. The form offers the banks already on file **under the name field as it is typed** (`BankNameField`), so the name is typed once and therefore spelled the same way in every list — see `ui/Naming.kt`, the one place the words for a kind are written. They were a row of chips *above* the field, which is the answers before the question: the row took a line of the form whether or not it was wanted and wrapped to three on a phone with several banks, pushing the box it was there to help off the screen. Under the field, on focus, is where a suggestion belongs — it costs nothing until the field is being filled in, and it narrows to what has been typed. A name that has been reached is no longer a suggestion, so an exact match drops out of the list: that is also what closes it after a tap, rather than anything doing it by hand.

**And the list is part of the form, not a menu floating over it.** As a popup it was silenced by the *second* tap on the box — which is what anybody does once the keyboard has slid up under their thumb: a popup counts a touch on its own anchor as a dismissal, focus never leaves, and nothing puts the list back but typing another character. Neither hook can hear that tap either, because an editable anchor reports nothing when it is tapped — the whole point of an editable anchor type is that a tap on it asks for the keyboard rather than for the list. So the suggestions were gone for the rest of the form's life, on a phone where a second tap is ordinary and not on an emulator driven one tap at a time. Drawn in the column there is no popup to dismiss and no "has the user waved it away" flag to get wrong: the list is on screen exactly while the field has focus and has something to offer, and it shows at most `MAX_BANK_SUGGESTIONS` of them so a dozen banks cannot push the rest of the form off the screen.

**A provider's wallets are the same shape, and are told apart by what they hold.** One provider holds a wallet per currency — Wise in dollars and Wise in euros — which is the same arrangement as a bank holding a savings account and a loan, so it takes the same machinery: the name field suggests the wallets already on file (`nameSuggestions`, which is `knownBanks` for a bank and `knownWallets` for a wallet), and editing one draws the row of tabs. **The tab says the currency and not the kind**, because "Wallet" is the same word on every one of them and a word repeated across a row distinguishes nothing — that is the same rule the bank tabs reach for when two of a bank's holdings would wear one word, arrived at first here rather than last, there being no second word to try. `HoldingTab.literal` carries it.

**And one provider holds one wallet per currency.** A second Wise in dollars is not a second wallet — it is the one already on file, entered twice, and nothing downstream could tell them apart: both rows read "Wise · USD" on the accounts page, both chips read "Wise (USD)" on the money form, and the tabs on either would offer two chips saying "USD". So the save is refused, and the refusal is said **under the currency chips**, because that is where the answer is — another currency, or the wallet they already have, whose balance is corrected rather than duplicated. Wallets only: a bank really can hold two savings accounts in one currency, and it has the optional name field to tell them apart with.

**The two families never mix.** A wallet named after a bank is not one of that bank's holdings, exactly as a goal called "Nabil" is not — so `walletTabs` is its own function and the wallet names are their own list, rather than the bank filters being relaxed. Everything downstream already distinguishes them: `holdingDisplayName` appends the currency to every holding it names, so a chip, a timeline row and a breakdown slice all read "Wise (USD)"; and on the Accounts page the wallets sit under their own heading with the currency on the second line, which is where a row's facts already go.

**The bank is the unit, not the holding.** The accounts list says the name once as a heading and each row underneath says only what it *is* — "Savings", "Fixed deposit", "Loan" — because a name repeated four times down a column distinguishes nothing.

**Where "what it is" is not enough, the user names it.** Two deposits at one bank are two rows both reading "Fixed deposit", and only their owner knows which is the one for the house — so every bank holding takes an optional **Name (optional)**, shown as "House FD". This is the *original* meaning of the two name columns, put back: `institution` (`lender` on a debt) is the bank, `name` is what this one is called. Where no name is given the bank goes in both, so everything that prints a name still prints one, and `ownName` — which compares the two, case-insensitively — reads that as "unnamed" and falls back to the kind. Null on money between people whatever their columns hold: a few old rows carry a lender as well, and reading that as a bank would turn a friend's name into a heading. `holdingLabel` shows the name **or** the kind and never both — a user who names an account has said what to call it, and "Dollar Account Savings" answers a question they already answered. What kind it is moves to the line underneath, which is where the currency and the rest of the row's facts already are; that line therefore says the kind whenever the title did not. `accountLabel`, which names the holding a movement passed through, reads the two columns the same way round — "Dollar Account - Global IME Bank", or simply "Nabil Bank" where there is no name of its own rather than the "Nabil Bank Nabil Bank" that joining two equal columns produced. The name is editable for good — it is a label the user chose, not a fact about the money, so nothing is rewritten by changing it. `AccountGroup` carries the bank's accounts *and* its debts, so an overdraft sits with the current account it backs rather than in a section two screens down; only money with a person is left to "What you owe" and "Owed to you", having no bank to sit under. Grouped case-insensitively (`institution ?: name`, lowercased) so "Nabil Bank" and "Nabil bank" are one relationship, and displayed in whichever spelling was typed first.

**The heading carries no figure.** A bank's holdings run in both directions — a deposit is money, a loan is a debt — so one number over them could only be a subtraction nobody asked for. The subtotal that used to sit there was summed from accounts alone, which stopped being the whole of the group the moment the debts moved into it.

**The name is a title and the holdings are a card.** A grey 11sp caption over loose rows did not read as a parent at all — the rows below it looked like the rows above it. The name takes `TitleStyle`, the group is one list item drawing its own rounded surface, and the rows inside are separated by hairlines. That is why the group is a single `item` rather than a heading followed by `items`: a card cannot be built out of separate list items, and a bank holds a handful of things, so nothing is lost by drawing them together.

Two details keep the rows one shape. **Every row starts with a dot**, debts included — they have no colour column of their own, so they take the colour their figure is already printed in (red owing, green owed to you). And **nothing sits past the figure**: every row ends at the same edge, because what used to be there — a pencil for "correct this balance" — is a gesture now.

**And every list that removes a movement says so afterwards.** The timeline, the accounts list, an account's statement and a debt's own all end a delete with the same one-word snackbar. The two statements were silent, which on a page that rearranges under the thumb read as the app having glitched rather than as the gesture landing — a debt's ledger counts its deletes (`deletedCount`) rather than flagging them, since two in a row are two things to report and a flag already true the second time would say nothing.

**Every one of those is said at the *top* of the page** (`TopSnackbar`). Material puts a snackbar at the bottom, and on this app that is the one place it cannot go: the foot of every tab is a navigation bar with the floating button standing on it, so "Deleted" arrived under the reader's own thumb and on top of the control they had just used — and the add menu opening six options tall shot it halfway up the page, which is the whole reason `AddHoldingMenu` had to be given zero height. A message about a row being read also has no business at the far end of the page from that row. At the top it is clear of the thumb, the button and the menu, and it lands in the corner the eye already goes to for the month. It is drawn **over** the page rather than in the `Scaffold`'s snackbar slot, because that slot is positioned from the bottom edge — a host told to fill the height is placed at `layoutHeight - itsOwnHeight - bottomBar`, which puts it off the top of the screen by the height of the navigation bar. So each screen wraps its own `Scaffold` in a `Box` and hangs the host off the top, which owes nothing to how tall anything else is. Inset by the status bar alone: it floats over a top app bar where there is one, because pushing a page's own title down to make room would move the layout under the reader every time something was said.

**And the two statements offer to undo it now**, as the timeline and Reminders always did — `AccountStatementViewModel.undoDelete` and `LoanLedgerViewModel.undoDelete`, both through the same `WalletRepository.undoDeleteEntry`, so whatever the delete put back on a debt or took off a goal is taken back with the row rather than left behind. Those were the two lists with the snackbar and not the offer, which is exactly the wrong way round: a statement is opened *because* a figure looked wrong, so it is the page a thumb is likeliest to swipe something off by accident, and on a debt's ledger the row it takes moves a balance as well as a list. The accounts list is still deliberately without one — an account takes every movement that ever touched it and five kinds of tombstone with it, and an Undo that had to put all of that back is a promise better not made.

**A row is opened with a tap, corrected with a long press, and removed with a swipe.** The pencil was one more thing drawn on every row and a target the thumb caught on the way to opening the account; the long press does the same job in the same place and needs no column of its own. It is offered on exactly the holdings the pencil was: not on a deposit, a policy or a goal, where what is held is worked out from the terms or put there by a rule, and a correction would be money arriving from nowhere in a holding nothing may be paid into.

**A swipe asks before it deletes, wherever it is offered.** `ConfirmDeleteDialog` is the one question and only the words change: the timeline, an account's statement, a debt's own statement and the accounts list all ask it. It used to be the accounts list alone, on the reasoning that an entry comes back from a snackbar and an account does not — but a swipe is a gesture a thumb makes by accident on a list of somebody's payments, and four seconds of snackbar is not a net a reader who did not notice the row leaving will ever reach for. So the question comes first and the Undo stays as the second net, on the lists that have one. The exception is the tutorial, where the app has just asked for that gesture and a dialog would be the lesson interrupting itself. What the accounts list gains instead is the snackbar it never had: no Undo behind it — an account takes with it every movement that ever touched it — `WalletRepository.deleteAccount` tombstones five things, each of which was a way for a deleted account to go on affecting the figures: every movement naming it *and both halves of its transfers* (half a transfer is money arriving from nowhere); every rule at either end of it, or the next launch materialises another occurrence for a holding that is gone; every rate it was on, which the foreign key would have cascaded had this been a real delete rather than a tombstone; the `matures_into_account_id` pointing at it, deliberately not a foreign key and so nobody else's job to clear; and the pay-from and disbursed columns on any loan that named it — the debt itself stays, since it is owed to a bank and not to an account. Rules are stopped **first**: one stopped after its rows were tombstoned would simply write new ones. A debt swipes away too, through `deleteLoan`, which already knew how.

**A tab switch is not an arrival.** The holding editor is the one destination that navigates to itself, so it draws no transition when it does (`holdingRoute` in the nav graph): the default slide drew both forms at once, one moving across the other, which read as a page having opened on top of a nearly identical page. Arriving from anywhere else keeps the slide. And because the editor's default state is the *create* form, it draws **nothing** until the holding is loaded (`isLoading`) — with no slide to hide it, that frame or two of empty boxes and kind chips was a blink of the wrong screen. The title bar is drawn throughout, so `isEditing` is set from the route before anything is read.

**Inside the editor the same bank is a row of tabs** (`bankTabs`, `showsBankTabs`), in place of the settled "Bank · Savings" and of the name field — the bank's name is the section heading above them. Each tab is a *different form*: tapping one navigates to that holding's own editor, carries nothing across, and its Save writes only that holding. It replaces the current screen rather than stacking on it (`popUpTo(HOLDING_PATTERN) { inclusive = true }`), or five taps between a savings account and its loan would leave five editors to back out through. Built from the **stored** rows, never from the form: the name is editable on some holdings and blank for a moment on others, and tabs that came and went as the user typed would be unusable.

**More than one, or none of it.** A bank with a single holding drew a row of one tab, already selected, directly under its own name — and a lone chip reading "Savings" at the top of a form is not navigation, it is the shape the *create* form uses to ask what a holding is. So it read as a question on the one screen where that question is settled for good, and tapping it did nothing. Withheld, the settled "Bank · Savings" comes back and says the same thing without offering to change it. The same rule `bankTabs` already applied to cash, a wallet and money with a person.

What is left beside the figure is the length, so **"Amount" and "How long?" pair on one line** under the tabs — the two facts a deposit or a term loan is. The boxes further down that would otherwise say the same thing know to stay quiet (`showsBankTabs` guards both the deposit's and the loan's settled term), and what pairs with the rate instead is the *other* half of the same question: "Pay every?" on a loan, the start date on a deposit, "Interest paid every" on a savings or current account. Each row is two facts that are no use apart. The rate history, which used to take that second slot on a savings account, moved under the row and is drawn there for every holding — a list of dated figures reads across the page rather than down half of it, and one shape for all of them beats two.

**One name for a holding, everywhere it is listed** — `holdingDisplayName`, "Demo Bank Savings (NPR)". Three parts, each earning its place: what to call it (the name the user gave *this* holding where there is one, the bank's where there is not — never both, because "Dollar Account - Global IME Bank" spends the width of a row saying it twice); which of the bank's products it is; and what it is denominated in, which is the one fact deciding whether two figures on a page may be added up, in brackets because it is a note about the holding rather than part of its name.

**The kind is said only where it tells two things apart.** One bank name can cover a savings account, a deposit and a current account, and then a row has to say which — but on somebody's *only* account at that bank, "Demo Bank Savings (USD)" is a word distinguishing it from nothing, so it reads "Demo Bank (USD)". Never on a wallet, a cash tin or a person either, each being the only one of itself, and never beside a name the user chose, which has already answered the question. The count reaches the rows as `accountSiblings`, a correlated subquery in the same join that already fetched the name; the entry form counts its own list in memory, since it has the whole of it. Unknown reads as one — a name is never qualified on a guess.

All of it travels on `accountKind`, `accountCurrency` and `accountSiblings` on `MoneyEntry`, `ProjectedEntry` and `HoldingBreakdown`, so the timeline, Home's breakdown, Reminders and the entry form's chips cannot drift apart. The chips in particular: one saying "Demo Bank · NPR" while every row it produced said something else is the same holding wearing two names two taps apart. A **debt** is the exception and is still named by its arrangement (`loanRowLabel`): an instalment names no account by design.

**A settled fact at the top of a form takes the box** (`SettledPair`, `boxed`), **on every holding and not only a bank's**. It was conditional on the tabs being drawn, so a wallet, a cash tin and money with a person all opened on loose prose above a column of fields — and a savings account at a bank with nothing else at it had the same, which made one form look like two depending on what else the user happened to bank there. The box is what says "this is a field, and it is settled"; whether there are sibling holdings has nothing to do with it. The value **wraps to two lines** rather than truncating, because half a phone's width does not hold "A person · I borrowed" and nothing here can be tapped to see the rest; the row is top-aligned so one box growing does not drag its neighbour's label off the line they share. And the "What is it?" eyebrow is gone from an existing holding — the box below carries that label itself, so the heading said the same words twice. Prose under a small label is right in the middle of a card, but the first row of a form is read against the fields under it: plain text starts at the page margin while every box starts inside a border, so the two never line up and the pair reads as though it belongs to something else. The bank's name above them is a `titleLarge` with a rule under it, not another small grey caption — it is what the whole screen is about, and at caption size it read lighter than the list row it was reached from.

Two rules here are easy to break and expensive to get wrong:

1. **Outstanding counts instalments only from `loan.started_on`**, the day the current principal figure was set. A lump sum re-bases the loan (`principal := remaining`) and reuses the *same* series id, so without that cutoff the payments made against the old balance get counted against the new one and the debt reads far too low. `saveLoan` preserves `started_on` (and the editor preserves `emi_starts_on`) on edit for the same reason.
2. **`principal_minor` stops meaning "the sum borrowed" the moment a lump sum lands.** The re-base rewrites it in place, so a debt of रू 1,00,000 with रू 5,000 paid off stores 95,000 and nothing else, and a form labelling that "Loan amount" would tell the borrower they borrowed less than they did — which is one reason a debt between people is asked simply "Amount" on the way in (`accounts_amount`, and the lent side used to say "Amount lent" under a heading already reading "I lent") and states its **Starting amount** afterwards (`HoldingEditorState.amountLabelRes`, which also gives a bank's debt "Loan amount" and a card its approved limit — the chips that answered the question while it was being asked are gone by the time the figure is settled text beside a name). `LoanMath.totalAdvanced` walks it back out of the dated movements — what the balance opened at, plus everything added since — and `Loan.borrowedInAll` carries it for the header and the "of रू 1,00,000" in the list. The additions have to be added back rather than left inside the opening figure, because the debt *arriving* is one of them: a debt whose disbursement was recorded opens at nothing and is made entirely of that first row. The walk-back cannot answer where the balance follows a *schedule*, since instalments cleared principal and the interest inside them together and nothing on file says how each one split — so there the figure is **stored**, in `loan.advanced_minor`: written once on the way in, moved only by more being borrowed on the same arrangement, and never by anything that pays the debt down. Null on every loan from before that column and nothing inferred from a null — a debt already re-based has no honest answer left, and seeding it with today's balance would write the shrunken figure down as the sum the borrower agreed to. Null on an overdraft too, which opens at nothing and shows its approved ceiling instead. The derived answer stays the preferred one wherever it works, because it is recomputed from what is on file and so cannot drift from a movement added or taken back. The editable amount box still holds the current figure, because saving must not put the debt back to what it was before it was paid down.

   **But what the *form* states beside the name is what the debt opened at**, which is a third figure again: `Loan.openedAt`, the same walk stopped one step earlier — the balance before any dated movement, plus the debt's own arrival where that was recorded. Everything borrowed since is deliberately left out, because the aggregate is exactly what "To pay" and "To receive" already say: a debt lent at रू 8,000 and topped up by रू 2,000 read रू 10,000 twice on one screen, and nowhere on it was the sum the two of them shook on. `borrowedInAll` is still what the Accounts row's "of रू 1,00,000" means, which is the other question and the honest answer to it. Null where the balance follows a schedule, for the reason the walk-back is.

**`money_entry.loan_part` is a record, not an input.** It marks payments that were deliberately all principal or all interest. Never subtract those rows from a balance: the principal they cleared is already inside `principal_minor`.

**A lump sum happens on the day it was paid, and so does the re-base.** Both dates that fall out of it are easy to get wrong in the same way, by reaching for today:

- The balance the payment *met* is the balance as it stood on `paidOn` — `outstandingOf(entity, asOf =)`, counting only the instalments up to that day. Reducing today's balance instead applies the payment to a figure the instalments since have already brought down, and counts them twice. `started_on` therefore moves to `paidOn`, so those instalments count again on the correct side of it, and the preview in the form asks the same question of the same day so it cannot promise a balance the save will not produce.
- The instalment **keeps its day of the month**. Restarting the schedule one interval after today moved a loan paid on the 10th to the 30th of every month afterwards, because that happened to be the day the lump sum was paid. The next instalment is `Recurrence.nextAfter(series.start_on, …, paidOn)` — the schedule's own next date.

**A movement can be taken back, and taking it back moves the debt.** Every row
in a debt's statement can be swiped away, the instalments included. The delete
goes through `WalletRepository.deleteEntry` wherever it happens (the timeline, an
account's statement, the debt's own, the entry form), because the row is only
half of what has to be undone:

- **A lump sum, a drawdown, or money lent on an existing arrangement each rewrote
  `principal_minor` in place.** Removing the row without putting the figure back
  left the debt exactly as the payment had made it — the money reappeared in the
  account and stayed off the balance. Four lists could delete such a row and none
  of them knew.
- **An instalment needs nothing put back**, because what is owed on a schedule is
  counted from the periods on file. **Interest serviced on its own** needs
  nothing either: it never moved the balance, which is the point of servicing it.
- **The debt arriving is not a payment against anything.** Deleting it forgets the
  account the money landed in and leaves the debt owed, which is the state of
  every debt whose disbursement was never recorded.

`LoanLedger.kindOf` decides which of those a row is, and it is deliberately the
same function the statement draws from: a row called a lump sum on the screen and
the debt arriving by the delete would put money back on a debt that never lost
it. `MovementReversal` maps the verdict to what has to happen, and both are
tested — the trap being that a repayment on money the user *lent* is an
adjustment **and** comes from the loan's rule, so asking about the adjustment
first would file every one of them as the debt growing.

What follows the balance follows it: the term is worked out again from the
restored figure (the instalment never moves — the same rule a rate change
obeys), the rule's end date moves with the term, a debt due in one go restates
what its single occurrence asks for, and a balance leaving zero reopens a closed
loan. An overdraft is the exception to that last one — nothing drawn is a
facility at rest, not a debt cleared. Undo is the same arithmetic backwards, so a
swipe taken back seconds later leaves the debt where it started.

**One lump sum cannot be removed while a later one is on file**, on a debt that
amortises. Each one re-based the loan on the balance it met, so the balances
after it were worked out from the reduced figure; putting the money back on
today's balance would be adding it at the wrong date and forgiving the interest
the instalments since charged on it. The user is told to take the later payment
first (`Reversal.LaterPaymentFirst`, one dialog for all four lists) rather than
handed a debt that is a few thousand rupees out. Order never matters on a running
total, so nothing else is refused.

**A deleted instalment is money that is late, not money that is gone**, and the *next* scheduled payment collects it. रू 10,000 swiped out of July leaves August asking for रू 20,000; swipe August away too and September asks for रू 30,000. The period itself still charged its days and cleared no principal, so the balance stands exactly where the payment before it left it and the catch-up payment settles two periods of interest — which makes the loan cost slightly *more* over its life, and is the whole point of not forgiving it.

**So the schedule is counted in periods and not in payments.** They were the same number until a row could be deleted, and `Loan.paymentsMade` is now how many of the schedule's rows are behind us — read from the **rule's own dates** rather than from the rows, because counting the rows drops the whole schedule back a month and draws the next instalment on a date that has already gone. `Arrears.of` puts the two together: the *count* of surviving payments decides how many periods are missing, and the *days* they sit on decide which. They disagree whenever an instalment's date was corrected by a day or two, and trusting the days alone would tell somebody who paid two days late that they owed double next month.

**A missed period is permanent, and that is why the set is carried rather than a count.** Once August's रू 20,000 has been paid nothing is owed any more, but July is still a period that charged interest and collected nothing — a balance recomputed as though it had never happened is a few rupees light for the rest of the loan. Nothing is written down for this: a scheduled date whose only row is a tombstone *is* the record, so it survives a restore. `LoanMath.schedule` takes the set and draws each of them as a row of zeroes — a row, not a gap, because every caller indexes these by position; `LoanLedger` walks past them for the same reason, or every balance below a deleted instalment would be a month out.

**Three places have to agree to the paisa**, and they read the one rule: the remaining-payments table, the row the timeline projects for a date still to come (`projectForward`, on the **first** future date and no other), and the row `materialiseDue` writes when that date arrives. A borrower who is shown रू 17,769.76 next month has to be debited रू 17,769.76 next month.

**A policy's premiums and a goal's contributions are owed exactly as an instalment is.** They run on the same machinery — a rule the app replays for a schedule that has to add up — so a premium swiped away makes the next one double, and `RecurrenceRepository.arrearsFrom` is the one place that says which rules those are. A rule the **user** wrote is the opposite and is deliberately excluded: deleting a month's salary says it did not arrive, and doubling next month's would be the app inventing income. It is the same line `watchedFrom` draws. A debt counts from the day its current balance started running, because a lump sum moves that day; a plan has no such day and counts from the rule's own start. Both halves of the transfer are scaled, since the money leaving the bank and the money landing in the policy are one movement.

**And the count of what has been paid reads one half of a transfer, not both.** `paidOccurrenceDays` filters on the rule's own direction: a transfer is two rows sharing one date, and counting both said every premium had been paid twice — so every one of them read as settled and none could ever be owed.

**A payment collecting arrears can be split back apart** (`LoanRepository.splitArrears`, the split mark on the schedule's first row). Rolling a missed instalment forward is the right default — money that is late is still owed — but it is not always what happened: the bank often took it a fortnight late, and then the honest record is a payment on *that* day. Only the day is asked for, one field per missed instalment and each named by the day it was **due**; what an instalment is worth is the schedule's answer and not the user's, and a field for it would let the two disagree. Each field is optional, because splitting one of three out and leaving the rest is a sentence the form has to be able to say. The row's own instalment is not offered — it is not missing, and dating it would ask the user to re-answer the row they are looking at.

Each date writes an occurrence of the loan's own rule exactly as `materialiseDue` would, `CONFIRMED` rather than `EXPECTED` (this is the user taking the row over, and a rule edit discards its own `EXPECTED` rows). The account it names comes from `RecurrenceRepository.accountForOccurrence` and not from the rule directly, which is why `watchedFrom` was lifted out of `materialiseDue`: two things write occurrences now, and a rule that narrow obeyed in one place and forgotten in the other is a rule the app breaks. **Floored at the day the money changed hands and deliberately not capped.** "I will pay July's on the 20th" is a real answer, and the whole point of asking is to say when. A day still to come settles no period *today*, so the debt goes on owing it and the balance does not move — the same rule that keeps a salary banked for the 3rd out of today's balance. What it does is come off `Arrears.carriedForward`, so the next scheduled payment stops asking for what is already promised. That is the one thing a forward-dated payment moves: `missed` is the schedule as it stands today, and when the day arrives the ordinary count picks the payment up and the period stops being missed by itself.

`WalletDatePicker` grew a `maxDate` on the way, greyed in both grids and capping the year list exactly as the floor does. Nothing uses it today: it was on the lump sum's date, because `applyPrepayment` clamped there — and **a payment can be dated forward now**, which is the right end of that problem to fix. "I am paying रू 4,30,000 off on the 30th" is a real answer and the whole point of asking for a date, and the app already knows what to do with a movement dated forward: it is written down, drawn in the month it falls in, and nothing feels it until the day comes.

**A payment ahead of today is recorded and not acted on.** There is no balance on a day that has not arrived, so `applyPrepayment` writes the row and returns; `LoanRepository.applyDuePayments` folds it in the first time the app opens on or after that day, beside `materialiseDue` and for the same reason. **What makes one pending is its date against `started_on`**, and nothing is written down to say so: a re-basing moves that day to the day of the payment, so every lump sum already folded in sits on it or behind it and only one still owed sits ahead — which survives a restore, a reinstall and a backup taken on another phone, where a flag would not. An overdraft's repayment moves the same mark, never backwards, since a facility's balance is a running total and its repayments are order-independent. It also repairs the one case the immediate re-base got wrong: a lump sum recorded *behind* one already on file discarded the later payment's effect, and the later payment is then ahead of the mark again.

Three things follow it. **Nothing on the debt says it is paid** — `principalPaidOutright` cuts at today, or "paid off early" quoted रू 5,80,000 beside a balance that had felt रू 5,30,000 of it; the card's own snackbar says the payment was noted rather than what it left owing. **The timeline's future month feels it** (`Loan.pendingPayments`, `pendingBy`), because the log has already drawn the row and a debt underneath ignoring it would sit contradicting it. And **deleting one takes nothing back**: it never moved the balance, so putting the money on would leave the borrower owing more than before they typed it.

**A skipped period is a row of zeroes, and nothing may read it as a payment.** `quotedEmi` took `rows.first()`, which on a debt whose *opening* instalment had been swiped away quoted "your first payment: रू 0" with the real figure on the next line down. The shape of a schedule is told by the rows that are payments, so first and last are taken from those.

**And the editor re-reads the debt when it comes back to the front.** Its statement and its schedule are pages of their own, and both change the debt — a payment swiped away on one puts money back on the balance, a carried instalment dated on the other takes it off the payment that was collecting it. `refreshLoan` is the debt's half of `refreshStatement` and follows the same rule: only what is settled, because the form may have half-typed answers in it and reloading the whole thing would throw them away on the way back.

**And what is left to pay is a page of its own** (`LoanScheduleScreen`, `LoanRepository.scheduleFor`), reached by the same card footer a debt's payments and a holding's transactions use. The table was drawn inside the editor behind a toggle, and the same three things were wrong with it that were wrong with the account statement: the editor is one long scrolling `Column`, so nothing in it is lazy and a seven-year loan composed eighty-four rows the moment it was tapped; it pushed the colour picker and Save a screen and a half down a form that is already long; and the rows are read down a column of near-identical digits, which is exactly what `rowStripe` exists for. A loan being *created* keeps the table inline: there is no loan to open a page for, and there the table is the live answer to what is being typed.

**Deleting a loan deletes what it put in the timeline**, past and future, following both links (`loan_id` and the loan's `series_id`). The app generated most of those rows itself from the schedule; left behind, they are payments to a debt that can no longer be opened, still holding an account balance down, removable only one swipe at a time. Closing a loan is the other answer and keeps everything: a debt that really was paid off keeps the payments that cleared it.

**Nothing the app generates for itself, dated before it was told about the loan,
may name an account.** Two places write such rows and both must obey it:
occurrences a rule generates, and the broken-period charge `saveLoan` writes
directly. The second was missed once and was the larger of the two —
रू 10,984.93 against a savings account holding रू 10,000, which is the whole of a
reported "the balance is gone". The disbursement is the one exception, on any
kind of debt, and belongs to the *user* rather than to a schedule: they named the
account, and leaving the field blank is how they say the balance already has it.
Both places read `watchedFrom` for the cutoff, which is where that disbursement
also moves it — see below.

**An occurrence of a schedule the app replays, dated before its rule was written,
names no account.** A loan
taken a year ago and entered today owes twelve instalments that really were
paid — the schedule needs them, or the debt reads a year behind — but they left
an account the app was not watching, and whose balance the user has since told it
directly. Debiting it again subtracts a year of payments from a figure that
already had them taken out, and the account goes negative for money long gone.
The cutoff is `recurring_series.createdAt`, not today: anything from the day the
rule was written onwards is money the app is watching leave, however late the app
is next opened. Same principle as recording nothing *arriving* when a loan is
created.

**But only for a schedule the app replays** — a loan's instalments, a policy's or
a goal's contributions. A rule the **user wrote by hand** has no cutoff at all,
and generalising this one to cover it was wrong. Somebody who writes "रू 100 a
month from Nabil Bank, from 14 April 2025" got one row that debited the account
and fifteen that named nothing: the fifteen still counted as spending, so the
month said money went out while no holding was any poorer, the account's own
statement listed one payment of the sixteen, and the balance was short by the
other fifteen. Nobody back-dates a rule by accident — doing it *is* the user
saying this has been coming out of that account since then, and the app's job is
to write down what they said. `materialiseDue` tells the two apart by asking
whether a loan owns the rule or its destination is a plan; everything else is the
user's own. `MoneyEntryDao.adoptOrphanedOccurrences` gives the account back to the
rows written under the old rule, on launch and once — narrow by design: only
`EXPECTED` rows (a confirmed one is the user's answer), only rules that are
nobody else's schedule, and only rules that are not transfers, since a back-dated
transfer is missing its arriving row and half a transfer put back is money leaving
for nowhere.

**Unless the loan's disbursement was recorded into that same account, in which
case the cutoff moves back to the day the money landed.** That is the one thing
that settles the question the rule above is guessing at: answering "money
received on: Nabil Bank" for a day last September is the user saying the app is
that account's bookkeeper from that day, so the balance they typed is what it
held *before* the money arrived and the instalments since have **not** been taken
out of it. Left out, an account credited with रू 27,00,000 in September sat there
holding a whole year of payments it had really made, and the timeline showed it
untouched in every month it had been paying from. `LoanRepository.watchedFrom` is that day —
`min(loan.createdAt, disbursed_on)` when `disbursed_account_id` is the account in
question — and **both** places that generate rows read it: the occurrences
`materialiseDue` writes, and the broken-period charge `saveLoan` writes directly.
The second is the one that gets forgotten, and it is the largest single row a
back-dated loan produces: रू 10,984.93 that the account paid on 20 September and
the app said it had not. A charge that names an account beside instalments that
do not is an account that pays the interest and never the loan.

**The rule is written before the loan and must not generate anything yet.**
`saveLoan` calls `saveSeries` to get a `series_id` to store, so at that moment
the loan row does not exist and `materialiseDue` cannot see which account the
money was disbursed into — every back-dated instalment came out naming none, and
the fix above did nothing at all. `saveSeries(materialiseNow = false)` holds it
back and `saveLoan` runs `materialiseDue` once the loan is on file.

It applies when the rows are generated, so a loan already on file keeps the rows
it has — deleting and re-adding it is what corrects one.

**Every row on it leads somewhere, except the app's own working.** A statement row opens where the movement belongs — a payment towards a debt on that debt, everything else on the money form — which is `StatementTarget`, decided in the view model because only it knows which account is being read. Interest the app credited to *this* account is the one row that opens nothing: it would land on the page it was tapped on, and it is the app's own arithmetic rather than anything the user typed. Told by its derived id (`INTEREST_POSTING_SUFFIX`), the same way the debt's opening movement is. A loan's statement does the mirror image: each payment opens the holding it passed through — the bank it left, or the cash tin — and a row naming none stays untappable, because there is no page for money that left nothing.

**An account can show its working, on a page of its own** (`AccountStatementScreen`, reached from the footer of the balance card). It is deliberately the same page a debt's payments get and is built to match it — one back arrow, the holding's name in the bar, where it stands now in a card, then the rows — because two lists answering the same question about two kinds of holding must not be two different-looking screens. It was drawn inline in the holding's editor, behind a toggle, and three things were wrong with that: the editor is one long scrolling `Column`, so the list is not lazy and every row of a decade-old salary account composed the moment the toggle was tapped; opening it pushed the colour picker and Save a screen and a half down a form that is already long; and the running balance — the column somebody opens it for — was read through a viewport a third of a page tall. What the editor keeps is the balance and the way in, and it re-reads that balance on `ON_RESUME` (`refreshStatement`), because a row swiped away on the statement restates it — only the balance, since the form may have half-typed answers in it. `statementFor` gives every row that has
touched one, newest first, each with what the balance stood at afterwards — the
column the user reads down when a figure is not what they expected. Balances
elsewhere are totals; this is the only place the app shows how it got there, and
without it a wrong figure has nowhere to be checked. Its rows swipe away too —
every one but a loan's instalment — and through the same door, so a payment
removed from an account's statement puts back whatever it took off a debt.

**It stops where the balance it explains stops**, which is today — the same cut
`observeBalances` makes. With the future in it, the running column climbed past a
salary banked for the 3rd that no other screen in the app had felt, and the
account read one figure on its own page and another everywhere else. What is
still to come belongs on the Timeline, where each row says so.

**And it arrives a page at a time**, `PAGE_SIZE` of it, with `SeeMore` at the
foot asking for the next — the same for a debt's own statement, which is a whole
screen away. A salary account a decade old has hundreds of movements and the
answer somebody opens the list for is nearly always in the last fortnight;
worse, the account's list is not lazy at all — the editor is one long scrolling
`Column` — so every row of it composed the moment the toggle was tapped. `SeeMore`
is deliberately what the currency row's "Show more" is, an action rather than one
more row: a filled button at the end of a list reads as the end of it rather than
as a way past it.

**One rule, one gap, everywhere something is separated** (`FOOTER_GAP`). A form is a stack of unlike questions — what it is, what it earns, which account it is paid from, what colour it is — separated by nothing but a gap, and a gap is also what separates a field from the sentence explaining it, so nothing said where a *new* question began. `SectionHeader(divider = true)` draws a rule above the heading; `ScheduleToggle` and `MovementAccount` draw the same rule above themselves, being the last row of a card rather than a heading; and the two card footers below are the same thing again. Never above the **first** section of a form, where there is nothing to separate from and the rule reads as part of the app bar, and never inside a card that is already its own separation.

**And the toggle that opens a schedule in place is spaced the same way** (`ScheduleToggle` — a policy's premiums, a goal's contributions, a loan being written down). It owns the whole rhythm rather than leaving the gap above the rule to its callers, because it is the same offer at the foot of the same kind of card: one drawn at eight points and the other at fourteen read as two different ideas on two screens a tap apart.

Two things have to be right for them to match, and the first attempt got neither. There is **no spacer between the rule and the row** — the row's own top padding is that gap, and adding one as well doubled it. And the **card gives up its bottom padding** whenever the toggle is drawn (`cardWithFooter`), or the words sit a footer's gap *plus* the card's inset from the edge. What the expanded table then needs is that padding back, which it supplies itself: the card cannot, because when the toggle is closed the words are the last thing in it.

**And both ways in are one component** (`CardFooterAction`) — "Every transaction"
on a holding's card and "See every payment" on a debt's, each a rule with one
full-width action under it and a chevron pointing along, because both open a
page. The rule is where the card stops stating figures and starts offering
somewhere to go; without it each read as one more line of the balance above.
**The spacing is symmetric about it**, which is why this is a component and not
two hand-built footers: both were a spacer, a rule and a `TextButton`, and a
`TextButton` carries a 40dp minimum height with the card's own bottom padding
under it — so the rule sat a dozen pixels below the figures and sixty above the
card's edge, and the footer read as a band of empty paper with a word floating in
it. One gap above the rule, one below, one under the words, which is what
`cardWithFooter` takes the card's bottom padding away for.

**And the line over that list says what the swipe does, in the words the gesture deserves.** It said "swipe to *undo* it", which is what the app does to the balance rather than what the user does to the row — and it promised a missed instalment on the next payment to every debt alike, including money with a person, which has no schedule and so cannot have one. So it is "swipe a payment left to **delete** it, the balance **will be** restored", and the clause about the next instalment stays only where there is a schedule to say it about (`loan_ledger_explain_person` beside `loan_ledger_explain`).

**A debt's payments and an account's transactions are drawn identically.** Both are banded and nothing else divides them: the ledger carried a hairline under every row *as well*, which is a ladder, and made the same list about the two kinds of holding into two different-looking screens.

**A movement is named by what it is.** `entryTitle` is the single answer — the
note first, then what the row *is* (an instalment, the two ends of a transfer,
the person a debt is with, a quarter of interest the app credited itself) — and
every list calls it: the statement, Home, the timeline. A row with none of those
and no note says **"Money out"** or "Money in", which is the plainest true thing
left to say about it; it used to fall back to the label it was filed under, and
before that to the words "Not labelled", which blamed the reader for an omission.
Nothing carries a colour beside the words any more: colour belongs to a
holding and is drawn where holdings are, which is the Accounts page and the
breakdown on Home.

**Fill means "write here".** The one visual job the editor has is telling a live
field from a settled one, and for a while it did the opposite: the read-only
boxes were filled white while the editable ones sat flat on the page's grey, so
the form advertised the reverse of what it did. Editable fields take
`editableFieldColors()`; settled ones keep the page behind them. A settled
*value* that is prose — a name, an amount — is plain text under a small label;
one the eye hunts for in a box — a date, a length — keeps the box, disabled.

**A form asks once and states afterwards.** The kind chips were the first to
become plain text on an existing holding; the same is now true of everything that
would rewrite history rather than describe it — a bank's name, the currency, the
starting balance, a loan's term, frequency, repayment shape, instalment figure,
dates and paying account. What can genuinely still change keeps its field: the
rate (banks reprice), the loan amount, the colour. `SettledField` is the one
place that draws the difference, and a settled *date* always carries its year,
because "१२ साउन" happens every year and a loan's is usually not this one.

**A month is shown after its schedule has run, and that includes what is already
recorded for it.** Two things move a balance forward: occurrences `projectForward`
computes from a rule, and *real entries the user has already dated in the future*.
The second fell through every crack — no rule produces them, so the projection
never saw them, and `observeBalances` cuts at today, so the current balance did
not hold them either. A salary banked for the 3rd reached no account at all.
Anything that projects a balance has to add both.

**Everything the timeline lists below the log is what this month moved — the debts included.** Every kind of holding is eligible — a bank account, a wallet, a cash tin, a deposit, a policy, a goal, and each of the three debt sections — and what narrows the list is activity, not kind: it appears when an entry dated inside the window or a projection falling inside it names it. A month is a story about some of the user's money and not all of it, and listing every holding they own put the two September touched among five it did not. A debt is moved by an instalment already paid, by one still to come, or by anything else against it — a lump sum, a drawdown, more borrowed — which is why the set is built from `MoneyEntry.belongsToLoanId` and from the series behind each projection, not from the loan table. Both halves of a transfer count, so a movement between two accounts shows both; anything untouched is the figure the Accounts page already gives.

**And an arrangement that began inside the window was moved by it**, whether or not it wrote a row. Going from not existing to owing what it owes is the largest thing that ever happens to a holding, and it is exactly the case with nothing to find it by: money lent to a person last November with no interest, no schedule and no account named writes no entry at all, so the one month it belongs to more than any other was the one month the page did not list it. The same was true of a deposit put away, a policy taken out, a goal started and a card approved — each absent from the very month it began in. A debt's beginning is `disbursed_on`, or a facility's `opened_on`, or failing both `started_on` (which a lump sum moves, so on a debt already paid down it names a re-basing rather than a beginning — still a month that moved it, and the only answer some debts have); an account's is `deposit_started_on`, which only a deposit, a policy and a goal have. A bank account or a cash tin is deliberately left to its movements: the day it was typed into the app is a fact about the app rather than about the money. Only under **Everything** — a beginning that put no row in the log has no business under a log narrowed to money going one way, which is the rule the filtering already obeys.

**And the same question is asked of whatever the filter has left.** The blocks are the other half of the page the chips narrow, so "Money out" lists the holdings this month's spending moved and nothing else — an account that only ever received money had no business under a log filtered down to what went out. It is the row predicate (`matches`) doing it, so a transfer moves no holding into either answer, exactly as it appears in neither list. What is filtered is *which* holdings are drawn and never what their figures say: each still states where the whole month leaves it, because a balance that counted only half the month's movements would be a number that is true nowhere.

**A month is shown after its schedule has run, and that includes the debts.**
The accounts on the timeline project forward to the end of the month being
viewed; `Loan.outstandingAfter` moves the loans over the same horizon, from the
instalments `projectForward` says fall in it. Without it a debt sat directly
under an account balance that had felt those payments, contradicting it — and it
was the loan that looked wrong. It goes through `LoanMath` rather than
subtracting the instalments, for the usual reason: most of an early payment is
interest, and naive subtraction clears a loan years too soon.

**And a month that has been and gone is answered as it stood.** The stepper runs
backwards as well as forwards, and there the question is not where the schedule
leaves a balance but where it had left it: `observeAccountBalances(asOf)` and
`observeLoansWithBalance(asOf)` both take the last day of the window whenever it
is behind today, so stepping back climbs a debt by one instalment a month exactly
as stepping forward brings it down. `asOf` has to reach `toDomain` as well as
`outstandingOf`, because `Loan.outstandingAfter` recomputes the schedule from
`paymentsMade`: a balance asked of June sitting beside a count of every payment
made since would answer with today's figure the moment anything projected it
forward. It moves the *schedule*, which is the figure every list prints; interest
metered day by day on a debt with no schedule still reads today, and no
past-month row prints it. The "now …" line on both an account and a debt is
withheld when the month leaves the figure where it found it, or every row on a
past month said the same number twice.

**But a schedule is the only part of a debt that can answer for itself, and the
stored figure describes today.** Instalments are counted from the rule's dates,
so any day can be asked about; everything else was written straight into
`principal_minor` — a lump sum re-bases the debt in place, a top-up adds to it, a
drawdown and a card purchase raise it — and a debt asked what it was worth last
November answered with what it is worth now. रू 8,000 lent to somebody read
रू 18,000 in the month before the second रू 10,000 was handed over, and a
रू 4,30,000 lump sum paid in June showed as already deducted every month back to
the day the loan was taken. `LoanRepository.rewound` is the correction, and it
takes the same two shapes `LoanLedger` takes for the balance column on a
statement:

- **A running total is walked backwards from today**, movement by movement. It
  has to be backwards: the figure such a debt opened at is not on file anywhere
  and only the present balance is a fact. The debt *arriving* is one of those
  movements, so a month before the money changed hands reads zero, which is what
  it was.
- **A schedule needs only what it cannot see** put back — the lump sums and
  top-ups, by `LoanDao.basisChangesAfter`, which excludes the opening by its
  derived id because on a loan with a schedule the principal was already the sum
  borrowed before that row was ever written.

**And a month before a lump sum is answered on the basis the debt was written
down with**, rebuilt by `asFirstWrittenDown`, so those months go on climbing an
instalment at a time instead of sitting flat at the balance the payment met. A
re-basing overwrites five things at once — the balance, the term, the
first-instalment date, the carried interest and where the rule starts — and four
of them come back from figures it deliberately leaves alone: `advanced_minor` is
what was taken, `disbursed_on` is when it started running, the term is however
long that takes to clear at this instalment, and the first instalment is the
current one **stepped back a period at a time** until it is the first after the
money arrived — which works only because the instalment keeps the day it has
always fallen on, so the whole schedule sits on one cycle. The fifth is the
instalment figure itself, which a borrower who chose to lower it rather than
finish sooner has changed with nothing on file saying what it used to be: that is
why the rebuild is reached **one re-basing back only**, and why anything else
falls through to putting the lump sums back on, which states the balance the
payment actually met. Either way no deduction is drawn in a month before the
money moved. `Loan.outstandingAfter` returns `outstanding` untouched when there
is nothing to project, or it would rebuild the schedule from `principal` and
throw the rewind away.

**A row that belongs to a debt opens the debt, wherever it is tapped** — the
timeline, Home, Reminders — and that is all of them, not just the instalments.
The money-out form cannot say "this is a lump sum against that loan", or a
drawdown, or the interest for the broken first period: it has no field for any
of it, so opening one there offers nothing to correct and one thing to break — a
re-save writes back a plain payment, and the row that rewrote `principal_minor`
stops pointing at the debt it rewrote. Every one of them is made on the debt's
own screen, and half of them the app wrote for itself from dates the user gave
it, each with an id derived from the loan's. `MoneyEntry.belongsToLoanId` is what
makes the debt reachable: `loanId` is only what the row itself stores, and an
instalment stores no loan at all — it is found through its series, exactly as
`loanName` is. `openEntry` is the one place that decides.

Interest-only payments must leave the balance exactly where it was — that is the point of servicing interest — and the UI says so, because a user expecting the debt to shrink would think the app lost their money.

**And it says so on the back of the row, not by refusing to sign the amount.** A statement row has two jobs: what was handed over, and what that did to the debt. They were run together for a while — interest serviced on its own was drawn unsigned and uncoloured, on the reasoning that a minus would claim the debt had come down by that much. But रू 10,984.93 really did leave the account and is gone, and drawn flat among a column of signed payments it read as a transfer, as though nothing had happened — while the card above it was already counting the same figure into "paid so far, interest included". So the amount is signed and coloured like the payment it is, and the row **turned over** says the rest: was owing रू 27,00,000, interest रू 10,984.93, left owing रू 27,00,000 — the same figure top and bottom, which is the honest way to say the debt did not move and reads as a statement rather than as a column that failed to change. `LoanLedger` therefore fills `balanceAfter` **and `balanceBefore`** for the interest row, carrying the schedule's running figure past it; the debt arriving gets the after and not the before, since the schedule's figure ahead of that row is what the borrowing *created* rather than what was owed the day before it; and a lump sum is deliberately still null on both, because it re-based the loan and the schedule above it belongs to a debt that no longer exists.

**A row on a debt's statement turns over and shows its working; it does not open an editor** (`LedgerRowView`, `LedgerRowWorking`). Every line on that page is the app's own record of what the loan did — an instalment its rule wrote, the interest its rate charged, the balance its schedule arrived at — and each figure is read back out of the loan rather than stored on the row, so a tap that reopened the entry form offered to retype a figure the schedule would go on quoting its own version of. A mistyped *amount* is corrected on the card that recorded it. What a reader arrives with instead is *why did a full payment barely move the balance?*, and the four figures that answer it — `balanceBefore`, the interest, the principal, `balanceAfter` — used to be scattered over the front of the row: the split crushed into a sentence under the date, what was left stranded at the foot of the amount column, and the figure it was all worked out from nowhere at all. Turned over they are one sum, ruled off above the answer. **Both faces are always composed, one at zero alpha and out of the semantics tree**, so the box is as tall as the taller of them and a turning row does not change the height of the list under it; the shorter face is centred in that height, or every unturned row reads as having a blank line under it. The angle is read inside `graphicsLayer` and never in composition, so a turn repaints without recomposing. A row the app can say nothing behind — a payment made in another currency — does not turn at all (`LedgerRow.hasWorking`): a card that turns to a blank back is worse than one that does not turn.

**Everything that happened *to* a debt can be swiped off it; the debt arriving cannot** (`LedgerRow.canDelete`, now `kind != OPENING`). Instalments and lump sums go, and the balance comes back with them — an instalment leaving a period that charged its interest and cleared nothing, which the next payment collects. The opening row is not a payment but the loan itself: removing it would leave a debt with a balance, a schedule and a year of instalments behind it and no money ever having been borrowed, which is a hole rather than a correction. The way to undo a loan that should never have been written down is to delete the loan, which the accounts list already offers and which says outright that it takes every payment with it.

### The one ad

**The ids are the app's own** — `ca-app-pub-4483991085473763~2654037317` in the manifest's `APPLICATION_ID` meta-data and `…/5190223826` in `AdIds.INTERSTITIAL`, registered against `com.qevixlabs.mywallet`. They must agree: the SDK reads the manifest at process start and refuses every request if the unit belongs to another account. This is the hard half of the lock on the `applicationId` above — an ad unit is bound to the package it was created for, so moving the package again orphans them. A freshly registered unit is allowed to answer "no fill" for a while; that is the account warming up rather than anything being wrong.

**`AdConfig.ENABLED` is the switch, and it is on.** With it false nothing is requested, the SDK is not started, and no rule below runs — which is what makes the app walkable: an interstitial arriving part way through a form costs the walk, and every screenshot taken with one on it has to be taken again. Turn it off for any session like that. It is checked inside `InterstitialAds` itself as well as at the trigger, because a switch that has to be remembered at four call sites will one day be forgotten at one of them. What it does *not* switch off is the account risk: the ids are real, so an ad served to a phone this repo is developed on is a real impression and a tap on it is invalid traffic. The emulator is a test device automatically; a real phone is not, so the developer's own phone is named in `AdConfig.TEST_DEVICES` and the configuration is set **before** `MobileAds.initialize` — a device told about it afterwards has already had one real ad served to it. That list ships rather than being stripped out before release, because the phone this is tried on runs the shipped build: there is no build type to hide it behind, and one id costs everybody else nothing.

**Consent comes before the SDK, not after it.** Play ships this app to every country it is not withheld from, and in the EEA, the UK and Switzerland an ad served with no consent record is a policy breach the *account* answers for. `user-messaging-platform` is a separate dependency from the ads SDK — it is not pulled in transitively, so the two are listed together in `libs.versions.toml` and `AdConsent` is the whole of what the second one is for. `InterstitialAds.preload` therefore no longer starts the SDK itself: it hands to `AdConsent.gather`, and `MobileAds.initialize` runs from that callback, only once `canRequestAds()` is true. On a phone whose owner refused, the SDK is never started at all.

This is invisible where it matters least and untestable where it matters most. Outside those regions there is no form to load, `gather` finds it can request ads on the first call and hands straight back — so nearly every user of this app, and the developer's own phone, see nothing and prove nothing. Use `ConsentDebugSettings` with a hashed device id and `DEBUG_GEOGRAPHY_EEA` when the form itself needs looking at. `gather` may call back immediately, or after a form is dismissed, or twice, or never; `startSdk` guards itself with a `compareAndSet` for that reason, and callers must be safe to enter more than once.

**The form has to exist in the console or none of it works.** With no published European-regulations message, UMP answers `Publisher misconfiguration: ... no form(s) configured for the input app ID` — the app is correct and the account is not. Publishing that message needs a privacy policy URL on the app in AdMob.

**"Account not approved yet" is not a bug.** A newly registered unit answers `Ad failed to load : 3` with those words until the app is linked to a store listing and passes AdMob's app-readiness review. The listing was linked on 6 Aug 2026 — a closed test is enough for AdMob to find it, the production track is not required — and the review is what remains; nothing in this repo can shorten it.

**It is raised by leaving a screen, not by standing still.** The trigger used to be idleness — the user at rest on a tab for eight seconds — and idleness is a poor proxy for "finished": somebody reading down their own timeline is at rest, and an ad arrived under a moving thumb three times while that was being tested. What replaces it is **backing out onto a tab** (`WalletApp.onLeftScreen`: anything that is not a top-level destination is a screen the user opened on purpose, so coming back out of one is a piece of work finished) and **the app coming back to the front**, which waits `AdConfig.AFTER_RESUME_MS` first — never in the frame the app returns in, where a full-screen ad reads as the app having been replaced rather than as an ad.

**Each of those is considered exactly once.** `AdCue` carries an id that only climbs, so two events in a row are two considerations and a recomposition is none; the effect watching it makes one attempt and stops. Nothing is retried on a miss — a failed load or an ad that could not go up has missed its moment and waits for the next trigger — though the *next* one is fetched, which is not the same thing.

**And everything it must be true of is asked at the moment it would appear**, not remembered from when the cue was raised: the activity still resumed, the user still simply standing on a tab (`idleRoute`, so a cue raised by a resume cannot cover a half-typed payment the app was reopened inside), and `AdConfig.MIN_GAP_MS` since the last one.

**Never on a first run and never on an empty app.** `firstRun` is this phone having had nothing on it when the app launched — the same session the setup questions, both swipe lessons and the lock offer run in, so withholding on that one flag withholds the ad from every one of them. And `hasFiguresOfTheirOwn` asks the database for one holding or one movement: an app opened, looked at and not yet used is somebody deciding whether to keep it, and advertising at them costs the decision. Asked of the database rather than held as a flag, because it becomes true the instant they add their first account.

## Working in this codebase

**Migrations.** `exportSchema = true`, and `app/schemas/<version>.json` is committed. Adding a column means: change the entity, bump `version` in `MyWalletDatabase`, hand-write a `Migration` in `Migrations.kt`, add it to `Migrations.ALL`, and commit the new schema JSON. There is no `fallbackToDestructiveMigration` and there must never be one. Before letting a migration near a phone, prove it: build the old schema from `schemas/<n>.json` with the `createSql` it contains, apply the migration SQL, and diff columns/types/defaults/indices against `<n+1>.json` — that is what Room checks at open time. Then do a real upgrade on the emulator over a seeded old database.

**`android:allowBackup` is false, and that is what makes "the copy on the phone is the only copy" true.** Android's Auto Backup is on unless a manifest says otherwise, and what it uploads is the whole Room database — the user's complete financial history — to their Google Drive, silently and with no screen in this app saying so. An offline-first money tracker with no account cannot promise no server and then ship the platform default that quietly is one. What replaces it is the app's own backup below: the same safety net, to a folder the user picked, at a moment they chose. It also decides what the Play Data Safety form may say, so the two must not drift.

**Backups** are JSON, not a copy of the `.db`, so a user can salvage them by hand years later. Restores merge: a row is overwritten only when the incoming copy is strictly newer, and tombstones (`deletedAt`) are honoured so something deleted on another device stays deleted. New fields must be optional with defaults, and bumping `CURRENT_FORMAT_VERSION` makes older builds *refuse* the file — so only bump it when a file genuinely cannot be read by them. It is still 2 after the debts, the rules, the rate moves and the rest of a holding's terms were added, for exactly that reason: an older build reads such a file with `ignoreUnknownKeys` and loses the new parts, which beats refusing a file it can read most of.

**Every column of every table it covers has to be in the file, and `BackupFormatTest` is what keeps it that way** — it compares field names on both sides of each mapper, so a column added to an entity fails the build until it is carried through. That test exists because the format was missing a great deal and said nothing about it: no loans, no rules, no rate history, and none of a deposit's term, a policy's premium or a goal's target. A restored phone came back with every entry and every account and no debts at all.

Three things about the merge are load-bearing:

- **Order.** Accounts go in before anything that points at them, because the references are real foreign keys — a rule carrying an unknown account id is refused, and one refused row used to abandon the whole restore.
- **Every reference is resolved before use.** A hand-trimmed file can name an account it does not contain, and that is dropped to null: an entry that has lost which holding it moved through is a small loss, one that never arrived is not.
- **One transaction, and tombstones are visible inside it.** `findAnyById` is the only read in the app that sees deleted rows, and the merge needs it: a merge blind to the tombstone treats a row deleted on *this* phone as one it has never met and brings it straight back.

**A same-named, untouched holding is folded by name.** This was written for the Cash account the first run used to create: restoring onto a reinstalled app brought its own Cash with a different id, and the user was left with two — one holding every rupee of history and one holding nothing. Nothing is seeded any more, so the case it was written for is gone, but the rule outlives it and holds for any holding the user made themselves and never used. Only a same-named holding of the same kind that nothing has ever touched is folded, so two accounts a user deliberately named the same are left alone.

**Strings** always live in resources, never hardcoded in Composables, and every new string needs its Nepali counterpart in `values-ne/` or lint fails the build. Delete strings that fall out of use — `UnusedResources` will find them.

**One title for a form the user arrived at.** Every editor reached through a back arrow says what it is editing in the same words — "Edit account" for every holding on file, debts included. It used to say "Edit loan" on a debt, which meant a bank's tabs changed the heading as the thumb moved along the row and read as having landed somewhere else.

**What a holding is, is answered once.** The kind and its sub-kind are chips
while creating and plain text afterwards. Savings and current are different
products, a term loan and an overdraft are different debts, and flipping
borrowed to lent would reverse the meaning of every payment recorded against it.
`HoldingChoice.groupsFor`/`bankHoldingsFor`/`personHoldingsFor` still narrow the
lists and are still tested: they are the backstop underneath the UI, not the UI.

**The launcher icon is an adaptive icon and nothing else** — minSdk is 26, so
there are no legacy square PNGs to keep in step. Two rules about it, both learned
on a device rather than reasoned about:

- **The artwork's *diagonal* fits the 72dp the platform guarantees, not its
  width.** The guaranteed region is a circle; fit a landscape subject to 72dp
  across and a round launcher mask slices both of its sides off at mid-height.
  Regenerating from source art means trimming the soft shadow around it too, or
  the shadow reads as grime on the tile.
- **The mark sits well inside that circle rather than filling it** — its diagonal
  is about 62 of the 108, so there is tile around it. Filling the tile made the
  icon a picture cropped to a square; air around a smaller mark reads as an icon.
  It keeps a cream stroke grown from its own silhouette, invisible against the
  pale top of the tile and there for whatever a themed launcher does with it.
- **The tile is a vector, not a colour** (`drawable/ic_launcher_background`), because
  it holds a gradient — white at the top, through sky blue, into a tint of the
  app's own green at the bottom. It covers the whole 108dp and not just the
  guaranteed 72: the outer ring is what a mask and its parallax eat into, and a
  background stopping short of it shows as a pale edge on some phones and not
  others.
- **A gradient's stops go where the mask can see them.** Only the middle 72dp is
  drawn, so offsets past about 0.83 are bleed. The first attempt put the green at
  1.0 and the icon read as white with a hint of mint — the colour was there, in
  the part no launcher shows.
- **The monochrome layer is its own flat glyph** (`ic_launcher_mono`), not the
  artwork. A themed icon is drawn from alpha alone, and an illustration with
  highlights and a shadow reduces to a smudge.
- **`mipmap-anydpi-v26` keeps its `-v26`** even though lint calls it unnecessary at
  minSdk 26. Drop it and the resource merger stops producing `mipmap/ic_launcher`,
  and the manifest cannot resolve its own icon.

Several earlier attempts are why it looks like this: a *green* wallet on the app's
dark green left nothing to see at launcher size, a brown one filling the tile was
busier than an icon should be, and a flat white tile was flat.

**The app is called "My Money Tracker"**, and it wears three names because the
three places it appears have different room:

| Where | Name | Set by |
| --- | --- | --- |
| Play Store listing | My Money Tracker | typed into the console, not built from the APK |
| Settings, app info, notifications | My Money Tracker | `appLabel` placeholder → `<application android:label>` |
| Icon caption, recents card | MyMoney Tracker | `launcherLabel` placeholder → `MainActivity android:label` |

A launcher gives a caption about ten characters a line and breaks it at spaces,
so "My Money Tracker" arrives there as "My Money" with the rest cut. Closing the
one gap keeps the name whole under the icon without costing the spaced form
anywhere it fits — including the store title, where the exact phrase people
search for has to survive. The activity label shadows the application one and
*only* the launcher and recents read it; that is the whole reason for the split.

Both are manifest placeholders rather than `app_name` so each build type can say
its own — a debug install beside a real one is meant to be obvious. The debug
launcher label is "MyMoney debug", not "MyMoney Tracker debug", because the same
ten-character line would drop the one word that tells them apart.

`app_name` is therefore unreferenced today and kept anyway, being the spoken name
and the first thing anything new would reach for.

**The old name, "My Wallet", is still all through the source and should stay
there.** `com.mywallet` is the Kotlin package, not the `applicationId`, and
`MyWalletApp`/`MyWalletDatabase`/`MyWalletTheme`/`Theme.MyWallet` are internal
identifiers no user can see. Three of its appearances are load-bearing and
renaming them breaks phones that already have the app: `applicationId
com.qevixlabs.mywallet` (Play identity and the AdMob unit both bind to it),
`MyWalletDatabase.NAME = "mywallet.db"` (rename it and every existing user opens
an empty app), and the `MyWallet.apk` asset name, which `release.sh` writes and
`UpdateChecker` fetches by literal URL — they have to agree or installed github
builds stop finding updates.

It is marked `translatable="false"`, because a product name is the same in both
languages. That was for a long time the one `MissingTranslation` error the build
carried "on purpose" — which meant `lintDebug` never exited zero, and an error
that always fires is one nobody reads. Saying the string is not translatable is
the same decision stated where the tool can act on it. **Lint is green now, so
anything it reports is new and is yours.**

**A class is named what the screen calls itself.** The tab reading "Timeline" is
`TimelineScreen`/`TimelineViewModel` on route `timeline`, and the one editor for
anywhere money sits is `HoldingEditorScreen`/`HoldingEditorViewModel` on route
`holding` — both were renamed when their words were, having been `History*` and
`AccountEditor*` long after the UI stopped saying either. When a label changes,
the file and the class change with it: a screen called one thing in the code and
another on the phone costs a search every time somebody goes looking for it.

**Comments** in this codebase explain *why*, especially where a simpler-looking alternative is wrong (an ordering that matters, a rounding that must not drift, a rate that must not be recomputed). Match that: state the reasoning, not the mechanics. `imePadding()` before `verticalScroll` in the editors is one of many places where the order is load-bearing and commented as such.

**Nothing suspends inside a state copy.** A view model that writes `_state.value = _state.value.copy(x = somethingSuspending())` reads the old state *before* the query runs and writes it back *after*, so every emission that lands in the gap is silently undone. The holding editor loads in two coroutines — one reading the settings, one collecting the accounts and loans — and a shortlist query put in the middle of one copy reverted the other's work about six times in ten: the bank-name suggestions, the bank tabs and the whole "Money pay from" row were empty for the life of the form, because the flow does not emit again until something in the database moves. Work the value out into a local first, which is what every other loader in that file already does. It fails a few times in ten rather than every time, so a single run of the app is not a test of it.

**Toolchain gotchas**, each of which costs a build cycle to rediscover: AGP 9 has built-in Kotlin and hard-errors if `org.jetbrains.kotlin.android` is applied (Compose needs only `com.android.application` + `kotlin.plugin.compose`); `compileSdk = 37` is required by current AndroidX while `targetSdk` stays 36; KSP versions track Kotlin separately; and `MainActivity` must extend `AppCompatActivity` or `AppCompatDelegate.setApplicationLocales` silently no-ops and the language picker does nothing.
